# 03 · Модель asyncio

**Мост:** [потоки](./02_threads_gil.md) позволили одному процессу пережидать
несколько I/O-операций: пока thread A стоит в `recv()`, thread B работает.
Но каждый поток несёт собственный стек и участвует в переключениях ОС.
Здесь один OS-поток будет держать много незавершённых операций как
async-задачи и переключать их в явных точках ожидания. В следующей главе
проверим, какой единственный блокирующий вызов способен остановить всю эту
схему.

**Вопрос сюжета:** как event loop продвигает несколько запросов в одном
потоке и что на самом деле происходит в строке с `await`?

### С собесов

Спрашивают: «Что такое event loop?», «Чем корутина отличается от task?»,
«Что делает `await`?», «Выполнится ли `async def` при вызове?» и «Почему
CPU-bound функция блокирует asyncio?». Частый провал — отвечать:
«`await` запускает функцию параллельно». `await` сам не создаёт поток и не
обещает параллелизм; он связывает корутины и может приостановить текущую,
пока ожидаемый результат не готов.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| цикл событий | event loop | Диспетчер: запускает готовые задачи, следит за таймерами и готовностью I/O |
| корутинная функция | coroutine function | Функция, объявленная через `async def` |
| объект корутины | coroutine object | Незавершённое вычисление, полученное вызовом `async def`; сам вызов его ещё не исполняет |
| задача | task | Обёртка, которая регистрирует корутину в event loop и хранит её состояние/результат |
| ожидаемый объект | awaitable | Объект, который разрешено поставить справа от `await`: корутина, task, future и другие |
| `await` | await | «Продолжи это вычисление; если результат ещё не готов, приостанови меня и верни управление loop» |
| готовность I/O | I/O readiness | Сокет сейчас можно читать или писать без обычного блокирующего ожидания |
| кооперативное переключение | cooperative scheduling | Задача сама доходит до точки, где отдаёт управление; loop не прерывает произвольный Python-код посередине |

Слово *task* перегружено. В Linux-главе M4a им могли называть сущность,
которую планирует ядро, — примерно OS thread. В этой главе `Task` означает
именно объект `asyncio` внутри Python-процесса. Event loop продвигает его
сам; планировщик ОС о такой async-задаче напрямую не знает.

---

## Четыре объекта на разных уровнях

```text
процесс Harbor
└── OS thread
    └── event loop
        ├── Task A ── исполняет coroutine handle_request_A()
        ├── Task B ── исполняет coroutine handle_request_B()
        └── Task C ── исполняет coroutine refresh_rooms()
```

Процесс и OS thread создаются через механизмы ОС, а CPU планируется для
готовых потоков. Event loop — код библиотеки внутри потока. Task — объект
Python внутри loop. Корутина — вычисление, состояние которого task может
приостанавливать и продолжать.

Фраза «корутина — лёгкий поток» иногда помогает почувствовать масштаб, но
стирает важную границу. OS thread может быть вытеснен планировщиком почти в
любой момент. Обычная корутина `asyncio` переключается кооперативно: пока
она не дошла до `await`, который действительно приостановил выполнение,
другая задача этого loop не получит поток.

---

## Вызов `async def` ещё не запускает тело

```python
import asyncio


async def load_room(room_id: str) -> str:
    print(f"start {room_id}")
    await asyncio.sleep(0.1)
    print(f"done {room_id}")
    return room_id


async def main() -> None:
    room_coro = load_room("Atlas")
    print(type(room_coro).__name__)
    room = await room_coro
    print(room)


asyncio.run(main())
```

Вызов `load_room("Atlas")` создаёт объект корутины. До строки
`await room_coro` тело не печатает `start Atlas`. `asyncio.run(main())`
создаёт event loop, запускает корутину `main` и закрывает loop после её
завершения.

Упрощённый вывод:

```text
coroutine
start Atlas
done Atlas
Atlas
```

Если создать объект корутины и забыть его `await`-нуть или превратить в
task, работа не выполнится. Python обычно предупредит, что корутина никогда
не была ожидаема. Такое предупреждение означает не «результат пришёл
поздно», а «вы создали рецепт вычисления и выбросили его».

---

## Корутина и task — не синонимы

Прямой `await` выражает зависимость: текущая корутина не может продолжить,
пока дочернее вычисление не даст результат.

```python
room = await load_room("Atlas")
```

Если сначала нужна независимая незавершённая работа, корутину регистрируют
как task:

```python
task = asyncio.create_task(load_room("Atlas"))
# здесь текущая корутина может запустить другую работу
room = await task
```

`create_task()` не создаёт OS-поток и не запускает тело «прямо внутри
вызова». Он ставит задачу в очередь готовых работ текущего event loop.
Тело начнёт исполняться, когда текущая корутина отдаст управление loop.

```text
coroutine object                    Task
«что можно исполнить»      →       «loop обязан продвигать это вычисление»
                                     │
                                     ├── состояние: ready / waiting / done
                                     ├── результат или исключение
                                     └── связь с event loop
```

Задачу нужно кому-то ждать и обрабатывать её результат. «Запустить и
забыть» опасно: родитель может завершиться раньше, исключение потеряет
контекст, а незавершённая работа будет отменена при закрытии loop.

---

## Что делает `await`

Возьмём строку:

```python
rooms = await repository.load_rooms()
```

Полезная модель состоит из пяти шагов:

1. текущая корутина вызывает `load_rooms()` и получает awaitable;
2. `await` начинает или продолжает его вычисление;
3. если результат уже готов, выполнение может продолжиться сразу;
4. если нужно ждать неблокирующее I/O, таймер или другую task, текущая
   корутина сохраняет состояние и возвращает управление event loop;
5. когда ожидаемое событие готово, loop снова ставит задачу в очередь и
   позднее продолжает её после `await`.

```text
Task A исполняется
      │
      ▼
await socket_read()
      │ данных пока нет
      ▼
состояние A сохранено ──► event loop ──► запускает готовую Task B
      ▲
      │ сокет A стал готов
      └──────── loop ставит A в ready queue
```

Ключевая оговорка: не каждое написанное `await` обязательно переключает
задачу. Если awaitable уже завершён, результат можно получить немедленно.
Поэтому `await` означает **разрешённую точку приостановки**, а фактическое
переключение зависит от состояния ожидаемой операции.

И наоборот, `async def` не делает синхронную работу неблокирующей. Если
внутри корутины вызвать функцию, которая на секунду заняла поток и не
отдала управление loop, остальные задачи этого loop тоже ждут.

---

## Как loop узнаёт о сокетах

Для сетевого I/O сокет переводят в неблокирующий режим. Попытка чтения не
держит поток до байтов, а сообщает: «сейчас данных нет». Event loop
регистрирует интерес к готовности этого FD у механизма ОС (`epoll`,
`kqueue`, `select` — конкретный выбор зависит от платформы и реализации).

Упрощённо одна итерация loop выглядит так:

```text
1. взять ready Task A
2. исполнять A, пока она не завершится или не приостановится
3. взять ready Task B
4. если ready queue пуста — спросить ОС, какие FD/таймеры готовы
5. разбудить связанные задачи и повторить
```

```text
ready queue:     [Task B, Task C]
waiting on FD:   FD 4 → Task A
timers:          10:00:00.200 → Task D

ОС сообщает «FD 4 можно читать»
                   ↓
ready queue: [Task B, Task C, Task A]
```

Loop не проверяет каждый сокет в бесконечном Python-цикле. Он просит ОС
уведомить о готовности и спит, если готовой работы нет. Это позволяет одному
потоку держать много ожидающих соединений без отдельного стека OS thread на
каждое.

## Структурная картина: родитель знает своих детей

Для двух независимых проверок можно использовать `asyncio.gather`:

```python
import asyncio


async def check_room(room_id: str, delay: float) -> str:
    print(f"start {room_id}")
    await asyncio.sleep(delay)
    print(f"ready {room_id}")
    return room_id


async def main() -> None:
    rooms = await asyncio.gather(
        check_room("Atlas", 0.2),
        check_room("Bay", 0.1),
    )
    print(rooms)


asyncio.run(main())
```

Обе корутины становятся работой loop, а `main` ждёт их общее завершение.
`Bay` закончит ожидание раньше, но `gather` вернёт результаты в порядке
переданных аргументов:

```text
start Atlas
start Bay
ready Bay
ready Atlas
['Atlas', 'Bay']
```

Смысл структуры здесь не в конкретной функции `gather`, а во владении:
`main` создал дочерние работы и не завершился, пока не собрал результаты.
В Python 3.11+ `asyncio.TaskGroup` делает такую группу и обработку сбоев ещё
явнее. Для практики, совместимой с Python 3.10, достаточно `gather`; модель
остаётся той же — у фоновой задачи должен быть владелец.

---

## Разобранный сухой прогон двух задач

Прогоним пример выше. Время условное; важен порядок состояний.

| Момент | Готовые задачи | Что исполняется | Ожидают |
|--------|----------------|-----------------|---------|
| `t=0` | `main` | `main` входит в `gather` | — |
| `t≈0` | `Atlas`, `Bay` | `Atlas` печатает start и доходит до sleep | Atlas: таймер 0.2 |
| `t≈0` | `Bay` | `Bay` печатает start и доходит до sleep | Atlas 0.2, Bay 0.1 |
| `t=0.1` | `Bay` | `Bay` печатает ready и возвращает строку | Atlas 0.2 |
| `t=0.2` | `Atlas` | `Atlas` печатает ready и возвращает строку | — |
| `t≈0.2` | `main` | `gather` отдаёт оба результата | — |

`asyncio.sleep` не ускорил таймеры. Два ожидания просто шли одновременно по
часам, пока поток был свободен. Если вместо `await asyncio.sleep(...)`
написать длинный цикл без `await`, первая задача займёт поток до конца и
вторая не начнёт работу.

## Async не отменяет гонки

В одном event-loop thread нет вытеснения в произвольной строке Python-кода,
поэтому рассуждать о переключениях легче. Но логическая гонка всё равно
возможна, если инвариант пересекает `await`:

```python
async def reserve(room_id: str) -> bool:
    if await is_room_free(room_id):
        await save_booking(room_id)
        return True
    return False
```

Task A и Task B могут обе завершить первую проверку со значением «свободно»,
а затем обе сохранить бронь. `await` явно показывает места, где другая
task способна продвинуться, но не превращает две операции хранилища в одну
транзакцию.

Правило из главы о потоках сохраняется: конкурентная модель меняет места
переключений, но бизнес-инвариант всё равно надо защищать на правильной
границе.

## Harbor и интервью

- Один event loop может держать много соединений, если сетевые библиотеки
  умеют неблокирующий I/O.
- Корутина обработчика — не OS thread; её локальное состояние сохраняется
  между приостановками.
- Task регистрирует корутину как независимо продвигаемую работу loop.
- `await` полезен там, где операция способна ждать, а не как украшение
  каждой функции.
- Async-репозиторий и async HTTP-клиент нужны не ради одинакового
  синтаксиса, а чтобы ожидание не занимало thread loop.
- Общая память задач остаётся общей; инвариант брони не защищается одним
  event loop.

## Частые ошибки

- Вызвать `async def` и решить, что тело уже выполнилось.
- Путать coroutine object с Task.
- Считать, что `await` создаёт параллельный поток.
- Создать task и потерять ссылку, результат и исключение.
- Вставить `await` перед каждой строкой, не понимая, какой awaitable ждём.
- Держать CPU-цикл между точками `await` и удивляться остановке всех задач.
- Считать однопоточный loop защитой от гонок через несколько `await`.

## Мини-голос

> Вызов `async def` создаёт coroutine object, но ещё не исполняет тело.
> Task регистрирует корутину в event loop и хранит её состояние и результат.
> `await` продолжает awaitable, а при реальном ожидании сохраняет текущую
> корутину и возвращает управление loop.
> Loop запускает готовые задачи и просит ОС сообщать о готовности сокетов.
> Это конкурентность I/O в одном потоке, а не магический параллелизм CPU.
