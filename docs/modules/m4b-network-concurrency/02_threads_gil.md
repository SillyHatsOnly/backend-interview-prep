# 02 · Потоки и GIL

**Мост:** в [прошлой главе](./01_socket_tcp_http.md) listener принял
соединение, а `recv()` на connected socket мог заблокировать текущий поток
до прихода байтов. Если сервер исполняет только одну последовательность
инструкций, медленный клиент задержит остальных. Здесь дадим одному процессу
несколько OS-потоков. В следующей главе решим ту же задачу иначе: много
async-задач будут по очереди работать в одном потоке.

**Вопрос сюжета:** что именно разделяют потоки процесса и почему GIL
позволяет им помогать при I/O, но не делает общую память безопасной?

### С собесов

Типовые вопросы: «Процесс или поток?», «Что такое GIL?», «Могут ли Python
threads работать одновременно?», «Когда потоки полезны?» и «Если есть GIL,
откуда гонки?». Слабый ответ звучит как «GIL запрещает многопоточность».
Точный ответ называет реализацию Python, различает Python-код и ожидание I/O,
а затем отдельно разбирает общие изменяемые данные.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| процесс | process | Контейнер исполнения с собственным виртуальным адресным пространством и ресурсами ОС |
| поток ОС | OS thread | Исполняемая последовательность внутри процесса; планировщик ОС может запускать разные потоки |
| Python-поток | Python thread | Объект `threading.Thread`, который в обычном CPython опирается на нативный поток ОС |
| планировщик | scheduler | Часть ОС, которая решает, какой готовый поток получает CPU |
| GIL | Global Interpreter Lock | Блокировка интерпретатора в стандартном CPython: Python-код в одном интерпретаторе исполняет один поток за раз |
| гонка | race condition | Результат зависит от того, как непредсказуемо чередовались конкурирующие действия |
| критическая секция | critical section | Участок, где общий инвариант надо проверить и изменить как одну защищённую операцию |
| переключение контекста | context switch | Сохранить состояние одного потока и продолжить другой |
| I/O-bound | I/O-bound | Большая часть времени уходит на ожидание сети, диска или другого сервиса |
| CPU-bound | CPU-bound | Большая часть времени уходит на вычисления процессора |

## Процесс хранит ресурсы, поток исполняет код

У процесса Harbor есть виртуальная память, таблица FD и другие ресурсы.
Потоки внутри него разделяют эти ресурсы. Поэтому любой поток может в
принципе обратиться к соединённому сокету процесса или к одному объекту
Python в куче.

У каждого потока при этом своё исполняемое состояние: стек вызовов, набор
регистров и место, с которого продолжать инструкции. Если два обработчика
зашли в разные функции, их локальные вызовы не складываются в один общий
стек.

```text
процесс Harbor
┌──────────────────────────────────────────────────────────┐
│ общие: Python heap, модули, конфигурация, таблица FD     │
│                                                          │
│  thread A             thread B             thread C      │
│  ┌──────────┐         ┌──────────┐         ┌──────────┐  │
│  │ свой стек│         │ свой стек│         │ свой стек│  │
│  │ регистры │         │ регистры │         │ регистры │  │
│  │ recv FD4 │         │ Python   │         │ recv FD5 │  │
│  └──────────┘         └──────────┘         └──────────┘  │
└──────────────────────────────────────────────────────────┘
             ▲                  ▲
             └──── scheduler ───┘
```

Разделение памяти делает обмен дешёвым: не нужно сериализовать каталог
комнат для каждого потока. Та же особенность создаёт риск: два потока могут
прочитать и изменить один словарь бронирований в неудачном порядке.

У разных процессов картина обратная. По умолчанию у них разные адресные
пространства, поэтому случайно изменить один Python-список из двух процессов
нельзя. Зато обмен требует межпроцессного механизма: сокета, pipe, очереди,
разделяемой памяти или внешней базы. Новый процесс также обычно тяжелее
нового потока по памяти и запуску.

| Свойство | Процессы | Потоки одного процесса |
|----------|----------|-------------------------|
| Адресное пространство | Раздельное | Общее |
| Python-объекты в куче | Не общие автоматически | Общие по ссылке |
| Таблица FD | У каждого процесса своя, с возможным наследованием | Разделяется внутри процесса |
| Стек исполнения | Свой у процесса/главного потока | Свой у каждого потока |
| Сбой и изоляция | Сбой одного worker обычно не завершает другой | Авария всего процесса завершает все его потоки |
| Обмен данными | Нужен IPC/внешнее хранилище | Возможен напрямую, но нужны правила синхронизации |

Таблица не выбирает победителя. Процесс полезен для изоляции и настоящего
параллелизма CPU-работы; поток удобен для нескольких I/O-ожиданий с общей
памятью. Цена выбирается под задачу.

## Что делает GIL в обычном CPython

Курс рассматривает стандартные сборки CPython 3.10–3.13. В них поток должен
владеть GIL, чтобы исполнять Python bytecode и работать с внутренним
состоянием объектов интерпретатора. Поэтому два потока одного интерпретатора
обычно не исполняют чистый Python-код параллельно на двух ядрах.

```text
момент времени ───────────────────────────────────────────►

thread A: [Python + GIL] [ожидает socket]      [Python + GIL]
thread B:               [Python + GIL] [wait]              ...
CPU:      считает A      считает B
```

Когда thread A входит в блокирующую сетевую операцию стандартной библиотеки,
CPython освобождает GIL на время ожидания ядра. Thread B может получить GIL
и исполнять Python-код. Именно поэтому потоки способны повысить пропускную
способность I/O-bound сервиса: пока один запрос ждёт сеть, другой продвигает
свою работу.

Для чистого CPU-bound цикла ситуация иная:

```text
thread A: [Python][ждёт GIL][Python][ждёт GIL]...
thread B: [ждёт GIL][Python][ждёт GIL][Python]...
```

Оба потока делят право исполнять Python-код, а не складывают мощность ядер.
К вычислению добавляются переключения и координация, поэтому два потока
могут оказаться даже медленнее одного. Для независимой тяжёлой CPU-работы
обычно рассматривают несколько процессов, нативный код, который осознанно
освобождает GIL, или другую архитектуру.

### Граница формулировки

GIL — особенность реализации CPython, а не закон языка Python. Некоторые
нативные расширения освобождают его вокруг долгой работы. В Python 3.13
также существует отдельная экспериментальная free-threaded сборка без
обычного GIL; это не повод молча переносить её свойства на стандартную
сборку. На собеседовании сначала зафиксируйте: «говорю об обычном CPython».

## Чего GIL не делает

### Не превращает несколько действий в одну транзакцию

Бизнес-правило Harbor звучит так:

> Если комната свободна, создать ровно одну бронь на этот интервал.

Проверка свободы и создание брони — два логических действия. Между ними
планировщик может дать работу другому потоку, либо первый поток может
отпустить GIL на I/O. Наличие GIL не соединяет действия в неделимую
операцию.

### Не запрещает гонки

Результат гонки зависит не от физического одновременного исполнения каждой
машинной инструкции, а от опасного чередования. Даже один CPU способен
создать гонку, если потоки переключаются между «прочитал» и «записал».

### Не защищает внешние системы

Два потока, два процесса или два экземпляра сервиса могут одновременно
обратиться к Postgres. Локальная блокировка интерпретатора другого процесса
не видна. Инвариант брони в реальном сервисе потребует ограничения данных и
транзакционной модели, а не веры в GIL.

### Не обещает атомарность вашего выражения

Некоторые отдельные операции встроенных типов в конкретной версии CPython
выглядят неделимыми из-за реализации. Строить бизнес-корректность на
неформальном списке «эта операция вроде атомарна» опасно: составное
`проверить → изменить` всё равно не атомарно, а реализация и сборка могут
измениться. Защищать нужно инвариант целиком.

## Разобранный сухой прогон гонки

Рассмотрим учебную функцию с общей памятью:

```python
import time


booked_rooms: set[str] = set()


def reserve(room_id: str) -> bool:
    if room_id in booked_rooms:
        return False

    time.sleep(0.01)  # изображает ожидание внешней проверки
    booked_rooms.add(room_id)
    return True
```

Два потока почти одновременно вызывают `reserve("Atlas")`.

| Шаг | Thread A | Thread B | `booked_rooms` |
|-----|----------|----------|----------------|
| 1 | Проверяет `Atlas`: свободна | — | `{}` |
| 2 | Входит в `sleep`, освобождает GIL | Проверяет `Atlas`: тоже свободна | `{}` |
| 3 | Ещё ждёт | Входит в `sleep` | `{}` |
| 4 | Добавляет `Atlas`, возвращает `True` | Ещё ждёт | `{"Atlas"}` |
| 5 | — | Тоже добавляет `Atlas`, возвращает `True` | `{"Atlas"}` |

Множество в конце содержит один элемент, но оба клиента услышали «бронь
успешна». Ошибка находится не во внутреннем устройстве `set.add`, а в том,
что проверка и решение вернуть успех не были защищены как единое правило.

`time.sleep()` здесь специально делает окно гонки заметнее, но не является
её причиной. Реальный разрыв дадут запрос к базе, сетевой вызов или обычное
переключение между действиями.

Лок может сделать критическую секцию недоступной второму потоку до окончания
первого. На этом этапе достаточно понять границу: защищают не «строку
`add`», а проверку вместе с изменением. Глубокий набор примитивов и
deadlock-сценарии здесь не нужен. Для нескольких процессов и настоящего
Harbor лок в памяти одного процесса всё равно недостаточен — позже правило
должно жить рядом с данными.

## Когда потоки помогают

Представим два запроса:

- A ждёт 200 мс ответ внутреннего каталога;
- B ждёт 200 мс другой сетевой ответ;
- собственная Python-обработка каждого занимает 5 мс.

Один поток выполняет их примерно так:

```text
A: CPU 5 ── wait 200 ── CPU 5
B:                              CPU 5 ── wait 200 ── CPU 5
```

Два потока могут перекрыть ожидания:

```text
thread A: CPU 5 ── wait 200 ── CPU 5
thread B:    CPU 5 ── wait 200 ── CPU 5
```

Сетевой сервис не заставил удалённые ответы прийти быстрее. Он просто не
оставил процесс полностью без дела во время первого ожидания. Итоговая
пропускная способность может вырасти, хотя задержка отдельного внешнего
вызова осталась прежней.

Потоки подходят, когда:

- библиотека блокирующая, но освобождает GIL на I/O;
- одновременно ожидается умеренное число операций;
- общую память можно держать простой и контролируемой;
- модель с потоком на работу понятнее и достаточна.

Цена потоков:

- стек и служебные данные на каждый поток;
- переключения контекста;
- сложные для воспроизведения гонки;
- необходимость ограничивать число потоков, а не создавать бесконечно;
- CPU-bound Python-код не получает автоматического параллельного ускорения.

## Упражнение в главе

1. Нарисуйте один процесс Harbor с двумя потоками. Поместите общий словарь
   комнат и FD listener в общую часть, а два стека вызовов — в отдельные.
   Объясните, почему кадр вызова относится к исполняющему его потоку, но
   Python-объект, на который ссылается локальное имя, может быть общим.
2. Выполните другой порядок сухого прогона `reserve`: thread A успевает
   добавить комнату до первой проверки thread B. Какие значения вернутся?
   Почему наличие одного правильного расписания не делает функцию
   потокобезопасной?
3. Разложите четыре задачи на I/O-bound и CPU-bound: ждать `recv()`,
   считать хеши большого массива чистым Python, ждать HTTP-ответ, сортировать
   огромный Python-список. Для каждой скажите, помогут ли обычные потоки
   CPython и почему.

Не ищите «идеальное число потоков» по формуле. Здесь проверяется модель
ожидания и общей памяти.

## Harbor и интервью

- Поток, заблокированный на одном socket FD, не обязан останавливать другие
  потоки того же процесса.
- Потоки разделяют каталог и кэши, поэтому изменения требуют явного
  контракта синхронизации.
- GIL объясняет ограничение чистого Python CPU-кода, но I/O-библиотеки
  обычно освобождают его во время ожидания.
- Несколько процессов сервера дают изоляцию и используют несколько ядер,
  но память между ними уже не общая автоматически.
- Временный in-memory набор броней годится для упражнения, не для
  инварианта продового Harbor с несколькими воркерами.

## Частые ошибки

- Говорить «поток легче процесса» и не называть, что именно разделяется.
- Считать, что GIL делает код потокобезопасным.
- Ожидать ускорения чистого Python CPU-цикла от двух `threading.Thread`.
- Считать, что потоки бесполезны вообще из-за GIL, игнорируя I/O.
- Защищать одну запись, оставив проверку бизнес-правила снаружи.
- Создавать новый поток на каждый вход без ограничения и не учитывать
  память, переключения и внешние лимиты.

## Мини-голос

> Процесс владеет адресным пространством и ресурсами, а каждый поток имеет
> свой стек исполнения и разделяет память процесса.
> В стандартном CPython GIL допускает один поток с Python-кодом на
> интерпретатор, но освобождается вокруг обычного блокирующего I/O.
> Поэтому потоки помогают перекрывать сетевые ожидания, а не ускоряют
> чистый Python CPU-код.
> GIL не отменяет гонки: проверка и изменение общего инварианта могут
> чередоваться.
> Для настоящей брони защита должна учитывать все процессы и хранилище.
