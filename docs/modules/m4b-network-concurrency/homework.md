Если порт занят, можно заменить `8000` или `9000` на другой незанятый порт
выше `1024`, но одно и то же число должно быть у сервера и клиента.
Привязывайте учебный сервер к `127.0.0.1`.

## Задание 1. Один запрос целиком *(обязательно, рисунок + голос)*

Нарисуйте путь запроса:

```text
браузер открывает http://127.0.0.1:8000/rooms
```

На рисунке должны быть:

- клиентский процесс и серверный процесс Harbor;
- клиентский socket FD и временный клиентский порт;
- listening socket FD на `127.0.0.1:8000`;
- результат `accept()` как отдельный connected socket FD;
- TCP byte stream между окончаниями;
- HTTP/1.1 request line, пустая строка после заголовков и HTTP-ответ;
- обработчик в одном из вариантов: OS thread **или** async task;
- одно место блокирующего ожидания и одно место, где другой запрос может
  продвинуться;
- стрелка ответа обратно браузеру.

Номера FD и эфемерный порт придумайте сами и подпишите, что это пример, а
не фиксированные значения.

Затем проговорите рисунок 3–5 минут без чтения главы. Обязательно объясните:

1. чем FD отличается от объекта сокета;
2. почему listener не превращается в соединение первого клиента;
3. что TCP обещает и чего не обещает;
4. почему один `recv()` не равен одному HTTP-запросу;
5. где находится процесс, где thread и где async task;
6. почему async не означает «CPU стал быстрее».

**Сдать:** фото/ASCII-рисунок, план из 8–12 тезисов и длительность устного
прогона. Аудио не обязательно; для ревью важны рисунок и формулировки,
которые вы действительно произнесли.

## Задание 2. Локальный сетевой опыт *(обязательно, код)*

Выберите **один** маршрут. Наберите его заново, не копируя файл из
мини-практики.

### Маршрут A · HTTP

На `BaseHTTPRequestHandler` и `HTTPServer` сделайте сервер с тремя
вариантами:

```text
GET /rooms  → 200, application/json, список из двух комнат
GET /health → 200, text/plain, тело ok\n
другой путь → 404, text/plain
```

Сервер должен обработать ровно три запроса последовательно и завершиться.
До первого запроса напечатайте FD listening socket, а внутри обработчика —
FD принятого соединения. Для этого найдите и используйте публичный метод
`fileno()` соответствующих socket-объектов; не обращайтесь к внутренним
полям с подчёркиванием.

Проверьте тремя командами `curl -i`, по одной на каждый вариант. Порядок
запросов выберите сами и заранее запишите ожидаемые статусы и тела.

В отчёте ответьте:

- какой вызов блокирует единственный поток между запросами;
- почему FD соединения может переиспользоваться после закрытия;
- почему `Content-Length` считается по `bytes`, а не по числу видимых
  символов;
- сможет ли такой сервер обслужить второй запрос, пока первый обработчик
  спит.

### Маршрут B · TCP echo

На `socket` сделайте сервер, который последовательно принимает ровно двух
клиентов. Каждый клиент:

1. соединяется с `127.0.0.1:9000`;
2. отправляет одну короткую строку в UTF-8;
3. завершает направление записи через `shutdown(SHUT_WR)`;
4. читает ответ до EOF.

Сервер читает запрос циклом до EOF и отвечает `echo: ` плюс исходные байты.
Он печатает FD listener, FD каждого connected socket и адрес клиента.
Запустите клиентов с разными строками.

В отчёте ответьте:

- почему одного `recv(1024)` было бы недостаточно как общего правила;
- чем в этом учебном протоколе отмечен конец запроса;
- почему второй клиент ждёт, пока сервер занят первым;
- какое ограничение протокола создаёт `shutdown(SHUT_WR)`.

**Сдать для выбранного маршрута:** код, команды, существенный вывод и
четыре ответа. Не добавляйте потоки или asyncio: задача специально фиксирует
один blocking handler.

## Задание 3. Последовательно и конкурентно *(обязательно, код + прогон)*

Даны три учебных I/O-ожидания:

```python
jobs = [
    ("Atlas", 0.15),
    ("Bay", 0.05),
    ("Cedar", 0.10),
]
```

Напишите корутину `check_room(room_id, delay)`, которая:

1. печатает `start <id>`;
2. ждёт через `await asyncio.sleep(delay)`;
3. печатает `ready <id>`;
4. возвращает `room_id`.

Сделайте два запуска на одном наборе данных:

- **sequential** — три прямых `await` по очереди;
- **concurrent** — один `asyncio.gather` для трёх корутин.

Оба запуска должны печатать список результатов и время по `perf_counter`.
До выполнения письменно предскажите:

- порядок `start`;
- порядок `ready`;
- порядок элементов результата;
- к какой величине будет ближе общее время: сумме задержек или максимальной
  задержке.

Затем добавьте в корутину для одной выбранной комнаты
`time.sleep(0.08)` **до** `await asyncio.sleep`. Снова сделайте прогноз и
запуск. После наблюдения удалите блокирующую строку.

В отчёте объясните:

1. почему `gather` меняет полное время, но не длительность каждого таймера;
2. почему порядок завершения и порядок списка результатов могут различаться;
3. кого блокирует `time.sleep` внутри корутины;
4. почему этот опыт ничего не доказывает об ускорении CPU-bound функции.

**Сдать:** один файл с двумя режимами, прогнозы до запуска, фактический
вывод и объяснение расхождений. Точные сотые доли секунды не проверяются.

## Задание 4. Чужой async-код *(обязательно, ревью + голос)*

Не запускайте фрагмент и не переписывайте его сразу:

```python
import json
import time
from pathlib import Path
from urllib.request import urlopen


async def prepare_confirmation(repository, room_id: str) -> dict:
    room = await repository.get_room(room_id)

    time.sleep(0.10)
    template = Path("confirmation.txt").read_text(encoding="utf-8")

    with urlopen(
        f"https://weather.example/rooms/{room_id}",
        timeout=2,
    ) as response:
        weather = json.loads(response.read())

    score = sum(number * number for number in range(2_000_000))
    await repository.save_view(room_id)

    return {
        "room": room,
        "template": template,
        "weather": weather,
        "score": score,
    }
```

Оставьте комментарии к каждой существенной операции и отнесите её к одной
из категорий:

- async I/O-ожидание, которое может отдать loop;
- синхронное блокирующее I/O;
- CPU-работа в thread event loop;
- короткая синхронная работа, которую допустимо оставить на месте при
  малом входе.

После классификации:

1. назовите минимум три места, способных задержать другие tasks;
2. для каждого предложите **направление** исправления: async-библиотека,
   ограниченный перенос blocking I/O в поток, изменение архитектуры
   CPU-работы или аргумент «оставить и измерить»;
3. объясните, почему механическая замена `def` на `async def` ничего не
   исправила бы;
4. назовите, какие таймауты и лимиты вы захотели бы обсудить до production,
   не реализуя их сейчас.

Затем сделайте отдельный устный прогон на 2–3 минуты:

> процесс → OS thread → GIL → event loop → coroutine → task → await

В прогоне должны прозвучать:

- что разделяют потоки;
- что GIL делает и чего не делает;
- почему возможна гонка `проверить → await → записать`;
- чем конкурентность отличается от параллелизма;
- почему async помогает I/O, а не ускоряет чистый Python CPU-код.

**Сдать:** аннотированный фрагмент или комментарии с привязкой к строкам,
план устного ответа из 8–12 тезисов и длительность прогона. Готовый
переписанный production-вариант не требуется.

## Задание 5. Hard · два сообщения в одном TCP-соединении

Вернитесь после обязательных заданий. Измените echo-протокол так, чтобы один
клиент отправлял **два** сообщения в одном соединении, а сервер возвращал
два ответа. Завершение направления записи больше не может быть границей
первого сообщения.

Сначала письменно выберите framing:

- строка, завершённая `\n`, с запретом перевода строки внутри сообщения;
  или
- четырёхбайтовая длина перед телом.

Реализуйте чтение, которое выдерживает:

- заголовок/разделитель, разбитый между несколькими `recv`;
- два сообщения, склеенные в одном `recv`;
- преждевременный EOF посередине сообщения.

Не считайте, что локальная машина всегда возвращает удобные куски. В отчёте
сформулируйте инвариант буфера: какие байты уже образуют полное сообщение,
а какие должны остаться до следующего чтения.

## Когда пакет готов к ревью

- [ ] На одном рисунке есть socket → TCP → HTTP → process/thread/task.
- [ ] Listener и accepted connection показаны разными FD.
- [ ] TCP назван byte stream без границ сообщений.
- [ ] Устно различаются процесс, OS thread, coroutine и task.
- [ ] GIL не назван защитой от гонок и не выдан за запрет I/O-конкурентности.
- [ ] В async-прогоне объяснён порядок start/ready/result.
- [ ] В чужом коде найдены blocking I/O и CPU-работа внутри event loop.
- [ ] Есть фраза: «async перекрывает ожидания, но не делает CPU быстрее».
- [ ] Синхронный вариант Harbor признан допустимым при малой нагрузке и
      простой задаче.
- [ ] Все файлы набраны руками без проектного каркаса.
