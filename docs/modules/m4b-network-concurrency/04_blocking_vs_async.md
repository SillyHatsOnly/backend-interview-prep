# 04 · Blocking или async

**Мост:** [event loop](./03_asyncio_model.md) может продвигать другую task,
когда текущая корутина приостановилась на неблокирующем ожидании. Но слово
`async` в заголовке функции не меняет поведение вызовов внутри неё. Здесь
сравним один блокирующий обработчик с асинхронным и увидим, почему
`time.sleep()` или синхронный HTTP-клиент останавливает весь loop. Дальше
проверим модель руками на двух маленьких программах.

**Вопрос сюжета:** когда async действительно перекрывает ожидания Harbor,
а когда простой синхронный код честнее и безопаснее?

### С собесов

Спрашивают: «Чем sync отличается от async?», «Что будет, если вызвать
blocking I/O внутри `async def`?», «Почему `asyncio` не ускоряет CPU-bound
задачу?» и «Когда вы не стали бы выбирать async?». Проверяют не любовь к
одной модели, а способность назвать узкое место, цену и границу
переключения.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| блокирующий вызов | blocking call | Не возвращает управление вызывающему потоку, пока операция не завершится или не ошибётся |
| неблокирующий I/O | non-blocking I/O | Если операция сейчас не готова, поток не ждёт внутри вызова; готовность отслеживается отдельно |
| синхронный код | synchronous code | Следующий шаг функции начинается после завершения текущего вызова |
| асинхронный код | asynchronous code | Незавершённое ожидание представлено объектом; корутина может уступить поток и продолжиться позже |
| задержка | latency | Сколько времени проходит для одного запроса |
| пропускная способность | throughput | Сколько работ система завершает за интервал времени |
| конкурентность | concurrency | Несколько работ находятся в процессе и чередуются |
| параллелизм | parallelism | Вычисления физически идут одновременно |
| давление нагрузки | backpressure | Способ не принимать бесконечно больше работы, чем система и зависимости способны обработать |

Асинхронность описывает организацию ожиданий, а не «быстрый режим»
функции. Синхронный сервер с несколькими потоками тоже конкурентен.
Асинхронный loop в одном потоке обычно не параллелен.

---

## Один blocking handler

Начнём с понятного синхронного обработчика:

```python
def handle_rooms(request: Request) -> Response:
    rooms = catalog_client.load_rooms()  # блокирует поток на сетевом I/O
    body = encode_rooms(rooms)
    return Response(status=200, body=body)
```

Здесь `Request`, `Response` и клиент — условные имена, а не готовый каркас
Harbor. Важен порядок: пока `load_rooms()` ждёт удалённый каталог, этот
поток не может начать `encode_rooms` и не может обслужить второй запрос.

```text
один поток

request A: [call]──────────── ждёт catalog ────────────[encode][reply]
request B:                                                   [call]──...
время ───────────────────────────────────────────────────────────────►
```

Blocking не означает, что вся машина обязательно простаивает. ОС может
запустить другой процесс или поток. Синхронные серверы именно так и
обслуживают конкурентные запросы: несколько worker-процессов, пул потоков
или их комбинация. Блокируется конкретный поток, а не слово «Python» во
всей системе.

Цена модели появляется при большом числе одновременных медленных ожиданий:
нужны потоки или процессы, у каждого есть память и переключения, а размер
пула ограничен. Когда все worker'ы заняты ожиданием, новые запросы стоят в
очереди.

## Async handler

Асинхронный вариант требует **асинхронной зависимости**, которая умеет
отдать управление event loop:

```python
async def handle_rooms(request: Request) -> Response:
    rooms = await async_catalog_client.load_rooms()
    body = encode_rooms(rooms)
    return Response(status=200, body=body)
```

Если сетевой ответ ещё не готов, `await` приостанавливает task A. Event loop
может запустить task B в том же OS-потоке.

```text
один event-loop thread

Task A: [call]── await catalog A ........................ [encode][reply]
Task B:        [call]── await catalog B ........ [encode][reply]
CPU:    A      B                                B        A
время ───────────────────────────────────────────────────────────────►
```

Точки означают время, когда соответствующая task существует, но не держит
CPU. Удалённый каталог не отвечает быстрее из-за `await`; задержка одного
вызова остаётся примерно прежней. Выигрыш в том, что один поток не простаивает
вместе с каждым соединением и способен продвигать другие запросы.

Если одновременно пришёл только один запрос, а дополнительной работы нет,
async часто ничего не выигрывает по времени. Более того, появляется новая
модель ошибок, отмены и владения задачами. Выбирать её стоит за конкретную
конкурентность I/O, а не за современный синтаксис.

## Два ожидания: что именно стало быстрее

Синхронная версия:

```python
import time


def wait_catalog(room_id: str) -> str:
    time.sleep(0.2)
    return room_id


rooms = [wait_catalog("Atlas"), wait_catalog("Bay")]
print(rooms)
```

Ожидания идут одно после другого, поэтому весь фрагмент занимает около
`0.4` секунды:

```text
Atlas: [wait 0.2]
Bay:              [wait 0.2]
```

Асинхронная версия:

```python
import asyncio


async def wait_catalog(room_id: str) -> str:
    await asyncio.sleep(0.2)
    return room_id


async def main() -> None:
    rooms = await asyncio.gather(
        wait_catalog("Atlas"),
        wait_catalog("Bay"),
    )
    print(rooms)


asyncio.run(main())
```

Два таймера перекрываются, поэтому общее время близко к `0.2` секунды:

```text
Atlas: [wait 0.2]
Bay:   [wait 0.2]
```

Это демонстрация организации ожидания, а не измерение производительности
реального сервиса. `asyncio.sleep` почти не расходует CPU. Если заменить
его на две функции, каждая из которых 0.2 секунды считает Python-цикл без
`await`, один loop выполнит их последовательно примерно за 0.4 секунды.
Добавление `async def` вокруг вычисления не создаст второе ядро.

## Главная ловушка: blocking call внутри `async def`

Плохой обработчик:

```python
import time


async def handle_booking(request: BookingRequest) -> Response:
    time.sleep(1)  # блокирует OS thread event loop
    return Response(status=201)
```

Корутина не дошла до awaitable. `time.sleep` удерживает текущий thread одну
секунду. Поскольку в нём работает event loop, за эту секунду loop не может:

- продолжить другую task, чей сокет уже готов;
- запустить таймер;
- принять результат асинхронной зависимости;
- вовремя обработать отмену.

```text
event-loop thread

Task A: [ time.sleep(1) -------------------------------- ]
Task B:       ready, но не исполняется .................. [run]
Task C:          timer истёк, но callback ждёт .......... [run]
```

Для искусственной задержки корректен `await asyncio.sleep(1)`: он ставит
таймер и отдаёт управление loop. Для настоящего сетевого запроса нужен
клиент с async API. Простая замена `time.sleep` на `asyncio.sleep` не чинит
синхронный драйвер базы или синхронный HTTP-клиент — у каждой зависимости
должен быть способ неблокирующего ожидания.

## Частые источники блокировки

### Синхронная сеть и база данных

`urllib.request.urlopen`, `requests.get`, синхронный драйвер БД и обычный
`socket.recv()` ждут в вызывающем потоке. В синхронном обработчике это
нормально. В thread event loop такой вызов останавливает все его задачи.

Лучший долгосрочный вариант — библиотека с честным async API, если весь
стек действительно выбран асинхронным. Для ограниченного legacy-вызова
можно использовать `await asyncio.to_thread(sync_function, ...)`: loop
передаёт блокирующую функцию в пул потоков и ждёт её как awaitable.

`to_thread` — мост, а не превращение библиотеки в неблокирующую. Поток всё
равно существует и блокируется; пул конечен; отмена ожидающей корутины не
обязана физически остановить уже запущенную функцию. Для чистого
Python CPU-bound вычисления остаётся ограничение GIL.

### Файлы и подпроцессы

Обычные `open().read()`, `write()` и `subprocess.run()` синхронны. Маленькое
чтение конфигурации при старте может быть приемлемо. Большой файл или
долгий подпроцесс на пути каждого запроса способен заметно заморозить loop.
Важно оценивать длительность и место вызова, а не запрещать каждую
синхронную строку догматически.

### CPU-работа

Большой цикл, тяжёлое кодирование, сжатие или проверка пароля могут не ждать
I/O, но занимать thread loop. Здесь async-клиент не поможет: работу надо
уменьшить, ограничить, вынести в процесс/воркер или использовать
подходящую реализацию. Какой вариант выбрать, зависит от задачи и
библиотеки.

## Async-код тоже можно сделать последовательным

Этот код корректен, но ждёт комнаты по одной:

```python
rooms = []
for room_id in room_ids:
    room = await load_room(room_id)
    rooms.append(room)
```

Если запросы независимы, группа задач может перекрыть ожидания. Но
безграничный `gather` на десятки тысяч элементов способен одновременно
открыть столько же соединений и перегрузить Harbor, базу или чужой сервис.

```text
слишком мало конкурентности:  A wait → B wait → C wait
разумный предел:              [A B C D] → следующая группа
без предела:                  100 000 запросов → лимиты/память/каскад ошибок
```

Конкурентность — ресурс, который ограничивают. На этом этапе достаточно
помнить принцип: не заменяйте последовательный цикл на огромный `gather`
без ответа на вопросы «сколько одновременно?» и «что выдержит зависимость?».
Пулы, семафоры, таймауты и отмена требуют отдельной практики; они не нужны,
чтобы понять базовую модель.

## Когда sync — хороший выбор для Harbor

На учебном этапе синхронная версия честнее, если:

- вы отрабатываете доменную функцию выбора комнаты, а не сетевую
  конкурентность;
- запросов мало и измеренной проблемы ожиданий нет;
- зависимости синхронные, а async-обёртки только маскируют потоки;
- простота отладки сейчас важнее высокой конкурентности;
- CPU-работа доминирует и event loop не решает узкое место.

Async становится обоснованным, когда Harbor одновременно держит много
сетевых ожиданий, а весь горячий путь — сервер, HTTP-клиент, драйвер БД —
умеет неблокирующий I/O. Даже тогда нужны лимиты, таймауты и наблюдение за
задержкой; `async` не заменяет проектирование нагрузки.

```text
Есть много одновременного ожидания I/O?
          │
       нет├────────► начни с sync; измерь
          │да
          ▼
Все ключевые зависимости имеют async API?
          │
       нет├────────► sync workers/threads или ограниченный bridge
          │да
          ▼
Готовы владеть task, timeout, cancellation и лимитами?
          │
       нет├────────► sync может быть безопаснее сейчас
          │да
          ▼
        async — обоснованный кандидат, не автоматический победитель
```

## Разобранный сухой прогон

В одном event loop запущены две задачи:

```python
async def task_a() -> None:
    print("A start")
    time.sleep(0.2)
    print("A end")


async def task_b() -> None:
    print("B start")
    await asyncio.sleep(0.05)
    print("B end")
```

Обе переданы в `gather` в порядке A, B.

1. Task A печатает `A start`.
2. Она вызывает `time.sleep(0.2)`. Thread loop блокируется; task B ещё не
   может напечатать даже `B start`.
3. Через 0.2 секунды A печатает `A end` и завершается.
4. Loop запускает B: она печатает `B start` и приостанавливается на
   `asyncio.sleep(0.05)`.
5. Через 0.05 секунды B печатает `B end`.

Ожидаемый порядок:

```text
A start
A end
B start
B end
```

Наличие `gather` не спасло программу: первая task не отдала управление.
Если заменить `time.sleep(0.2)` на `await asyncio.sleep(0.2)`, B начнёт до
окончания A и завершится первой.

## Упражнение в главе

1. Перерисуйте сухой прогон после замены `time.sleep` на
   `await asyncio.sleep`. Укажите состояния обеих tasks в моменты 0, 0.05
   и 0.2 секунды.
2. Для каждого вызова скажите, что блокируется и чем можно обосновать
   выбор: маленький `json.dumps`, `requests.get`, `await async_client.get`,
   тяжёлый Python-цикл, `await asyncio.sleep`.
3. Harbor получает один запрос в минуту и читает данные из простого
   синхронного репозитория. Дайте аргумент **за sync**. Затем измените
   условие на 5 000 одновременно открытых I/O-ожиданий и дайте аргумент
   **за исследование async**. Не называйте победителя без условий.
4. Объясните, почему `asyncio.to_thread` освобождает event loop, но не
   устраняет поток и не обещает ускорить чистый Python CPU-код.

## Harbor и интервью

- Sync handler блокирует свой worker/thread; другие worker'ы всё ещё могут
  работать.
- Async handler масштабирует ожидания только с неблокирующими
  зависимостями.
- Один `time.sleep`, синхронный HTTP-запрос или долгий CPU-цикл внутри
  `async def` задерживает все tasks данного loop.
- `gather` перекрывает независимые ожидания, но не должен создавать
  неограниченную нагрузку.
- В маленьком Harbor sync — нормальный осознанный старт, а не «устаревший
  код».
- Выбор подтверждают профилем нагрузки и измерением, а не наличием слова
  `async` в вакансии.

## Частые ошибки

- Считать async синонимом «быстрее».
- Смешать async handler с синхронным клиентом и не заметить блокировку loop.
- Пытаться исправить CPU-bound код дополнительными `await`.
- Последовательно `await`-ить независимые операции и ожидать
  конкурентности.
- Запустить неограниченный `gather` и перенести очередь в чужой сервис.
- Переписать простой учебный домен на async до появления сетевой задачи.
- Считать `to_thread` бесплатным и бесконечным.

## Мини-голос

> Blocking call удерживает текущий OS thread до результата.
> В sync-сервере конкурентность дают worker-процессы или потоки.
> В async-сервере `await` неблокирующего I/O отдаёт event loop другой task.
> Синхронный вызов внутри `async def` блокирует thread loop и все его tasks.
> Async перекрывает ожидания, но не ускоряет CPU и не заменяет лимиты.
> Для маленького Harbor простой sync-код может быть лучшим текущим выбором.
