# 01 · Socket → TCP → HTTP

**Мост:** M4a показал, что процесс обращается к файлам и другим объектам
ядра через файловые дескрипторы, а блокирующий вызов может остановить
текущий поток. Теперь Harbor должен получить запрос не из локального файла,
а из браузера. Для процесса это не совершенно новый мир: сетевое окончание
тоже будет объектом ядра с FD. В следующей главе посмотрим, что делать
процессу, пока один такой FD ждёт байты.

**Вопрос сюжета:** как строка `GET /rooms` проходит от браузера до
обработчика Harbor и почему на этом пути нужны сразу сокет, TCP, порт и
HTTP?

### С собесов

Часто спрашивают: «Что такое сокет?», «Чем TCP отличается от HTTP?»,
«Зачем нужен порт?», «TCP передаёт сообщения или поток?», «Что делает
`accept()`?» и «Что происходит после ввода URL?». Сильный ответ не
перечисляет уровни отдельно, а проводит один запрос через них. Типичная
ошибка — сказать, что один `send()` на клиенте соответствует одному
`recv()` на сервере. TCP такого соответствия не обещает.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| сокет | socket | Объект ядра — сетевое окончание; процесс получает к нему доступ через FD |
| файловый дескриптор | file descriptor, FD | Небольшой номер в процессе, по которому системный вызов находит открытый объект ядра |
| IP-адрес | IP address | Адрес сетевого интерфейса узла; помогает доставить пакет до нужной машины |
| порт | port | Число 0–65535, которое вместе с адресом указывает сетевое окончание приложения |
| клиент | client | Сторона, которая начинает соединение или запрос |
| сервер | server | Сторона, которая ждёт соединения на известном адресе и порту |
| слушающий сокет | listening socket | Сокет сервера, который принимает новые TCP-соединения |
| соединённый сокет | connected socket | Окончание одного конкретного TCP-соединения |
| TCP | Transmission Control Protocol | Транспорт, который показывает приложению надёжный упорядоченный поток байтов |
| поток байтов | byte stream | Последовательность без встроенных границ «один вызов — одно сообщение» |
| HTTP | Hypertext Transfer Protocol | Прикладной протокол: правила формы и смысла запроса и ответа |

Слово «поток» здесь встречается в двух разных смыслах. **TCP byte stream** —
последовательность байтов в сети. **OS thread** из следующей главы — поток
исполнения инструкций. По-русски слова совпадают, объекты — нет.

## Одна картина: браузер спрашивает Harbor

Для первого прогона всё работает на одной машине. Браузер обращается к
`http://127.0.0.1:8000/rooms`, где `127.0.0.1` означает локальный узел, а
`8000` — порт учебного сервера.

```text
клиентский процесс: браузер                 серверный процесс: Harbor
┌──────────────────────────┐               ┌─────────────────────────────┐
│ HTTP: GET /rooms         │               │ listening socket, FD 3      │
│            │             │               │ 127.0.0.1:8000              │
│            ▼             │               │             │ accept()      │
│ socket, FD 17            │               │             ▼               │
│ 127.0.0.1:53124          │               │ connected socket, FD 4     │
└────────────┬─────────────┘               │ 127.0.0.1:8000             │
             │                              └──────────────┬──────────────┘
             │      TCP: упорядоченные байты               │
             └─────────────────────────────────────────────┘

соединение различают четыре значения:
127.0.0.1:53124  →  127.0.0.1:8000
 client IP:port      server IP:port
```

Браузер строит HTTP-запрос, но не «посылает объект HTTP» ядру. Он кодирует
запрос в байты и записывает их в сокет. TCP отвечает за транспорт этих
байтов. На сервере ядро складывает пришедшие байты в буфер соединённого
сокета, а процесс читает их через `recv()` или более высокоуровневую
библиотеку.

Уровни решают разные задачи:

```text
HTTP   — что означают байты: метод, путь, заголовки, тело, статус
TCP    — как дать приложению упорядоченный надёжный поток байтов
IP     — к какому сетевому узлу доставлять пакеты
socket — через какой объект процесс читает и пишет этот сетевой поток
FD     — каким номером процесс называет сокет в системных вызовах
```

Если назвать TCP «форматом запроса», мы потеряем методы и статусы HTTP. Если
назвать HTTP «доставкой пакетов», не сможем объяснить потерю, повторную
передачу и порядок байтов. Слои связаны, но не взаимозаменяемы.

## Сокет и FD: близкие, но не одинаковые слова

В разговоре часто говорят «сокет — это файловый дескриптор». Для рабочего
объяснения полезно быть точнее:

1. системный вызов `socket()` создаёт объект сокета в ядре;
2. процесс получает число, например `3`;
3. число `3` — FD, запись в таблице открытых дескрипторов процесса;
4. операции `bind`, `listen`, `accept`, `recv` и `send` через этот FD
   обращаются к объекту сокета.

```text
процесс Harbor

таблица FD                    объекты ядра
┌───────────┐                 ┌──────────────────────────┐
│ 0 stdin   │ ──────────────► │ терминал                 │
│ 1 stdout  │ ──────────────► │ терминал                 │
│ 3 socket  │ ──────────────► │ TCP listener :8000      │
│ 4 socket  │ ──────────────► │ TCP connection с :53124 │
└───────────┘                 └──────────────────────────┘
```

FD имеет смысл только внутри процесса. Число `4` у браузера и число `4` у
Harbor могут указывать на совершенно разные объекты. Поэтому в логах
недостаточно сказать «сломался FD 4»: нужен процесс и контекст соединения.

Сходство сокета с файлом полезно, потому что оба объекта можно читать,
писать и закрывать через общий механизм дескрипторов. Но сокет не является
обычным файлом на диске. У него есть сетевое состояние, локальный и
удалённый адреса, входной и выходной буферы, а ошибки зависят от другой
стороны соединения.

### Слушающий сокет не переносит каждый запрос сам

Сервер сначала создаёт отдельное место встречи:

```text
socket() → bind(127.0.0.1:8000) → listen() → accept()
```

`bind()` связывает сокет с локальным адресом и портом. `listen()` переводит
его в режим ожидания входящих соединений. `accept()` забирает одно готовое
соединение и возвращает **новый** FD соединённого сокета.

```text
FD 3: listener :8000
  ├── accept() → FD 4: connection с клиентом :53124
  ├── accept() → FD 5: connection с клиентом :53125
  └── продолжает слушать новые соединения
```

Если бы `accept()` превращал единственный listener в соединение с первым
клиентом, сервер перестал бы принимать остальных. Разделение позволяет
оставить FD 3 «дверью здания», а FD 4 и FD 5 — отдельными разговорами с
посетителями.

На клиенте последовательность короче:

```text
socket() → connect(127.0.0.1:8000) → send()/recv() → close()
```

Это пока схема системных действий, а не задание написать сервер с нуля.
Маленький живой пример будет в [практике](./05_mini_practice.md).

## Адрес, порт и роли

IP-адрес отвечает на вопрос «к какому сетевому узлу идти», а порт —
«какое сетевое окончание на этом узле нужно». Один компьютер может
одновременно обслуживать SSH, базу данных и Harbor, потому что процессы
слушают разные порты.

Сервер обычно выбирает заранее известный локальный порт, например `8000`.
Клиенту тоже нужен локальный порт, но для исходящего соединения его обычно
временно назначает ОС. Поэтому на схеме браузер получил `53124`. Такой порт
называют эфемерным (ephemeral): он нужен, чтобы ядро вернуло ответ именно
этому соединению, но пользователь обычно его не выбирает.

TCP-соединение различают по четвёрке:

```text
(source IP, source port, destination IP, destination port)
```

Два браузера могут одновременно подключиться к `127.0.0.1:8000`: их
клиентские порты различаются, поэтому соединения не смешиваются. Более
точно ядро учитывает ещё транспортный протокол: TCP-порт `8000` и UDP-порт
`8000` относятся к разным пространствам.

Клиент и сервер — роли в установлении общения, а не направления данных.
Клиент начинает соединение, сервер его принимает; после этого оба окончания
могут и отправлять, и получать байты. Сервер Harbor посылает HTTP-ответ
назад, но не становится из-за этого клиентом.

Для адреса с именем, например `harbor.example`, перед соединением обычно
нужно получить IP через DNS. В локальном примере используется готовый
адрес `127.0.0.1`, поэтому этот дополнительный шаг не скрывает основную
цепочку.

## Что обещает TCP

TCP показывает приложению **надёжный упорядоченный поток байтов** между
двумя окончаниями установленного соединения.

**Надёжный** означает: TCP обнаруживает потерю или повреждение сегментов и
пытается передать данные повторно. Приложение либо читает доставленные
байты, либо в итоге получает разрыв/ошибку; оно не должно само собирать
пакеты по номерам для обычного потока.

**Упорядоченный** означает: если отправитель записал сначала `ABC`, потом
`DEF`, приложение-получатель увидит `ABCDEF` в таком порядке. Отдельные
сетевые пакеты могли прийти иначе, но TCP скрывает переупорядочивание до
чтения приложением.

**Поток байтов** означает: границы вызовов не сохраняются. Рассмотрим
отправителя:

```text
send(b"GET /")
send(b"rooms HTTP/1.1\r\n")
```

Получатель имеет право увидеть, например:

```text
recv(...) → b"GET /rooms HT"
recv(...) → b"TP/1.1\r\n"
```

или всё одной порцией:

```text
recv(...) → b"GET /rooms HTTP/1.1\r\n"
```

Это не поломка TCP. Два `send()` могли склеиться, а один большой `send()`
мог разбиться на несколько чтений. Поэтому прикладной протокол обязан сам
задавать границы: разделитель строк, длину тела, специальный формат кадра
или закрытие направления записи.

TCP также не обещает:

- что удалённое приложение **обработало** запрос, только потому что локальный
  `send()` завершился;
- что бизнес-операция выполнится ровно один раз;
- что соединение никогда не оборвётся;
- что задержка будет маленькой;
- что данные зашифрованы — шифрование обычно добавляет TLS.

Например, Harbor мог создать бронь, а соединение оборвалось до ответа.
Повтор клиента способен создать вторую бронь, если прикладной протокол и
бизнес-логика не предусмотрели идемпотентность. Надёжность TCP не равна
гарантии бизнес-результата.

## HTTP задаёт смысл байтам

Для учебной модели возьмём HTTP/1.1. Запрос к Harbor может выглядеть так:

```http
GET /rooms HTTP/1.1
Host: 127.0.0.1:8000
Accept: application/json

```

После строки запроса идут заголовки, затем пустая строка. У запроса с телом
после неё шли бы байты тела, длина или способ передачи которых описывается
правилами HTTP. Сервер разбирает метод `GET`, путь `/rooms` и заголовки, а
затем выбирает обработчик.

Ответ:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 25

["Atlas", "Bay", "Cedar"]
```

Статус `200` сообщает результат на уровне HTTP. `Content-Type` объясняет,
как трактовать тело, а `Content-Length` задаёт его длину в **байтах**.
Сервер не может надеяться, что один `recv()` совпадёт с пустой строкой или
целым телом: библиотека HTTP читает поток столько раз, сколько нужно, и
собирает сообщение по правилам протокола.

Фраза «HTTP — текст поверх TCP» полезна именно для первого HTTP/1.1
прогона: строки хорошо видны глазами. Это не универсальное описание всех
версий. HTTP/2 использует бинарные кадры поверх TCP, а HTTP/3 работает
поверх QUIC, который использует UDP. Но роли слоёв сохраняются: прикладной
протокол определяет смысл, транспорт организует доставку, приложение
работает через сетевое окончание.

## Разобранный сухой прогон

Пусть Harbor уже слушает `127.0.0.1:8000`, а браузер открывает
`http://127.0.0.1:8000/rooms`.

1. У процесса Harbor есть listener, допустим FD `3`, привязанный к порту
   `8000`. Вызов `accept()` сейчас блокируется: готового соединения нет.
2. Браузер создаёт сокет. ОС назначает клиентскому окончанию временный порт
   `53124`.
3. `connect()` устанавливает TCP-соединение с `127.0.0.1:8000`. Детали
   рукопожатия выполняют сетевые стеки ОС.
4. Listener становится готовым; `accept()` возвращает Harbor новый FD `4`
   для соединения `53124 → 8000`. FD `3` продолжает слушать.
5. Браузер кодирует HTTP/1.1-запрос в байты и записывает их в свой сокет.
6. TCP доставляет упорядоченный поток. Он может разбить данные на части и
   повторить потерянную часть; границы `send()` серверу не видны.
7. Код Harbor читает FD `4`. Если байтов ещё недостаточно, блокирующий
   `recv()` останавливает **текущий поток** до данных или ошибки.
8. HTTP-библиотека узнаёт конец заголовков, разбирает `GET /rooms` и
   передаёт управление обработчику.
9. Обработчик формирует список комнат. HTTP-библиотека добавляет статус и
   заголовки, кодирует ответ в байты и пишет их в FD `4`.
10. Браузер читает ответ из своего сокета и показывает данные. Соединение
    затем закрывается или остаётся для следующего HTTP-обмена — это зависит
    от версии и договорённостей протокола.

Главный вопрос для следующей главы находится в шаге 7. Пока один поток
Harbor ждёт байты, сможет ли тот же процесс принять и обслужить другого
клиента?

## Упражнение в главе

Не запускайте код: работайте с рисунком.

1. Harbor слушает `10.0.0.5:8000`. Два клиента получили локальные порты
   `51001` и `51002`. Запишите две четвёрки TCP-соединений и объясните,
   почему одинаковый серверный порт не смешивает их.
2. Клиент сделал `send(b"BOOK")`, затем `send(b" A1\n")`. Назовите три
   допустимых разбиения результата на вызовы `recv()`. Почему серверу нужен
   разделитель `\n` или другая длина сообщения?
3. Нарисуйте listener FD `3` и два результата `accept()` — FD `4` и FD `5`.
   Какой из них останется после закрытия соединения первого клиента?
4. Скажите вслух, на каком уровне живут метод `GET`, повторная передача
   потерянных байтов, порт `8000` и номер FD `4`.

В упражнении нет требования угадать реальные номера FD или клиентских
портов: их выбирает ОС. Важно правильно расположить роли.

## Harbor и интервью

- `GET /rooms` — смысл HTTP; TCP не знает, что такое комната или метод.
- Порт `8000` выбирает сетевое окончание учебного Harbor, а не конкретную
  функцию Python.
- Listener принимает соединения; отдельный connected socket несёт байты
  одного TCP-соединения.
- `recv()` возвращает доступные байты, а не «готовый JSON» и не обязательно
  целый запрос.
- Для локальной отладки `127.0.0.1` безопаснее привязки ко всем интерфейсам:
  учебный сервер не становится доступен соседним машинам без необходимости.
- На интервью цепочку лучше рассказывать на одном URL, чем давать четыре
  несвязанных определения.

## Частые ошибки

- Считать FD глобальным номером сокета во всей ОС.
- Читать HTTP прямо из listening socket вместо результата `accept()`.
- Называть порт идентификатором процесса: один процесс может держать
  несколько сокетов, а порт относится к сетевому окончанию.
- Считать TCP сообщениями и ожидать соответствия `send()` ↔ `recv()`.
- Приравнивать успешный `send()` к выполненной брони.
- Говорить «HTTP всегда текст поверх TCP», не ограничив модель HTTP/1.1.

## Мини-голос

> Процесс получает сокет через FD, но FD — только локальный номер ссылки на
> объект ядра.
> Серверный listener привязан к адресу и порту; каждый `accept()` создаёт
> отдельный connected socket.
> TCP даёт упорядоченный надёжный поток байтов, но не сохраняет границы
> вызовов `send`.
> HTTP/1.1 задаёт форму и смысл запроса и ответа поверх этого потока.
> Успешная доставка байтов ещё не гарантирует успешную бизнес-операцию.
