## Задание 1. Доменная ошибка распределения *(medium, обязательно)*

В существующем пути `allocate` добавьте:

```python
class AllocationError(Exception):
    ...


class NoRoomAvailable(AllocationError):
    ...
```

Требования:

- `allocate(...) -> MeetingRoom` возвращает первую подходящую комнату;
- если кандидата нет, функция бросает `NoRoomAvailable`;
- объект ошибки хранит `guest_count`, чтобы обработчик не разбирал текст;
- неположительное число гостей остаётся отдельной ошибкой невалидного
  входа, а не маскируется под «нет мест»;
- внешний сценарий ловит только `NoRoomAvailable`;
- `AttributeError`, `KeyError` и другие неожиданные ошибки не проглатываются.

Тесты: первая подходит; подходит не первая; никто не подходит; пустой
каталог; `guest_count == 0`; намеренно повреждённый объект не превращается в
`NoRoomAvailable`.

**Сухой прогон:** две малые комнаты и запрос на восемь гостей. Покажите
строку, где создаётся ошибка, переход в обработчик и выполнение `finally`,
если он есть.

## Задание 2. Ленивый поток комнат *(medium, обязательно)*

Реализуйте:

```python
from collections.abc import Iterable, Iterator


def iter_suitable_rooms(
    rooms: Iterable[MeetingRoom],
    guest_count: int,
) -> Iterator[MeetingRoom]:
    ...
```

Требования:

- функция является генераторной и отдаёт подходящие комнаты в исходном
  порядке;
- внутри не строится промежуточный `list`, `tuple` или `set`;
- невалидный `guest_count` замечается при первом потреблении генератора;
- повторный проход по уже исчерпанному генератору не выдаёт элементы;
- `allocate` может взять первый элемент потока и не читать остаток.

Докажите ленивость тестом, а не только словами. Сделайте маленький источник,
который считает, сколько комнат у него запросили. После нахождения первой
подходящей комнаты счётчик не должен включать более поздние элементы.

**Сухой прогон:** A(2), B(6), C(10), запрос 5. Покажите два последовательных
`next` и конечный `StopIteration`.

## Задание 6. Pyright clean на моделях *(medium, обязательно)*

Самостоятельно установите и запустите инструмент в существующем виртуальном
окружении:

```bash
python -m pip --version
python -m pip install pyright
pyright --version
pyright harbor
```

Требования:

- `harbor/models.py` и `harbor/errors.py` проходят с директивой

- не добавлены без объяснения `Any`, `cast` и `# type: ignore`.

Сдать два вывода: первый запуск с ошибками и итоговый чистый запуск. Между

значения и исправление. После Pyright отдельно запустите runtime-тесты и
объясните, какие проверки есть только там.

Не подключайте CI и не создавайте конфигурационный файл ради галочки.

## Задание 7. Разбор незнакомого кода *(medium, обязательно)*

Не запускайте и не правьте фрагмент первые десять минут:

```python
def build_plan(
    rows: list[dict[str, object]],
    blocked: set[str],
    guests: int,
) -> list[str]:
    plan: list[str] = []

    for row in rows:
        room_id = str(row["id"])
        capacity = int(row["capacity"])

        if room_id in blocked or capacity < guests:
            continue

        plan.append(room_id)
        blocked.add(room_id)

        if len(plan) == 2:
            break

    return plan
```

Сдать письменный разбор:

1. инвариант одним точным предложением;
2. входы, возврат, исключения и мутации;
3. минимум семь краёв, включая повреждённую строку;
4. сухой прогон на трёх комнатах, где первая заблокирована, а следующие две
   подходят;
5. три «безобидные» правки, которые способны изменить договор;
6. одно вызывающее место, которое вы бы поискали перед рефакторингом;
7. минимальный шов для внешней записи блокировки, если вместо `set` будет
   реальное хранилище;
8. что Pyright способен заметить и что останется вопросом бизнес-смысла.

Только после текста запустите четыре маленьких опыта и сравните результат с
прогнозом. Исправлять фрагмент в рамках задания не нужно: цель — сначала
прочитать договор.

## Задание 8. Hard · ленивые сырые строки *(вернуться позже)*

Реализуйте ленивую границу:

```python
def iter_rooms(
    rows: Iterable[dict[str, object]],
) -> Iterator[MeetingRoom]:
    ...
```

Каждая строка валидируется только при потреблении. Неверный id или capacity
приводит к `InvalidRoomData`; если причиной был `KeyError`, `TypeError` или
`ValueError`, сохраните цепочку исключений.

Сценарий для доказательства ленивости:

1. первая строка содержит подходящую корректную комнату;
2. вторая строка повреждена;
3. `allocate` запрашивает только первую комнату;
4. повреждённая строка ещё не прочитана и ошибка не возникает;
5. полный `list(iter_rooms(rows))` доходит до второй строки и получает
   `InvalidRoomData`.

Сдать рисунок моментов выполнения: создание генератора, первый `next`,
первый `yield`, следующий `next`, ошибка. Объясните, где должен стоять
`try`, чтобы поймать отложенную ошибку.

## Задание 9. Hard · шов хранилища *(вернуться позже)*

Возьмите вариант `allocate`, который сам читает комнаты из репозитория и
помечает выбранную занятой.

1. До изменения зафиксируйте характеризующими тестами текущий успешный и
   ошибочный путь.
2. Отделите решение «какая комната подходит» от внешнего эффекта
   резервирования.
3. Введите минимальный шов: одну или несколько `Callable` либо маленький
   `Protocol`, только если операций действительно несколько.
4. Подставьте в тесте простой фейк без настоящей БД.
5. Сохраните публичное поведение либо перечислите намеренные изменения
   договора.
6. Добейтесь чистого Pyright на новом интерфейсе.
7. Письменно объясните, почему шов сам по себе не делает пару

Не стройте контейнер зависимостей и не подключайте фреймворк. Сложность
