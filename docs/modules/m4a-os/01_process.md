# 01 · Процесс: граница запущенной программы

**Мост:** в M3 функция начиналась с входных данных и заканчивалась
результатом. Но до первого вызова Python уже кто-то запустил интерпретатор,
выделил ему память и связал его с терминалом. Здесь разберём эту единицу
запуска; в следующей главе заглянем в её память.

**Вопрос сюжета:** что именно создаёт Linux, когда мы запускаем Harbor, и
почему два worker не являются двумя копиями одной общей Python-памяти?

### С собеседований

Обычно спрашивают: «Программа и процесс — одно и то же?», «Что такое PID?»,
«Чем процесс отличается от потока?», «Что делают `fork` и `exec`?» и
«Откуда берутся zombie?». Слабый ответ перечисляет термины. Сильный проводит
границу: файл с кодом пассивен, процесс исполняется; у процесса есть
идентичность и ресурсы; потоки внутри одного процесса делят эти ресурсы.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| программа | program | Код и данные на диске; сами по себе ничего не исполняют |
| процесс | process | Запущенный экземпляр программы вместе с состоянием и ресурсами, которыми управляет ОС |
| идентификатор процесса | process identifier, PID | Число, по которому ядро и инструменты различают живые процессы |
| родительский PID | parent PID, PPID | PID процесса, который создал этот процесс |
| адресное пространство | address space | Набор виртуальных адресов, доступных процессу |
| изоляция | isolation | Один обычный процесс не может напрямую читать и менять память другого |
| поток | thread | Последовательность выполнения внутри процесса; потоки одного процесса делят память и открытые ресурсы |
| создать копию процесса | `fork` | Unix-модель: создать дочерний процесс, начинающий с почти того же состояния |
| заменить программу | `exec` | Загрузить в существующий процесс другую программу вместо текущей |
| worker | worker process | Процесс-исполнитель, которому сервер отдаёт часть запросов |
| zombie | zombie process | Уже завершившийся ребёнок, чей родитель ещё не забрал статус завершения |

PID уникален среди одновременно живых процессов в этой системе, но не
навсегда. После завершения номер может быть выдан снова. Поэтому старый PID
нельзя хранить как вечную личность сервиса.

---

## Программа лежит, процесс живёт

Файл `python3` на диске — программа. Файл `harbor.py` — данные для
интерпретатора. Когда shell запускает команду, Linux создаёт контекст
исполнения: назначает PID, подготавливает виртуальную память, таблицу
открытых ресурсов, учёт прав и хотя бы один поток выполнения.

```text
на диске                         во время работы

python3 + harbor.py       ┌──────────────────────────────┐
        │                 │ process PID 4182             │
        └──── запуск ───▶ │ Python + код Harbor          │
                          │ виртуальная память           │
                          │ таблица FD                   │
                          │ поток выполнения             │
                          └──────────────────────────────┘
```

Один и тот же файл можно запустить дважды. Получатся два процесса с разными
PID и разными адресными пространствами. Если первый положит бронь в
глобальный `dict`, второй не увидит запись: одинаковый исходный код не
означает общую изменяемую память.

### Увидеть свой PID

Команда ниже запускает короткий процесс Python. Модуль `os` спрашивает ядро
о PID самого процесса и его родителя:

```bash
python3 -c 'import os; print(f"PID={os.getpid()} PPID={os.getppid()}")'
```

Пример формы вывода:

```text
PID=4182 PPID=3920
```

Числа на вашей машине будут другими. `PPID` часто указывает на shell,
запустивший Python. Сразу после печати процесс завершится, а его запись
исчезнет из обычного списка живых процессов. В
[Linux-лаборатории](./05_linux_lab.md) добавим паузу, чтобы успеть его
рассмотреть.

## Что изолирует процесс

Главная практическая граница — память. Процесс обращается к виртуальным
адресам своего адресного пространства. Ядро и аппаратная защита памяти
переводят эти адреса в физическую память и не дают обычному коду просто
прочитать адрес другого процесса.

Изоляция нужна не ради красивой схемы. Если один worker Harbor повреждает
свой список или падает с ошибкой сегментации в нативной библиотеке, он не
должен произвольно переписать объекты соседнего worker. Цена этой границы —
обычные Python-объекты автоматически не разделяются. Для общей истины о
бронированиях позже понадобится Postgres, а для явного обмена между
процессами существуют файлы, pipes, sockets и другие механизмы IPC.

Процесс также имеет собственный набор или представление ресурсов:

- текущий каталог и переменные окружения;
- права пользователя;
- таблицу файловых дескрипторов;
- обработчики сигналов и состояние завершения;
- один или несколько потоков.

Некоторые ресурсы при создании ребёнка наследуются, а некоторые объекты
ядра могут указывать на общий нижележащий ресурс. Поэтому «изолированы» не
значит «никак не связаны». Точная формулировка: адресные пространства
разделены, а совместное использование должно возникнуть через явный
механизм ОС.

## Модель `fork` → `exec`

В Unix удобно мысленно разделять запуск на два действия:

1. `fork` создаёт дочерний процесс с новым PID. Он начинает с почти такого
   же состояния, как родитель.
2. `exec` заменяет программу и память этого процесса новой программой,
   сохраняя саму личность процесса — в частности, PID.

```text
shell, PID 3920
        │
        │ fork
        ├──────────────────────┐
        │                      ▼
        │              child, PID 4182
        │              пока похож на shell
        │                      │
        │                      │ exec python3
        │                      ▼
        │              Python, PID 4182
        │              выполняет harbor.py
        │                      │
        │                      │ exit status 0
        │◀──────────── wait ───┘
        ▼
shell снова показывает приглашение
```

Слово «копия» не означает немедленное физическое удвоение всей RAM. Linux
обычно применяет copy-on-write: родитель и ребёнок сначала могут ссылаться
на одни физические страницы только для чтения, а при записи изменяемая
страница копируется. Подробная модель памяти будет в следующей главе.

Современный shell или Python иногда использует оптимизированный
`posix_spawn`, а не буквальную пару системных вызовов `fork` и `exec`.
Для базовой Unix-модели разделение всё равно полезно: сначала появляется
контекст нового процесса, затем в нём оказывается нужная программа. Не
надо делать вывод о точных системных вызовах только по этой схеме — для
этого позже используем `strace`.

### Принятый Python-интерфейс

Из Python дочерние программы обычно запускают через `subprocess`, а не через
ручной `os.fork()`. Библиотека берёт на себя платформенные различия,
передачу аргументов и ожидание статуса:

```python
import subprocess


completed = subprocess.run(
    ["python3", "-c", "print('child is running')"],
    check=True,
)

assert completed.returncode == 0
```

Список аргументов передаёт границы слов явно и не требует shell-разбора.
Параметр `check=True` превращает ненулевой код завершения в исключение.
Автоматика удобна, но она не отменяет дочерний процесс: у него будет свой
PID и своё адресное пространство.

## Разобранный прогон запуска

Представим конкретные числа. Shell имеет PID `3920` и выполняет:

```bash
python3 harbor.py
```

Прогон модели:

1. Shell просит ОС запустить ребёнка. Ребёнок получает PID `4182`, а его
   PPID равен `3920`.
2. В ребёнке загружается `python3`; PID остаётся `4182`.
3. Интерпретатор читает `harbor.py`, создаёт Python-объекты и выполняет код.
4. Пока Python работает на переднем плане, shell ждёт завершения ребёнка и
   не показывает новое приглашение.
5. Python заканчивает с кодом `0`. Ядро сохраняет минимальные сведения о
   завершении.
6. Shell получает статус через ожидание (`wait`), после чего запись ребёнка
   можно убрать, и показывает приглашение снова.

Если запустить команду с `&`, shell не обязан ждать перед новым
приглашением, но остаётся родителем и позже всё равно должен собрать статус
ребёнка. Фоновый запуск меняет поведение shell, а не объединяет память
процессов.

## Почему web workers часто являются процессами

Синхронный сервер с одним процессом и одним потоком может выполнять лишь
одну цепочку Python-кода за раз. Если этот поток ждёт медленный запрос к
базе, новый запрос тоже ждёт своей очереди. Один из способов увеличить
число независимых исполнителей — поднять несколько worker-процессов.

```text
                 входящие запросы
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
     worker 1       worker 2       worker 3
     PID 5101       PID 5102       PID 5103
     своя память    своя память    своя память
     свой Python    свой Python    свой Python
```

Процессы дают две важные вещи:

1. **Изоляцию отказа.** Падение одного worker не обязано уничтожить память
   остальных; управляющий процесс может поднять замену.
2. **Использование нескольких CPU-ядер.** Разные процессы могут реально
   исполняться на разных ядрах. Детали GIL и потоков появятся в M4b.

За это платят памятью и координацией. Каждый worker загружает интерпретатор,
код, кэши и обычно заводит свой пул соединений с БД. Глобальный словарь
`bookings` существует отдельно в каждом процессе. Если worker 1 записал
`bookings["A"]`, worker 2 не получает изменение автоматически.

Термин `worker` описывает роль, а не универсальную реализацию. Конкретный
сервер может использовать процессы, потоки или event loop. На собеседовании
лучше сказать «в process-based конфигурации каждый worker — отдельный
процесс» и назвать последствия, чем утверждать, что любой web worker всегда
процесс.

### Почему Harbor начинает с одного

На учебном этапе один процесс сохраняет одну видимую причинную цепочку.
Мы не притворяемся, что Python-словарь годится как общая production-база.
Сначала строим корректную доменную модель и наблюдаем один PID; затем
добавим явное внешнее хранилище и только после этого будем размножать
worker. Иначе ошибка разделённого состояния появится раньше, чем станет
понятна граница, которую мы нарушили.

## Процесс и поток: первый контраст

Процесс — контейнер изоляции и ресурсов. Поток — то, что идёт по
инструкциям внутри этого контейнера и планируется на CPU.

```text
process PID 5101
┌──────────────────────────────────────┐
│ общая память                         │
│ общая таблица FD                     │
│                                      │
│ thread A: свой стек и позиция кода   │
│ thread B: свой стек и позиция кода   │
└──────────────────────────────────────┘
```

Два потока одного процесса видят одни Python-объекты и дескрипторы. Это
делает обмен дешёвым, но создаёт гонки: один поток может изменить состояние,
пока другой на него опирается. Два процесса по умолчанию такой памяти не
делят. В M4a достаточно удерживать границу; синхронизацию и Python GIL
разберём в M4b.

## Zombie — не оживший процесс

Когда ребёнок завершился, родителю нужен его код завершения: `0`, если всё
успешно, или другое значение при ошибке. Ядро временно хранит PID и этот
статус, пока родитель не выполнит `wait`. Такая короткая запись и называется
zombie.

Zombie уже не исполняет пользовательский код и не удерживает своё прежнее
адресное пространство. Он занимает запись в таблице процессов. Один
краткоживущий zombie обычно не проблема, но процесс-родитель, который
никогда не собирает тысячи детей, может исчерпать доступные PID или лимиты
таблицы.

Не путайте zombie с осиротевшим процессом. Осиротевший ребёнок ещё может
работать, хотя его исходный родитель завершился; система передаёт заботу о
нём специальному процессу. Zombie, наоборот, уже закончил работу, но его
статус пока не забран.

В выводе `ps` zombie обычно имеет состояние `Z` и пометку
`<defunct>`. В этом модуле специально создавать его не нужно: идея нужна
для диагностики, а не как обязательный трюк.

## Упражнение в главе

Не запускайте команды до первого ответа вслух.

1. Вы дважды запустили `python3 harbor.py`. Сколько ожидаете PID и сколько
   независимых словарей `bookings`? Что изменится, если это два потока
   одного процесса?
2. Нарисуйте цепочку `shell → fork/spawn → exec → exit → wait`. Укажите,
   на каком шаге появляется новый PID и на каком меняется программа.
3. Worker 1 добавил бронь в глобальный список, а worker 2 её не видит.
   Объясните причину без слов «кэш сломался».
4. Скажите, чем zombie отличается от процесса, который просто спит в
   ожидании I/O.
5. Выполните команду с `os.getpid()` и `os.getppid()`. Объясните оба числа,
   а затем повторите запуск и проверьте, что PID — свойство запуска, а не
   файла `python3`.

## Harbor и интервью

- Один учебный Harbor — один PID и одна понятная область изменяемой памяти.
- Несколько process workers дают изоляцию и параллелизм по ядрам, но не
  общую Python-коллекцию.
- Postgres позже станет явным местом общего состояния, а не «синхронизацией
  глобальных переменных».
- Управляющий процесс сервера должен замечать завершение workers и собирать
  их статусы.
- На интервью начните с границы памяти и ресурсов, затем переходите к цене
  процессов и потоков.

## Частые ошибки

- Называть файл с программой процессом, хотя он не запущен.
- Считать PID вечным уникальным идентификатором.
- Говорить, что `fork` всегда немедленно копирует всю физическую память.
- Утверждать, что все web workers при любой конфигурации являются
  процессами.
- Ожидать общий глобальный `dict` у нескольких process workers.
- Считать zombie работающим процессом, который ест CPU.
- Путать zombie с ребёнком, чей родитель завершился.

## Мини-голос

> Программа — код на диске, процесс — её запущенный экземпляр с PID,
> виртуальной памятью и ресурсами.
> Два процесса изолированы и не делят обычные Python-объекты автоматически.
> Потоки одного процесса, наоборот, разделяют память и FD.
> `fork` создаёт ребёнка, `exec` заменяет в нём программу, а `wait` забирает
> статус завершения.
> Process workers используют несколько ядер, но общее состояние выносят
> наружу.
