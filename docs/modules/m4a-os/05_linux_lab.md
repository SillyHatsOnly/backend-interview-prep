# 05 · Лаборатория Linux: увидеть процесс живьём

**Мост:** четыре главы построили модель на схемах. Теперь проверим её на
Linux Mint: создадим свой процесс, найдём его PID и состояние, посмотрим
память и FD, а затем увидим блокирующие системные вызовы. После лаборатории
домашка потребует повторить наблюдение без пошаговой подсказки.

**Вопрос лаборатории:** можем ли мы связать одну строку Python с конкретным
PID, записью в `/proc`, открытым FD и паузой внутри системного вызова?

```text
что хотим узнать                где смотрим

кто запущен, кто родитель   →   ps
CPU и состояние во времени  →   top / htop
что знает ядро о PID         →   /proc/PID
какие ресурсы открыты        →   lsof + /proc/PID/fd
какие syscalls происходят    →   strace
```

Команды ниже выполняете вы. Не создавайте файл через heredoc или
сгенерированный setup-скрипт: два маленьких файла нужно набрать в редакторе,
чтобы понимать каждую строку.

---

## Что получить на выходе

Сохраните для себя короткий журнал:

1. прогноз до команды;
2. саму команду;
3. две–пять важных строк вывода;
4. объяснение: что изменилось в процессе и почему.

Полные дампы `strace` и `lsof` в отчёт не нужны. Цель — интерпретация, а не
объём терминального вывода.

---

## Безопасность

- Работайте только со своими учебными Python-процессами.
- Не запускайте `strace` через `sudo` и не подключайтесь к системным
  сервисам. В этой лаборатории мы запускаем свой процесс сразу под
  `strace`, поэтому дополнительных прав не нужно.
- Для остановки своего foreground-процесса сначала используйте `Ctrl+C`.
  Не привыкайте начинать с `kill -9`: он не даёт приложению выполнить
  обычное завершение и закрыть ресурсы.
- Не пытайтесь вызвать OOM и не уменьшайте системные лимиты. Память здесь
  только наблюдаем.
- PID переиспользуются. Перед действием ещё раз проверьте команду процесса,
  особенно если первоначальный скрипт уже мог завершиться.
- `/proc/PID` — живой снимок. Каталог законно исчезнет сразу после
  завершения процесса.
- `strace` может записать пути, аргументы и введённые данные. Не публикуйте
  trace целиком; учебный `read.trace` после разбора можно удалить.

## Шаг 0. Проверить инструменты

Нужны два окна терминала: **A** запускает процесс, **B** наблюдает. Сначала
проверяем версии и наличие команд, чтобы отличить «пакет не установлен» от
ошибки в опыте.

В любом терминале выполните:

```bash
python3 --version
command -v ps
command -v top
command -v lsof
command -v strace
command -v htop
```

`command -v` печатает путь, если команда найдена, и ничего — если нет.
`ps`, `top` и `/proc` обычно уже доступны в Linux Mint. `lsof`, `strace` и
`htop` могут отсутствовать.

Если нет **обязательных** `lsof` или `strace`, сначала объясните себе, зачем
они нужны: `lsof` связывает PID с открытыми ресурсами, `strace` показывает
границу между процессом и ядром. Затем установите только нужные пакеты:

```bash
sudo apt update
sudo apt install lsof strace
```

`htop` — необязательный интерактивный просмотрщик. `top` полностью
достаточен для выхода лаборатории. Если хотите сравнить интерфейсы:

```bash
sudo apt install htop
```

Не включайте установку пакетов в скрипт: это разовое осознанное изменение
системы.

## Шаг 1. Набрать процесс, который спит

Нужен процесс, который живёт достаточно долго для наблюдения. Он печатает
собственные PID и PPID, затем просит ядро разбудить поток через заданное
число секунд.

В терминале A сначала узнайте PID текущего shell:

```bash
echo $$
```

Теперь откройте файл в редакторе. Например:

```bash
nano sleep_probe.py
```

Наберите руками:

```python
import os
import sys
import time


seconds = int(sys.argv[1])
print(f"PID={os.getpid()} PPID={os.getppid()}", flush=True)
print(f"sleeping for {seconds} seconds", flush=True)
time.sleep(seconds)
print("awake", flush=True)
```

В `nano` сохраните через `Ctrl+O`, подтвердите имя через `Enter` и
выйдите через `Ctrl+X`. Если используете другой редактор, действия те же:
набрать, перечитать, сохранить.

Запустите процесс на 90 секунд:

```bash
python3 sleep_probe.py 90
```

Сравните напечатанный `PPID` с `echo $$`. В обычном терминале родителем
будет shell. Если среда запуска добавила промежуточный процесс, числа могут
не совпасть — это повод посмотреть реальную цепочку, а не подгонять вывод
под схему.

Запишите напечатанный PID. Дальше в терминале B положим его в переменную
shell. Вместо `12345` введите своё число:

```bash
pid=12345
```

Переменная нужна только для удобства набора следующих команд; она не
создаёт и не меняет процесс.

## Шаг 2. `ps`: один снимок процесса

`ps` нужен, чтобы получить контролируемый снимок: PID, родителя, состояние,
время жизни, CPU, память и команду в одной строке.

В терминале B выполните:

```bash
ps -o pid,ppid,stat,etime,%cpu,%mem,comm,args -p "$pid"
```

Разберите столбцы:

- `PID` и `PPID` — процесс и родитель;
- `STAT` — текущее состояние; во время `sleep` обычно увидите `S`;
- `ELAPSED` — сколько процесс живёт по настенным часам;
- `%CPU` и `%MEM` — моментальные/усреднённые оценки, а не абсолютная истина;
- `COMMAND`/`ARGS` — имя и аргументы запуска.

Состояние `S` здесь ожидаемо: поток ждёт таймер и не обязан расходовать CPU.
Если процесс успел завершиться, `ps` напишет, что выбранного PID нет. Просто
запустите его снова и обновите переменную `pid`; не используйте старый PID
вслепую.

Чтобы отдельно увидеть родителя, возьмите PPID из вывода и выполните:

```bash
ps -o pid,ppid,stat,comm,args -p НОМЕР_PPID
```

Замените `НОМЕР_PPID` числом, не копируйте слово буквально.

## Шаг 3. `top` и идея `htop`: наблюдение во времени

`ps` отвечает «что было в момент снимка». `top` обновляет показатели и
помогает заметить переходы. Ограничим экран одним учебным PID:

```bash
top -p "$pid"
```

Найдите столбцы состояния и CPU. Спящий процесс должен почти всё время
иметь состояние сна и около нуля CPU. Нажмите `q`, чтобы выйти.

Если установили `htop`, можно посмотреть тот же PID более удобным
интерактивным интерфейсом:

```bash
htop -p "$pid"
```

Выйдите через `q` или `F10`. `htop` не даёт другой реальности — только
иначе показывает те же данные ядра. Для воспроизводимого отчёта `ps` обычно
удобнее, потому что точный набор столбцов задаётся командой.

### Маленькая проверка CPU

После завершения долгого запуска выполните короткий:

```bash
time python3 sleep_probe.py 2
```

Сравните `real` с `user + sys`. Две секунды прошли по часам, но процесс
почти не считал. Это наблюдение из главы о blocking I/O, а не просто
особенность команды `sleep`.

## Шаг 4. `/proc`: представление ядра

`/proc` выглядит как каталог, но многие файлы в нём создаются ядром на
чтение. `/proc/PID` показывает состояние конкретного живого процесса.

Если процесс завершился, снова запустите:

```bash
python3 sleep_probe.py 90
```

Обновите `pid` в терминале B, затем выберите важные строки статуса:

```bash
grep -E '^(Name|State|Pid|PPid|Threads|VmSize|VmRSS):' \
  /proc/"$pid"/status
```

Здесь:

- `Threads` показывает число OS threads в процессе;
- `VmSize` — размер виртуального адресного пространства;
- `VmRSS` — страницы процесса, находящиеся в RAM, с оговорками об общей
  памяти;
- `State` должен согласовываться с `ps`, хотя состояние может измениться
  между двумя командами.

Теперь посмотрите настоящую командную строку. Аргументы в `/proc` разделены
нулевым байтом, поэтому `tr` заменяет его пробелом:

```bash
tr '\0' ' ' < /proc/"$pid"/cmdline
echo
```

`echo` здесь только переносит приглашение shell на новую строку.

Не читайте `/proc/PID/environ` ради любопытства: там могут быть секреты.
Для цели M4a достаточно статуса, аргументов и FD.

## Шаг 5. `/proc/PID/fd` и `lsof`: открытые ресурсы

Каталог `fd` содержит символические ссылки по номерам дескрипторов. Сначала
посмотрите его напрямую:

```bash
ls -l /proc/"$pid"/fd
```

У foreground-скрипта FD `0`, `1` и `2` обычно ведут к псевдотерминалу вида
`/dev/pts/N`. Проверьте каждый адрес отдельно:

```bash
readlink /proc/"$pid"/fd/0
readlink /proc/"$pid"/fd/1
readlink /proc/"$pid"/fd/2
```

Одинаковая цель не означает один и тот же FD: это три записи таблицы,
которые сейчас связаны с одним терминальным устройством и имеют разные
роли.

`lsof` добавляет понятные столбцы и типы. Сначала ограничьте вывод тремя
стандартными FD:

```bash
lsof -a -p "$pid" -d 0,1,2
```

Флаг `-a` означает «одновременно выполнить условия PID и списка FD».
В столбце `FD` возможен суффикс режима: например, `0r` читается, а `1w`
пишется. Точный вид зависит от версии и терминала.

Теперь посмотрите весь вывод:

```bash
lsof -p "$pid"
```

Не каждая строка здесь является числовым FD. Значения `cwd`, `rtd`, `txt`,
`mem` в столбце `FD` обозначают текущий каталог, корень, исполняемый файл и
memory-mapped объекты. Для ответа «какие именно дескрипторы открыты» ищите
числовые записи и сверяйте их с `/proc/PID/fd`.

Скрипт уже прочитал свой исходный файл при старте и не обязан держать
`sleep_probe.py` открытым всё время. Поэтому отсутствие этого пути среди
числовых FD — нормальное наблюдение.

## Шаг 6. `strace` сна: увидеть системный вызов

`strace` показывает системные вызовы на границе процесса и ядра. Запустим
новый короткий процесс сразу под наблюдением. Фильтр оставляет несколько
вариантов syscall, которыми разные версии Python могут реализовать сон:

```bash
strace -tt -T \
  -e trace=clock_nanosleep,nanosleep,select,pselect6 \
  python3 sleep_probe.py 2
```

Что означают параметры:

- `-tt` — время с микросекундами;
- `-T` — длительность каждого системного вызова;
- `-e trace=...` — не печатать тысячи нерелевантных вызовов запуска;
- последняя часть — обычная команда, которую `strace` запускает как ребёнка.

На современной системе часто встретится строка примерно такой формы:

```text
clock_nanosleep(..., {tv_sec=...}, NULL) = 0 <2.000...>
```

Точный syscall, аргументы и длительность отличаются. Важен факт: поток
находился внутри ожидания около двух секунд, после возврата напечатал
`awake` и завершился. `strace` пишет свою диагностику в stderr, поэтому она
может визуально перемешаться с stdout программы.

Если фильтр не показывает вызов сна, не делайте вывод «Python не обращался
к ядру». Версия интерпретатора или libc могла выбрать другой механизм.
Сначала получите короткую агрегированную сводку всех syscall. Флаг `-w`
просит считать настенное время, включая ожидание:

```bash
strace -c -w python3 sleep_probe.py 2
```

Ищите вызов, на который пришлось около двух секунд, затем добавьте его имя
в фильтр и повторите опыт. `-c` показывает суммы и число вызовов, но не их
порядок; без `-w` сводка учитывала бы системное CPU-время и скрыла бы
длительность сна. Так мы сначала уточняем гипотезу, а не листаем
нефильтрованный огромный trace.

## Шаг 7. Набрать процесс, который ждёт stdin

Теперь свяжем блокирующий `read` с FD `0`. Откройте второй файл:

```bash
nano read_probe.py
```

Наберите:

```python
import os


print(f"PID={os.getpid()} PPID={os.getppid()}", flush=True)
room_id = input("room id> ")
print(f"received={room_id!r}", flush=True)
```

Сохраните файл и сначала запустите без трассировки:

```bash
python3 read_probe.py
```

Не вводите строку сразу. Пока приглашение `room id>` ждёт, во втором
терминале:

1. положите напечатанный PID в `pid`;
2. выполните команду `ps` из шага 2;
3. посмотрите `/proc/"$pid"/fd/0`;
4. выполните `lsof -a -p "$pid" -d 0,1,2`.

Свяжите наблюдение словами: поток спит, FD `0` ведёт к терминалу, процесс
жив, а CPU доступен другим. Затем вернитесь в терминал A, введите, например,
`A-17` и нажмите Enter. Процесс получит строку и завершится.

## Шаг 8. `strace` чтения: найти паузу

Теперь запускаем тот же файл под `strace`. Вывод трассировки направим в
отдельный файл, чтобы Python-приглашение осталось читаемым. `-T` добавит
длительность syscall:

```bash
strace -tt -T -e trace=read,write \
  -o read.trace \
  python3 read_probe.py
```

Подождите три–пять секунд, введите `A-17` и нажмите Enter. Затем откройте
trace:

```bash
less read.trace
```

Python при старте читает модули и файлы, поэтому `read` будет много.
В `less` наберите `/read(0` и нажмите Enter, чтобы искать чтение stdin;
`n` переходит к следующему совпадению. Ближе к концу ожидается строка
формы:

```text
read(0, "A-17\n", ...) = 5 <несколько секунд>
```

Точный размер буфера и формат могут отличаться. Пять байтов — это четыре
символа `A-17` и перевод строки в ASCII/UTF-8. Длительность справа показывает,
что системный вызов не возвращался до Enter. Рядом найдите `write`, который
печатал приглашение или результат.

Выйдите из `less` клавишей `q`. Если trace больше не нужен и вы уже сохранили
важные строки в журнал:

```bash
rm read.trace
```

Удаление осознанное: trace содержит введённые данные. Сам
`read_probe.py` оставьте для домашнего повторения.

## Шаг 9. Закрыть цикл наблюдения

Для каждого инструмента произнесите одну причинную фразу:

- `ps` показал `S`, **потому что** поток ждал таймер или ввод;
- `%CPU` был близок к нулю, **потому что** waiting-поток не крутил активный
  цикл;
- `/proc/PID/status` существовал, **потому что** процесс был жив;
- `/proc/PID/fd/0` вёл к терминалу, **потому что** shell оставил stdin
  связанным с ним;
- `lsof` показал числовые FD и дополнительные mappings, которые нельзя
  смешивать;
- `strace` показал долгий `read(0, ...)`, **потому что** строка ещё не была
  введена.

После завершения скрипта повторите:

```bash
ps -p "$pid"
ls /proc/"$pid"
```

Обе команды должны показать, что прежнего живого процесса больше нет.
Если PID уже переиспользован, `ps` может показать другой процесс — именно
поэтому всегда сверяем `args`, а не доверяем одному числу.

## Если наблюдение отличается

Различие не надо скрывать. Проверьте по порядку:

1. Процесс ещё жив и PID записан без ошибки?
2. Вы смотрите из того же пользователя?
3. stdin действительно терминал, а не перенаправленный файл?
4. Версии Python и Linux используют другой syscall?
5. Инструмент установлен и команда завершилась без сообщения об ошибке?

В контейнере, IDE или удалённой среде родитель и устройство терминала могут
отличаться от обычного Mint Terminal. Модель остаётся проверяемой: у
процесса есть реальный PPID и реальные цели FD, просто они другие.

Не повторяйте одну и ту же команду вслепую. Запишите отличие, сформулируйте
новую гипотезу и выберите инструмент, который её различает.
