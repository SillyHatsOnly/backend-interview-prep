# 04 · Планирование и блокирующий I/O

**Мост:** у процесса есть FD, через который Python просит ядро читать или
писать. Но данные не всегда готовы немедленно: пользователь ещё не ввёл
строку, диск занят, сервер БД не прислал ответ. Здесь разберём судьбу
вызвавшего потока во время ожидания; следующая глава покажет её через
`ps` и `strace`.

**Вопрос сюжета:** если Harbor ждёт байты из FD, занимает ли он CPU и может
ли в это время обработать другой запрос?

### С собеседований

Спрашивают: «Что планирует ОС?», «Чем CPU-bound работа отличается от
I/O-bound?», «Что значит blocking call?», «Блокируется поток или процесс?» и
«Почему async помогает ожиданию, но не тяжёлому вычислению?». Главная
ошибка — отвечать «блокируется процесс». Блокирующий вызов останавливает
вызвавший **поток**. Если поток в процессе один, пользовательский код этого
процесса действительно больше не продвигается, но ядро и другие процессы
продолжают работать.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| планировщик | scheduler | Часть ядра, которая выбирает готовый поток для выполнения на CPU |
| выполняется | running | Поток сейчас получает инструкции CPU |
| готов | runnable / ready | Поток может считать, но ждёт своей очереди на CPU |
| спит / ждёт | sleeping / waiting | Поток пока не может продолжить: ожидает событие, таймер или I/O |
| вытеснение | preemption | ОС прерывает поток и отдаёт CPU другому готовому потоку |
| CPU-bound | CPU-bound work | Скорость ограничена вычислениями на процессоре |
| I/O-bound | I/O-bound work | Большая часть времени уходит на ожидание внешних данных или записи |
| блокирующий вызов | blocking call | Вызов не возвращает управление потоку, пока результат не готов или не случилась ошибка/таймаут |
| неблокирующий режим | non-blocking mode | Если операция сейчас не готова, вызов сразу сообщает об этом вместо сна потока |
| активное ожидание | busy waiting | Цикл постоянно проверяет условие и расходует CPU, хотя полезной работы нет |
| переключение контекста | context switch | Сохранение состояния одного потока и продолжение другого |

В Linux планируемую сущность часто называют task; для базовой модели можно
думать об OS thread. Процесс задаёт общие ресурсы, а каждый поток имеет свою
позицию выполнения, регистры и стек и отдельно бывает running, runnable или
waiting.

---

## CPU — очередь, а не постоянная собственность процесса

На одном CPU-ядре в конкретный момент исполняется один поток. Если готовых
потоков больше, планировщик быстро переключается между ними. Пользователь
видит одновременное продвижение, хотя на одном ядре это чередование. На
нескольких ядрах несколько потоков действительно могут исполняться
параллельно.

```text
время ─────────────────────────────────────────────────────▶

CPU 0:  worker A  │ shell │ worker B │ worker A │ browser
CPU 1:  browser   │ worker C         │ kernel   │ worker C

worker A: running ─▶ runnable ─▶ running ─▶ waiting for I/O
worker B: runnable ─────────────▶ running ─▶ runnable
```

Вытеснение означает, что поток не выбирает сам каждую точку паузы.
Планировщик может отдать CPU другому. Поэтому порядок выполнения нескольких
потоков или процессов нельзя считать стабильным только потому, что в одном
запуске лог всегда печатался одинаково.

Справедливость тоже не означает строгую карусель «ровно по 10 мс каждому».
Планировщик учитывает приоритеты, загрузку ядер и другие правила. Для M4a
важен инвариант: runnable конкурирует за CPU, waiting до события в этой
конкуренции не участвует.

---

## Считает или ждёт

Рассмотрим две операции Harbor.

**Вычисление:** перебрать миллион комбинаций комнат. Поток постоянно
выполняет инструкции. Он runnable или running и потребляет процессорное
время. Ускорение требует лучшего алгоритма, другого ядра или другого
исполнителя; простое ожидание ничего не исправит.

**I/O:** отправить запрос Postgres и ждать ответ по socket. После отправки
потоку пока нечего вычислять: необходимые байты находятся за пределами
процесса. В блокирующем режиме ядро укладывает поток спать и будит, когда
данные готовы, произошла ошибка или истёк таймаут.

```text
CPU-bound:
running [compute][compute][compute] → result
CPU занят полезными или бесполезными вычислениями всё время

I/O-bound, blocking:
running [send] → waiting .......... → runnable → running [handle result]
                        в паузе CPU исполняет другие потоки
```

Ожидание может быть долгим по настенным часам и почти бесплатным по CPU.
Поэтому фраза «запрос выполнялся две секунды» ничего не говорит о том,
считал процесс две секунды или почти всё время спал.

## Что делает блокирующий `read`

Пусть Python выполняет `input()`, а stdin связан с терминалом на FD `0`.
Пользователь ещё не нажал Enter.

```text
Python thread          kernel / FD 0              другие потоки
     │
     │ read(0, ...)
     ▼
данных нет ──────────▶ поставить в wait queue
     │                        │
     │ sleeping              ├──────────────▶ CPU работает здесь
     │                        │
пользователь вводит A-17\n ──┘
     │
     │ runnable: данные готовы
     ▼
планировщик даёт CPU
     │
read возвращает "A-17\n"
     ▼
Python продолжает код
```

Пошагово:

1. `input()` в итоге просит прочитать данные из stdin.
2. Ядро проверяет буфер терминала. Полной строки пока нет.
3. В блокирующем режиме системный вызов не возвращает «пусто». Текущий
   поток переводится в ожидание.
4. Планировщик не выдаёт ему CPU до подходящего события и запускает других.
5. После ввода ядро делает поток runnable.
6. Поток не обязательно продолжает в ту же наносекунду: сначала
   планировщик должен снова дать ему CPU.
7. `read` возвращает байты, Python декодирует строку и идёт дальше.

Блокировка относится к вызвавшему потоку. Второй поток в том же процессе
может исполняться, потому что имеет собственное состояние выполнения.
Однако он разделяет память и FD, поэтому появляются вопросы синхронизации.
Несколько process workers тоже продолжают работу независимо, потому что это
другие процессы и потоки.

## `sleep` не является активным циклом

Чтобы отделить настенное время от CPU-времени, сначала объясним команду.
Утилита shell `time` печатает:

- `real` — сколько прошло по часам;
- `user` — сколько CPU-времени ушло на пользовательский код;
- `sys` — сколько CPU-времени ушло в ядре от имени процесса.

Теперь выполните:

```bash
time python3 -c 'import time; time.sleep(2)'
```

Форма результата зависит от shell, но `real` будет около двух секунд, а
`user + sys` — намного меньше. `sleep(2)` просит ОС разбудить поток позже;
он не обязан два миллиарда раз проверять часы.

Сравните с активным ожиданием:

```python
import time

deadline = time.monotonic() + 2
while time.monotonic() < deadline:
    pass
```

Оба фрагмента возвращают управление примерно через две секунды. Но второй
держит поток runnable и тратит CPU на проверки. На ноутбуке это означает
лишнее тепло и конкуренцию, а в сервисе — отнятое у запросов процессорное
время.

Не используйте активный цикл как способ «не блокироваться». Неблокирующий
I/O работает иначе: операция быстро сообщает «пока не готово», а поток
занимается другой полезной работой и просит ядро уведомить о готовности.
Эту механику event loop разберём в M4b.

## Разобранный прогон одного запроса Harbor

Пусть один синхронный worker имеет один поток. Запрос бронирования проходит
этапы:

```text
0 ms      принять уже готовый запрос          running, CPU
1–3 ms    проверить вместимость               running, CPU
3 ms      отправить SQL                       running, CPU
4–54 ms   ждать ответ Postgres                waiting, CPU не занят worker'ом
54 ms     ответ готов                         runnable
55–57 ms  собрать результат                   running, CPU
57 ms     записать ответ клиенту              running или краткое waiting
```

Настенное время — около 57 мс, а CPU-время worker — примерно 6 мс.
Проблема одного синхронного потока не в том, что он жжёт CPU все 50 мс
ожидания. Проблема в том, что его цепочка кода не может в это время начать
другой запрос.

Несколько process workers дают несколько независимых блокирующих
исполнителей: пока один ждёт БД, другой может принять запрос. Но каждый
worker требует память и соединения, а большое число одновременно
заблокированных workers не бесконечно масштабируется.

`asyncio` позже позволит одному потоку добровольно переключаться между
многими задачами в точках ожидания, если библиотеки используют
неблокирующий I/O. Оно не сделает тяжёлый перебор комнат быстрее: CPU-bound
функция без `await` всё равно удержит event loop.

## Состояния в `ps`

`ps` показывает краткий код состояния процесса или его главного потока.
Для лаборатории достаточно первых букв:

| Код | Упрощённый смысл |
|-----|------------------|
| `R` | running или runnable: выполняется либо готов к CPU |
| `S` | interruptible sleep: ждёт событие и может быть разбужен сигналом |
| `D` | uninterruptible sleep: обычно ждёт ядро/I/O в состоянии, которое нельзя сразу прервать обычным сигналом |
| `T` | остановлен, например сигналом или отладчиком |
| `Z` | завершился, родитель ещё не забрал статус |

Это снимок, а состояния меняются быстрее команды. Отсутствие `R` в одном
выводе не доказывает, что процесс никогда не считает. И `S` не означает
ошибку: терминал, сервер и shell большую часть спокойного времени именно
ждут.

Не делайте из `D` автоматический диагноз «сломался диск». Код говорит о
состоянии ожидания, а причину уточняют по стеку ядра, логам и системным
вызовам. В M4a достаточно не путать его с zombie.

## Таймаут — часть контракта ожидания

Блокирующая операция без ограничения может ждать бесконечно: peer не
ответил, pipe не закрыт, пользователь ушёл. Для сетевого backend у каждого
внешнего ожидания позже должен появиться осмысленный timeout и решение,
что делать после него.

Таймаут не делает операцию неблокирующей. Поток всё ещё может спать, просто
не дольше заданного срока. После таймаута нужна обработка ошибки и, иногда,
отмена нижележащей работы. Слишком короткий timeout создаёт ложные отказы,
слишком длинный удерживает исполнителей и ресурсы.

В этой главе мы не подбираем production-значения Harbor. Фиксируем идею:
ожидание имеет владельца, предел и поведение при истечении.

## Упражнение в главе

Дан один worker с одним потоком:

```text
запрос A: 2 мс CPU → 100 мс ожидание БД → 3 мс CPU
запрос B приходит через 10 мс
```

1. Нарисуйте timeline. Когда этот worker сможет начать B в синхронной
   модели?
2. Сколько примерно CPU-времени и настенного времени занимает A?
3. Изменится ли ответ, если добавить второй process worker? Какую цену он
   добавит?
4. Почему один async event loop потенциально начнёт B во время ожидания A,
   но не сможет переключиться, если A вместо I/O выполняет 100 мс чистого
   Python-вычисления без точки уступки?
5. Выполните команду с `time.sleep(2)`. До запуска предскажите соотношение
   `real`, `user`, `sys`; после запуска объясните его состояниями потока.
6. Скажите вслух: «блокирующий вызов останавливает ...» — закончите фразу
   точно, не используя слово «всё».

## Harbor и интервью

- Планировщик выдаёт CPU готовым потокам; waiting-поток временно не
  конкурирует за процессор.
- Блокирующий `read` останавливает вызвавший поток до данных, ошибки,
  сигнала или таймаута.
- Один синхронный worker простаивает как обработчик запроса, даже если его
  CPU свободен для других процессов.
- Несколько process workers скрывают часть ожиданий, но умножают память и
  подключения.
- Async полезен для множества ожиданий; CPU-bound код требует другого
  решения и хорошего алгоритма.
- По одному коду `S` или `R` диагноз не ставят: это короткий снимок.

## Частые ошибки

- Говорить «блокируется вся ОС» или без уточнения «блокируется процесс».
- Считать, что sleeping-поток постоянно ест CPU.
- Путать waiting с runnable: первый пока не может продолжать, второй готов,
  но ждёт CPU.
- Называть активный цикл неблокирующим решением.
- Обещать, что `asyncio` ускорит тяжёлое вычисление.
- Считать один снимок `ps` полной историей процесса.
- Называть любой `S` зависанием, а любой `D` поломкой диска.
- Забывать timeout у внешнего ожидания.

## Мини-голос

> ОС планирует потоки: running сейчас считает, runnable готов, waiting ждёт
> событие.
> Блокирующий I/O останавливает вызвавший поток, но обычно освобождает CPU
> для других.
> Если поток в worker один, этот worker не начнёт второй запрос до возврата
> вызова.
> Несколько workers дают несколько исполнителей ценой памяти и ресурсов.
> Async позже позволит переиспользовать ожидание, но не ускорит CPU-bound
> вычисление само по себе.
