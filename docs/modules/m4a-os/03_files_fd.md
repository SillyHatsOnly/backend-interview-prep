# 03 · Файлы и файловые дескрипторы

**Мост:** процесс изолирован памятью, но backend бесполезен без внешнего
мира. Ему нужно читать конфигурацию, писать лог, общаться с терминалом, а
позже — принимать сеть. Linux даёт этим разным ресурсам общий маленький
интерфейс. В следующей главе посмотрим, что происходит с потоком, когда
чтение из такого ресурса пока не может вернуть данные.

**Вопрос сюжета:** что означает число `3`, которое вернул `open`, и почему
будущий socket Harbor тоже будет представлен числом, хотя он не является
файлом на диске?

### С собеседований

Спрашивают: «Что такое file descriptor?», «Какие FD зарезервированы для
stdin/stdout/stderr?», «Что делает pipe?», «Почему socket — FD?» и «Что
будет при утечке дескрипторов?». Частый провал — назвать FD указателем на
файл. Дескриптор — маленький индекс в таблице конкретного процесса; за
индексом ядро хранит ссылку на открытый объект и его состояние.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| файловый дескриптор | file descriptor, FD | Неотрицательное число — индекс открытого ресурса в таблице процесса |
| открыть | open | Попросить ядро связать новый FD с ресурсом и режимом доступа |
| закрыть | close | Удалить связь FD с ресурсом; номер можно будет использовать снова |
| стандартный ввод | standard input, stdin | Поток входа по соглашению на FD 0 |
| стандартный вывод | standard output, stdout | Обычный результат программы по соглашению на FD 1 |
| стандартный поток ошибок | standard error, stderr | Диагностика по соглашению на FD 2 |
| смещение | file offset | Текущая позиция чтения или записи в обычном открытом файле |
| перенаправление | redirection | Shell заранее связывает стандартный FD с другим ресурсом |
| канал | pipe | Буфер ядра с концом для записи и концом для чтения |
| сокет | socket | Объект ядра для обмена данными; в Unix процесс обращается к нему через FD |
| утечка FD | file descriptor leak | Процесс продолжает держать ненужные дескрипторы и со временем упирается в лимит |

## FD — номер в таблице процесса

У каждого процесса есть таблица дескрипторов. В упрощённой картине запись
ведёт к описанию открытого объекта в ядре, а уже оно — к файлу, pipe, socket
или другому ресурсу.

```text
process PID 5101

таблица FD                 объекты ядра
┌────┬──────────────┐
│ 0  │──────────────┼──▶ terminal input
│ 1  │──────────────┼──▶ terminal output
│ 2  │──────────────┼──▶ terminal output
│ 3  │──────────────┼──▶ open file description
│ 4  │──────────────┼──▶ pipe read end
└────┴──────────────┘          │
                              ▼
                        /etc/os-release
                        offset, flags
```

Число `3` не содержит путь, данные или права. Оно имеет смысл только вместе
с таблицей процесса. В другом процессе FD `3` может указывать на совсем
другой файл или socket. Даже в одном процессе номер после `close(3)` может
быть быстро переиспользован для нового ресурса.

Это важно для логов и гонок. Фраза «ошибка на FD 7» без PID и момента
наблюдения неполна: нужно знать, в таблице какого процесса и до какого
закрытия существовала запись.

### Три уровня, которые не надо смешивать

Python-программа обычно видит объект файла:

```text
Python file object
        │ .fileno()
        ▼
FD в таблице процесса
        │
        ▼
open file description в ядре
        │ offset + flags
        ▼
файл / pipe / terminal / socket
```

Python-объект добавляет буферизацию, кодировку текста и удобные методы.
FD остаётся интерфейсом ОС. У нескольких FD иногда может быть одно общее
описание открытого файла — например, после `dup` или наследования при
`fork`; тогда они могут разделять текущую позицию. Для базовой диагностики
достаточно помнить: FD — не сам ресурс, а процессная ручка к нему.

## `open → read/write → close`

Откроем существующий системный файл, чтобы не создавать учебную заготовку:

```python
with open("/etc/os-release", encoding="utf-8") as source:
    descriptor = source.fileno()
    first_line = source.readline()
    print(f"fd={descriptor} line={first_line!r}")
```

Разобранный прогон:

1. `open(...)` просит ядро открыть путь для чтения.
2. Ядро проверяет права и создаёт запись открытого файла с позицией в
   начале.
3. В таблице процесса появляется свободный номер. Часто это `3`, потому что
   `0`, `1`, `2` уже заняты, но программа не должна полагаться на конкретное
   число.
4. Python создаёт объект `source`, который хранит FD и свою буферизацию.
5. `readline()` в какой-то момент читает байты через FD; позиция открытого
   файла сдвигается.
6. Выход из `with` закрывает Python-объект и FD даже при исключении.

Контекстный менеджер нужен не для стиля. Если забывать закрывать файл в
долго живущем worker, каждая заявка может оставлять новую запись в таблице.
После достижения лимита следующий `open` или `socket` завершится ошибкой
вроде `OSError: [Errno 24] Too many open files`. Проблема проявится далеко
от места первой утечки.

### Принято в Python

Для ресурса с ограниченным временем жизни используйте `with`:

```python
def load_mint_name() -> str:
    with open("/etc/os-release", encoding="utf-8") as source:
        for line in source:
            if line.startswith("PRETTY_NAME="):
                return line.removeprefix("PRETTY_NAME=").strip().strip('"')
    raise RuntimeError("PRETTY_NAME is missing")
```

Ручная пара `open()` / `close()` легко ломается при раннем `return` или
исключении. `with` закрывает этот путь автоматически, но не решает все
задачи: если сохранить объект файла в глобальной коллекции, контекст не
закончится, а если передать FD другому коду, договор владения всё равно надо
объяснить.

## FD 0, 1 и 2: договор с shell

По соглашению процесс стартует с тремя стандартными потоками:

```text
FD 0  stdin   откуда программа читает обычный ввод
FD 1  stdout  куда пишет обычный результат
FD 2  stderr  куда пишет ошибки и диагностику
```

Проверить номера Python-потоков можно так:

```bash
python3 -c 'import sys; print(sys.stdin.fileno(), sys.stdout.fileno(), sys.stderr.fileno())'
```

Обычный вывод:

```text
0 1 2
```

Это соглашение, а не требование «все три всегда терминал». Shell может до
запуска процесса поменять связи. Поэтому программа продолжает писать в FD
`1`, но данные оказываются в файле:

```bash
python3 -c 'print("Harbor started")' > harbor.out
```

Знак `>` просит shell открыть `harbor.out`, связать с ним stdout будущего
процесса и только затем запустить Python. Код Python не знает имя файла и
ничего не меняет.

stdout и stderr можно развести:

```bash
python3 -c 'import sys; print("ok"); print("warning", file=sys.stderr)' \
  > normal.out 2> diagnostic.err
```

Здесь `>` относится к FD `1`, а `2>` — к FD `2`. Раздельные каналы нужны,
чтобы данные можно было передать следующей программе, а диагностику всё
равно увидеть или сохранить отдельно. Если приложение пишет обычный JSON и
traceback в один поток без договора, автоматическая обработка результата
ломается.

## «Всё является файлом» — полезно, но не буквально

Unix объединяет многие объекты тем, что процесс получает FD и использует
похожие операции: читать, писать, закрывать, ждать готовности. В таблице
могут находиться:

- обычный файл;
- терминал или устройство;
- directory FD для некоторых системных операций;
- read/write-концы pipe;
- socket;
- специальные Linux-объекты вроде `eventfd`.

Но socket не превращается в файл на диске, а pipe не получает обычную
позицию, которую можно произвольно перематывать. Общий интерфейс не стирает
семантику ресурса. Правильная версия лозунга: «многие Unix-ресурсы доступны
через FD и общий набор операций».

## Pipe: два FD и буфер ядра

Pipe соединяет stdout одной программы со stdin другой. У него два конца:
один для записи, другой для чтения.

```text
Python process                 kernel pipe                 wc process

FD 1 ── write ──▶ [ A\nB\nC\n buffered bytes ] ── read ──▶ FD 0
```

Сначала предскажите число строк, затем выполните:

```bash
python3 -c 'print("A"); print("B"); print("C")' | wc -l
```

Ожидаемый результат:

```text
3
```

Shell создаёт pipe и процессы, связывает stdout Python с write-концом, а
stdin `wc` — с read-концом. Родительские лишние концы должны быть закрыты:
иначе читатель может не увидеть конец потока и продолжит ждать, потому что
где-то всё ещё существует открытый write-end.

Pipe не обязан передавать весь вывод одним куском. Запись и чтение идут
порциями, а вместимость буфера конечна. Если читатель медленный и буфер
заполнен, запись тоже может заблокироваться. Это прямой мост к следующей
главе: блокироваться может не только чтение без данных, но и запись без
свободного места.

## Сокет — будущий FD Harbor

В M4b сервер создаст socket системным вызовом. Ядро вернёт процессу новый
FD, например `5`. Через него сервер будет принимать соединения и читать
байты запроса.

```text
Harbor worker
table FD:
  0 → terminal input
  1 → log output
  2 → error output
  5 → listening socket
  7 → accepted client socket
```

Номера условны и могут меняться. Важна модель:

1. socket — объект ядра;
2. процесс обращается к нему через FD;
3. если байтов пока нет, обычное блокирующее чтение ждёт;
4. Linux умеет сообщать о готовности многих FD — на этом позже вырастет
   event loop.

Пока не нужно знать TCP handshake и `asyncio`. Достаточно связать будущую
сеть с уже знакомой таблицей процесса, а не считать её отдельной магией
фреймворка.

## Утечки и владение

У процесса есть мягкий и жёсткий лимит числа FD. Посмотреть текущий мягкий
лимит shell можно командой:

```bash
ulimit -n
```

Большой лимит не исправляет утечку, а только откладывает отказ. Для каждого
открытого ресурса нужен ответ на вопрос «кто и когда закрывает?».

В Harbor правила могут быть разными:

- маленький конфигурационный файл — `with open(...)` внутри функции;
- лог — долго живущий обработчик, который закрывается при остановке
  приложения;
- клиентское соединение — закрывается после ответа или по договору
  keep-alive;
- пул БД — владеет несколькими соединениями и закрывает их при shutdown.

Если закрыть FD слишком рано, следующий код получит ошибку. Если не закрыть
никогда, процесс исчерпает таблицу. Владение ресурсом — часть контракта,
а не уборка «когда-нибудь сборщиком мусора».

## Harbor и интервью

- FD — индекс в таблице конкретного процесса; номер сам по себе ничего не
  говорит без PID.
- `0`, `1`, `2` — stdin, stdout, stderr по соглашению; shell может
  перенаправить их до запуска Harbor.
- `with` фиксирует владельца и срок жизни короткого файлового ресурса.
- Pipe связывает два процесса через два конца и буфер ядра.
- Сокет позже займёт обычную строку таблицы FD, хотя его семантика не равна
  дисковому файлу.
- Утечка файлов и утечка соединений в итоге расходуют один класс
  процессного ресурса — дескрипторы.

## Частые ошибки

- Называть FD самим файлом или путём.
- Считать номера FD глобально уникальными.
- Полагаться на то, что первый открытый файл всегда получит номер `3`.
- Забывать, что номер переиспользуется после `close`.
- Смешивать stdout и stderr, а затем пытаться передать данные по pipe.
- Повторять «всё файл» так, будто socket хранится на диске и имеет offset.
- Надеяться, что сборщик мусора вовремя закроет любой долгоживущий ресурс.
- Повышать `ulimit`, не устраняя утечку.

## Мини-голос

> FD — маленький номер в таблице конкретного процесса.
> Запись ведёт к открытому объекту ядра; сам номер не является файлом.
> FD 0, 1 и 2 по соглашению означают stdin, stdout и stderr, но shell может
> перенаправить их.
> Pipe соединяет write-end одного процесса с read-end другого.
> Socket тоже будет FD, а незакрытые файлы и соединения могут исчерпать
> общий лимит дескрипторов.
