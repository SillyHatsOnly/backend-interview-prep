## Что сдать

Один каталог или документ с пятью видами материала:

1. краткая карта для устного ответа;
2. два маленьких Python-скрипта, которые вы набрали сами;
3. точные команды опытов и только важные фрагменты вывода;
4. прогнозы **до** запуска и объяснения **после**;
5. короткий рассказ о запросе Harbor на уровне процесса, FD и ожидания.

Для каждого опыта используйте прикладной цикл M0.5:

```text
вопрос → прогноз → безопасная команда → наблюдение → объяснение расхождения
```

Не сдавайте необъяснённый дамп `strace`, скрин всего `htop` или текст,
сгенерированный без живого запуска. В выводе скройте имена пользователя,
домашние пути и любые данные окружения, которые не нужны для ответа.

## Задание 1. Карта ОС вслух *(обязательно, low)*

Запишите аудио на 4–6 минут или проведите ответ на ревью вживую. До записи
разрешён план из десяти коротких опорных фраз, но не полный текст для
чтения.

Начните с команды:

```text
python3 harbor.py
```

И свяжите в одном рассказе:

- программа и процесс;
- PID и PPID;
- изолированное виртуальное адресное пространство;
- stack и heap без фразы «все локальные объекты Python лежат на стеке»;
- таблица FD и номера `0`, `1`, `2`;
- процесс и поток;
- running, runnable и waiting;
- блокирующее чтение;
- один Harbor сейчас и несколько worker-процессов позже;
- socket как будущий FD, без ухода в TCP и HTTP.

Обязательная концовка: объясните, почему блокирующий вызов останавливает
текущий поток, но не обязан занимать CPU и не останавливает другие
процессы.

**Сдать:** опорный план и аудио/живой ответ. Не сдавайте пересказ словаря по
пунктам: между понятиями должна быть причинная связь.

## Задание 2. Жизнь одного процесса *(обязательно, medium)*

Используйте свой `sleep_probe.py` из
[лаборатории](./05_linux_lab.md). Перед каждым запуском запишите прогноз:
какими будут отношение PID/PPID, состояние, CPU и судьба `/proc/PID` после
завершения.

Нужно самостоятельно выполнить и сохранить ключевые строки:

```bash
python3 sleep_probe.py 60
ps -o pid,ppid,stat,etime,%cpu,%mem,comm,args -p PID
top -p PID
grep -E '^(Name|State|Pid|PPid|Threads|VmSize|VmRSS):' /proc/PID/status
ls -l /proc/PID/fd
```

В командах замените `PID` своим числом. Можно положить его в переменную
shell, как в лаборатории, но в отчёте должно быть видно, как вы проверили,
что номер всё ещё относится к вашему скрипту.

После завершения повторите `ps -p PID` и обращение к `/proc/PID`. Объясните:

1. почему во время `sleep` процесс жив, хотя почти не использует CPU;
2. почему `VmSize` и `VmRSS` различаются;
3. почему исчезновение `/proc/PID` связано с жизненным циклом;
4. почему один PID без `args` недостаточен для безопасной диагностики;
5. чем увиденное состояние отличается от zombie.

**Сдать:** команды, до пяти строк каждого полезного вывода и 8–12
предложений объяснения. Полный экран `top` не нужен.

## Задание 3. FD и блокирующий `read` *(обязательно, medium)*

Используйте свой `read_probe.py`. Сначала запустите его обычно и оставьте на
приглашении ввода. Во втором терминале исследуйте процесс:

```bash
ps -o pid,ppid,stat,%cpu,comm,args -p PID
readlink /proc/PID/fd/0
readlink /proc/PID/fd/1
readlink /proc/PID/fd/2
lsof -a -p PID -d 0,1,2
```

До команд нарисуйте ожидаемую таблицу из трёх FD. После команд исправьте
рисунок по факту.

Затем запустите тот же скрипт под трассировкой:

```bash
strace -tt -T -e trace=read,write -o read.trace python3 read_probe.py
```

Подождите несколько секунд, введите короткий вымышленный id комнаты и
найдите в trace чтение из FD `0`. Не сдавайте весь файл.

Ответьте:

1. Какой ресурс стоял за FD `0`?
2. Какой поток остановился на `read`?
3. Почему `%CPU` оставался малым?
4. Что сделало поток runnable?
5. Почему FD `0` другого процесса не обязан вести к тому же ресурсу?
6. Как socket Harbor позже попадёт в ту же модель?

**Сдать:** схема FD до/после наблюдения, команды, одна–три строки trace и
ответы своими словами. После разбора удалите trace, если он содержит
введённые данные.

## Задание 4. Цена копии списка *(обязательно, medium)*

Напишите вручную `memory_probe.py`. Он должен:

1. напечатать PID;
2. создать список из `200_000` ссылок на неизменяемое значение;
3. остановиться на `input`, чтобы вы сняли `VmRSS`;
4. сделать поверхностную копию списка;
5. снова остановиться на `input`;
6. проверить через `is`, являются ли внешний список и один вложенный объект
   общими или разными.

Сначала используйте `200_000`, а не огромный размер. Не пытайтесь вызвать
OOM. Если разница плохо видна из-за аллокатора и округления страниц,
увеличивайте размер осторожно и запишите, почему это сделали.

В другом терминале до и после копии выполните:

```bash
grep -E '^(VmSize|VmRSS):' /proc/PID/status
```

До запуска оцените:

- время копирования через `n`;
- дополнительную память через `n`;
- что именно останется общим;
- почему RSS может измениться не ровно на вашу арифметическую оценку.

После опыта объясните наблюдение. Отдельно напишите, почему такая копия не
синхронизирует каталоги двух worker-процессов Harbor и почему
`copy.deepcopy()` не является правильным ответом на межпроцессное
состояние.

**Сдать:** код, два снимка памяти, прогноз и 8–12 предложений разбора.
Числа на конкретной машине не считаются универсальной нормой.

## Задание 5. Один запрос Harbor *(обязательно, текст)*

Напишите 14–20 предложений и одну ASCII-схему на тему:

> Что происходит на уровне процесса и FD, когда Harbor обрабатывает один
> запрос бронирования?

Граница рассказа:

- Harbor пока один процесс с одним основным потоком;
- будущий сервер получает запрос через socket FD;
- Python-код проверяет доменное правило в памяти процесса;
- обращение к Postgres позже идёт через другой socket FD;
- блокирующее ожидание ответа БД останавливает текущий поток;
- во время ожидания CPU может исполнять другие процессы;
- после готовности поток снова становится runnable;
- ответ записывается в клиентский socket;
- FD закрывается или сохраняется по явному договору;
- несколько process workers имели бы отдельную Python-память;
- общая бронь не должна жить только в глобальном `dict`.

Не описывайте TCP handshake, HTTP-парсер, `asyncio` API и транзакции: этих
слоёв ещё не было. Если упоминаете их, обозначьте как следующий модуль, а
не как уже разобранную механику.

**Сдать:** текст и схему. В каждом предложении должно быть понятно, кто
действует: Python-код, поток, процесс, ядро или внешний ресурс.

## Задание 6. Разбор чужой карты *(обязательно)*

Коллега объяснил систему так:

> Worker — это поток, у каждого потока своя память. FD — глобальный номер
> файла во всей Linux. `sleep(5)` пять секунд занимает ядро CPU. Два
> worker-процесса видят один глобальный список Python, потому что запущены
> из одного файла. Если процесс имеет состояние `S`, это zombie. Socket к
> файловым дескрипторам не относится.

Не запускайте поиск по интернету до первого разбора.

1. Разбейте текст на отдельные проверяемые утверждения.
2. Для каждого неверного утверждения назовите нарушенную границу.
3. Перепишите объяснение в 8–12 предложениях.
4. К трём исправлениям приложите наблюдение из своих заданий: команду и
   одну строку вывода.
5. Отметьте один тезис, который нельзя полностью проверить уже выполненными
   опытами, и скажите, какой безопасный опыт или следующий модуль нужен.

**Сдать:** комментарии к исходному тексту и исправленную версию. Ответ
«всё неверно» без механики не принимается.

## Задание 7. Hard · pipe не заканчивается

Два процесса соединены pipe. Писатель уже отправил данные и завершился, но
читатель продолжает ждать конец потока. Известно, что управляющий процесс
случайно оставил у себя открытым ещё один write-end.

Нарисуйте:

- три процесса;
- таблицы FD;
- оба конца pipe;
- какие записи должны закрыться после запуска детей.

Объясните, почему отсутствие новых байтов ещё не означает EOF и какое
закрытие изменит ситуацию. Затем предложите план диагностики через
`/proc/PID/fd` и `lsof`, но не создавайте сложный стенд автоматически.

Вернитесь после обязательных заданий. Это проверка владения FD, а не знания
редких флагов shell.

## Задание 8. Hard · процессы, память и бюджет workers

Представьте, что один прогретый worker Harbor показывает примерно
`VmRSS = 180 MiB`. Команда запускает восемь process workers. Нельзя просто
умножить число и объявить точный итог: часть страниц может быть общей,
copy-on-write меняется после записей, а RSS разных процессов может
двойным счётом учитывать shared pages.

Составьте план измерения:

1. какие PID собрать;
2. какие поля `/proc` снять до и после реального запроса;
3. почему одного `VIRT` мало;
4. как отличить рост одного worker от умножения числа workers;
5. какой безопасный предел остановки задать, чтобы не проверять гипотезу
   через настоящий OOM.

Код production-сервера не нужен. Нужен честный план эксперимента и список
неопределённостей.

## Задание 9. Hard · диагностировать `Z`, не создавая zombie

В инциденте `ps` периодически показывает дочерние процессы со статусом `Z`
и пометкой `<defunct>`.

Напишите порядок рассуждения:

1. что ребёнок уже успел сделать;
2. какая минимальная запись ещё хранится;
3. чья обязанность не выполнена;
4. какие PID и PPID надо связать;
5. почему `kill -9` по zombie не является лечением;
6. что искать в коде или менеджере процессов.

Не создавайте zombie на основной машине ради доказательства. Здесь
проверяется модель жизненного цикла, а не трюк с `fork`.

## Когда пакет готов к ревью

- [ ] Я различаю программу, процесс и поток без телеграфа из терминов.
- [ ] Я объясняю, почему два process workers не делят обычный Python-список.
- [ ] Я не называю виртуальный адрес физическим и не приравниваю `VIRT` к
      RAM.
- [ ] Я объясняю поверхностную копию ссылками и ценой O(n).
- [ ] Я определяю FD как индекс таблицы конкретного процесса.
- [ ] Я могу показать stdin/stdout/stderr через `/proc` и `lsof`.
- [ ] Я показываю блокирующий `read` через `strace` и не говорю, что он
      постоянно ест CPU.
- [ ] Я отличаю `S` от `Z`.
- [ ] Рассказ Harbor не уходит в ещё не пройденные TCP, HTTP и `asyncio`.
- [ ] В отчёте есть прогнозы, наблюдения и объяснения, а не только вывод
      команд.
