# 02 · Память процесса: адреса, объекты и копии

**Мост:** [предыдущая глава](./01_process.md) провела границу процесса:
worker не читает Python-словарь соседа напрямую. Теперь разберём, из чего
состоит «своя память» и почему адрес, видимый программе, не равен ячейке
RAM. Дальше увидим ещё одну таблицу процесса — файловые дескрипторы.

**Вопрос сюжета:** где живут Python-объекты, что именно копирует
`rooms.copy()` и почему безобидная копия большого списка может приблизить
worker Harbor к OOM?

### С собеседований

Спрашивают: «Стек и куча — в чём разница?», «Что такое virtual memory?»,
«Где лежит локальная переменная Python?», «Поверхностная и глубокая копия?»
и «Откуда берётся OOM?». Опасный ответ механически переносит модель C в
Python: «локальное всегда на стеке, объект всегда в куче». В CPython имя в
локальной области обычно хранит ссылку, а сам Python-объект управляется
интерпретатором и живёт в выделенной ему динамической памяти.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| виртуальная память | virtual memory | Адреса, которые видит процесс; ядро и CPU переводят их в физические страницы или другое хранилище |
| адресное пространство | virtual address space | Допустимая для процесса карта виртуальных адресов |
| страница | page | Блок фиксированного размера, которым ОС отображает виртуальную память |
| физическая память | physical memory, RAM | Реальные байты оперативной памяти машины |
| resident set, RSS | resident set size | Страницы процесса, которые сейчас находятся в RAM; метрика не идеально делит общие страницы |
| стек вызовов | call stack | Цепочка активных вызовов и служебное состояние выполнения каждого потока |
| куча памяти | heap | Область для динамически выделяемых данных; не путать со структурой `heapq` из M3 |
| ссылка | reference | Значение, через которое Python-имя указывает на объект |
| поверхностная копия | shallow copy | Новый внешний контейнер с теми же ссылками на вложенные объекты |
| глубокая копия | deep copy | Попытка рекурсивно скопировать вложенный граф объектов |
| нехватка памяти | out of memory, OOM | Система или лимит процесса не может удовлетворить дальнейшее выделение памяти |

## Одна картинка виртуальной памяти

Два процесса могут использовать одинаковый виртуальный адрес, но попадать в
разные физические страницы. Именно поэтому адрес внутри процесса не является
глобальным номером байта RAM.

```text
worker A, PID 5101                 worker B, PID 5102
вирт. адрес 0x7000                 вирт. адрес 0x7000
        │                                  │
        ▼                                  ▼
   таблица страниц A                  таблица страниц B
        │                                  │
        ▼                                  ▼
  RAM: страница 42                    RAM: страница 91
  bookings = {"A": ...}               bookings = {}

другие виртуальные страницы могут быть:
  • ещё не загружены;
  • отображены из файла или общей библиотеки;
  • временно вытеснены в swap, если он настроен;
  • недоступны процессу.
```

При обращении к адресу CPU проверяет таблицы страниц. Если отображение
разрешено, получается физическая страница. Если страницы пока нет в RAM,
возникает page fault: ядро должно подготовить её, например прочитать из
файла. Если адрес вообще не принадлежит процессу, нативный код получает
ошибку доступа; в Unix это часто заканчивается `SIGSEGV`.

Виртуальная память нужна для изоляции и удобного адресного пространства.
Она не обещает, что весь видимый диапазон уже занимает RAM. Поэтому большое
значение `VIRT` в `top` не равно фактически занятой физической памяти.
Для первого приближения рядом смотрят RSS, а затем уточняют, какие страницы
анонимные, файловые и общие. В лаборатории сравним `VmSize` и `VmRSS` из
`/proc/PID/status`.

## Stack и heap без мифа о Python

На низком уровне у каждого потока есть собственный стек. Он помогает
хранить адрес возврата, регистры и служебное состояние активных вызовов.
Когда функция вызывает другую функцию, цепочка растёт; при возврате
соответствующий кадр больше не активен.

Куча памяти служит для объектов, чей размер и время жизни определяются во
время работы. Python-список может расти, словарь пережить функцию, которая
его создала, а объект передаваться между частями программы. Для таких данных
интерпретатор запрашивает и переиспользует динамическую память.

```text
поток выполнения                    память Python-процесса

стек вызовов                        динамические объекты
┌──────────────────────┐            ┌──────────────────────┐
│ allocate_room()      │  rooms ──▶ │ list                 │
│ name: rooms (ссылка) │            │ [ref, ref]           │
├──────────────────────┤            └────┬───────┬─────────┘
│ handle_request()     │                 │       │
└──────────────────────┘                 ▼       ▼
                                  ┌──────────┐ ┌──────────┐
                                  │ dict A   │ │ dict B   │
                                  └──────────┘ └──────────┘
```

Эта схема намеренно упрощена. Реализация CPython хранит состояние
Python-вызовов не как «все локальные объекты прямо в машинном стеке»:
интерпретатор управляет кадрами и ссылками, а Python-объекты обычно
размещены в управляемой динамической памяти. Детали менялись между версиями
Python. Для backend-разработчика устойчивое правило такое:

- имя — не коробка со всем объектом, а связь с объектом;
- локальность имени не доказывает физическое размещение объекта в стеке;
- пока на объект остаются ссылки, он может жить после возврата из функции;
- каждый поток имеет свою цепочку выполнения, но потоки процесса могут
  ссылаться на одни и те же объекты.

### Рекурсия и стек

Глубокая рекурсия увеличивает цепочку активных вызовов и расход памяти.
CPython обычно останавливает её исключением `RecursionError` на настроенном
пределе раньше, чем бесконтрольно исчерпается машинный стек. Увеличивать
предел только ради обхода длинной внешней цепочки рискованно: алгоритм всё
равно хранит все незавершённые вызовы. В M3 поэтому для графа неизвестной
глубины использовали явный список-стек.

## Python-имя не копирует объект

Рассмотрим две комнаты:

```python
rooms = [
    {"id": "A", "capacity": 4},
    {"id": "B", "capacity": 8},
]

alias = rooms
copied = rooms.copy()
```

После этих строк отношения выглядят так:

```text
rooms ───┐
alias ───┴──▶ list L1 ──▶ dict A
                     └──▶ dict B

copied ──────▶ list L2 ──▶ dict A
                     └──▶ dict B
```

`alias = rooms` не создаёт новый список: оба имени указывают на `L1`.
`rooms.copy()` создаёт новый внешний список `L2`, но переносит в него те же
ссылки на словари. Поэтому:

```python
assert alias is rooms
assert copied is not rooms
assert copied[0] is rooms[0]

copied.append({"id": "C", "capacity": 2})
assert len(rooms) == 2          # внешний список независим

copied[0]["capacity"] = 6
assert rooms[0]["capacity"] == 6  # вложенный словарь общий
```

Это не странность `copy()`, а точный контракт поверхностной копии. Новый
контейнер позволяет независимо добавлять и удалять ссылки, но не дублирует
весь граф объектов.

---

## Почему «скопировать список» стоит времени и памяти

Пусть в `rooms` находится `n` ссылок. Чтобы построить поверхностную копию,
Python должен:

1. выделить место под новый контейнер;
2. пройти `n` позиций;
3. записать в новые позиции ссылки на прежние объекты;
4. обновить внутренний учёт ссылок.

Значит, копия списка стоит O(n) времени и O(n) дополнительной памяти под
массив ссылок. Вложенные объекты при этом не дублируются. На типичной
64-битной CPython один миллион позиций означает примерно восемь мегабайт
только под новый массив указателей, плюс служебные данные; точное число
зависит от реализации и платформы.

### Разобранный сухой прогон

Для `rooms = [A, B, C]`:

```text
до copy:
rooms → L1 [ref A, ref B, ref C]

шаг 1: выделить L2 на три позиции
copied → L2 [empty, empty, empty]

шаг 2: перенести ссылки
copied → L2 [ref A, ref B, ref C]

после copied.pop():
rooms  → L1 [ref A, ref B, ref C]
copied → L2 [ref A, ref B]

после B["free"] = False через copied:
оба списка по-прежнему ведут к одному изменённому B
```

`copy.deepcopy()` пытается рекурсивно создать независимые вложенные объекты
и ведёт таблицу уже увиденных объектов, чтобы сохранить общие ссылки и
обработать циклы. Его цена зависит уже от всего достижимого графа. Это не
безопасная кнопка «на всякий случай»: копирование большой доменной модели
может быть дорогим, а соединения, locks и файловые объекты вообще не имеют
разумной глубокой копии.

Для Harbor сначала спрашиваем, зачем нужна копия. Если нужен неизменяемый
снимок id комнат, возможно, достаточно `tuple(room["id"] for room in
rooms)`. Если нужна общая истина о бронях между worker, никакая копия
списка задачу не решит — она создаст ещё одну расходящуюся версию.

## `fork` и copy-on-write

После `fork` родитель и ребёнок логически имеют отдельные адресные
пространства, но немедленно копировать все физические страницы дорого.
Linux обычно помечает страницы так, чтобы оба процесса временно читали одни
физические данные. Когда один процесс записывает страницу, ядро создаёт ему
отдельную физическую копию.

```text
сразу после fork:
parent virtual page ─┐
                     ├──▶ одна физическая page, только чтение/COW
child virtual page ──┘

после записи child:
parent virtual page ─────▶ старая физическая page
child virtual page  ─────▶ новая физическая page
```

Это объясняет, почему pre-fork сервер может сначала выглядеть экономно, а
после прогрева и изменений память workers растёт. Copy-on-write не делает
обычный Python-словарь общим: изменения ребёнка как раз уходят в его
собственные страницы и не появляются у родителя.

## От выделения памяти до OOM

Python запрашивает память у своего аллокатора, тот при необходимости — у
ОС. Освобождённый Python-объект не обязан немедленно уменьшить RSS:
интерпретатор может оставить блок для будущих объектов, а ОС управляет
страницами крупнее одного объекта.

Нехватка памяти может проявиться несколькими путями:

- конкретное выделение не удалось, и Python поднял `MemoryError`;
- процесс достиг лимита контейнера или cgroup и был завершён;
- вся система оказалась под давлением памяти, и Linux OOM killer выбрал
  процесс-жертву;
- активное вытеснение в swap не убило процесс, но сделало сервис очень
  медленным.

Нельзя обещать, что приложение всегда успеет поймать `MemoryError`. При
системном OOM процесс могут завершить извне. И нельзя считать, что OOM
killer обязательно выберет «самый большой процесс»: выбор зависит от
оценки ядра и настроек.

### Сценарий Harbor

Один worker получает каталог из миллиона ссылок и на каждый запрос делает
две временные копии. Даже поверхностные копии добавляют два больших массива
ссылок. Если workers восемь и запросы пересекаются во времени, цена
умножается. Проблема появилась не потому, что `list.copy()` «плохой», а
потому, что архитектура не сформулировала срок жизни снимка и число
одновременных копий.

При диагностике нужны три вопроса:

1. Что растёт: число объектов, размер контейнера или количество процессов?
2. Рост временный и память переиспользуется или ссылки удерживаются
   навсегда?
3. Какой лимит действует: память машины, контейнера или самого процесса?

## Harbor и интервью

- Локальное имя Python обычно держит ссылку; оно не встраивает весь объект
  в машинный стек.
- Поверхностная копия списка создаёт O(n) новых позиций, но сохраняет ссылки
  на вложенные объекты.
- Восемь workers означают восемь независимых куч Python, даже если
  copy-on-write сначала скрыл часть физической цены.
- `VIRT` показывает адресное пространство, а не обещание «столько RAM уже
  занято».
- OOM диагностируют вместе с лимитами, числом процессов, RSS и сроком жизни
  объектов.

## Частые ошибки

- Путать heap памяти со структурой данных «куча» из `heapq`.
- Говорить «все локальные переменные Python лежат на стеке».
- Считать виртуальный адрес физическим адресом RAM.
- Приравнивать `VIRT` к реальному потреблению памяти.
- Называть поверхностную копию O(1), потому что вложенные объекты общие.
- Использовать `deepcopy` как универсальную изоляцию состояния.
- Думать, что copy-on-write превращает память forked workers в общую.
- Обещать, что любой OOM проявится как перехватываемый `MemoryError`.

## Мини-голос

> Процесс видит виртуальные адреса, а ядро отображает страницы в RAM или
> другое хранилище.
> У потока есть стек вызовов, но Python-имя обычно ссылается на объект,
> которым управляет интерпретатор.
> Поверхностная копия списка создаёт новый массив ссылок за O(n), а
> вложенные объекты остаются общими.
> После `fork` copy-on-write экономит физические страницы до первой записи,
> но логическая память процессов всё равно раздельна.
> При OOM смотрю на RSS, лимиты, число workers и срок жизни объектов.
