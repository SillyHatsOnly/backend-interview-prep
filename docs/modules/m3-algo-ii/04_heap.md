# 04 · Куча и приоритетная очередь

**Мост:** backtracking из [предыдущей главы](./03_backtracking.md) перебирал
много возможных наборов. Здесь задача другая: набор уже известен, но он
меняется со временем, и после каждого изменения надо быстро узнать один
лучший текущий элемент. В Harbor это ближайшее окончание активной брони или
самая важная заявка ожидания.

**Вопрос сюжета:** как много раз забирать «следующий по приоритету», не
сортируя всю коллекцию после каждого добавления?

### С собесов

Спрашивают: «Что гарантирует heap?», «Сколько стоят push, pop и peek?»,
«Почему это не отсортированный массив?» и «Когда обычная сортировка лучше?».
Типичный провал — считать, что внутренний список кучи полностью упорядочен,
и читать `heap[1]` как второй минимум.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| приоритетная очередь | priority queue | Интерфейс: добавить элемент и забрать самый приоритетный |
| куча | heap | Обычная реализация приоритетной очереди в виде дерева внутри массива |
| мин-куча | min-heap | Ключ родителя не больше ключей его детей; минимум находится в корне |
| ключ приоритета | priority key | Часть элемента, по которой решается, кто выходит первым |
| добавить | push | Положить элемент и восстановить свойство кучи |
| извлечь | pop | Забрать корень и восстановить свойство кучи |
| посмотреть вершину | peek | Прочитать корень, не удаляя его |
| просеивание | sift up / sift down | Обмены с родителем или ребёнком после изменения |

Приоритетная очередь — это обещание поведения, а куча — способ выполнить
это обещание. Такой же интерфейс можно построить на отсортированном списке,
но цены операций будут другими.

---

## Под капотом: дерево без объектов-узлов

Мин-куча хранится в обычном массиве. Для индекса `i`:

```text
родитель:        (i - 1) // 2
левый ребёнок:   2 * i + 1
правый ребёнок:  2 * i + 2
```

Например, ключи массива `[610, 620, 630, 700, 650]` представляют дерево:

```text
                 610 (индекс 0)
               /                 \
       620 (индекс 1)       630 (индекс 2)
        /          \
 700 (индекс 3) 650 (индекс 4)
```

Каждый родитель не больше своих детей. Но `650` стоит после `700` в массиве,
и это нормально: между разными ветками порядка нет. Куча хранит ровно
столько порядка, сколько нужно для быстрого минимума, а не для печати всей
коллекции по возрастанию.

### Добавление

Новый элемент ставят в конец массива, чтобы дерево осталось заполненным по
уровням. Затем сравнивают с родителем и поднимают, пока свойство кучи не
восстановится. Высота дерева O(log n), значит `push` стоит O(log n).

### Извлечение

Минимум лежит в индексе 0. После его удаления последний элемент переносят в
корень и опускают, каждый раз меняя с меньшим ребёнком. Этот путь тоже не
длиннее высоты: `pop` стоит O(log n). Простое чтение `heap[0]` — O(1).

Построить кучу из готового списка через `heapify` можно за O(n). Это не
серия независимых сортировок: просеивание начинается снизу, а большая часть
узлов находится близко к листьям и почти не двигается.

## Интуиция Harbor: какая бронь закончится следующей

Пусть активная бронь хранится как `(end_minute, room_id)`, где
`end_minute` — число минут от полуночи:

```text
room A заканчивает в 10:30 → (630, "A")
room B заканчивает в 10:10 → (610, "B")
room C заканчивает в 10:20 → (620, "C")
```

Нас интересует не полный календарь, а один вопрос, который повторяется:
«какая комната освободится следующей?» Ключ — время окончания, поэтому
мин-куча сразу держит нужную бронь в корне.

```python
import heapq


active_bookings = [
    (630, "A"),
    (610, "B"),
    (620, "C"),
]
heapq.heapify(active_bookings)

assert active_bookings[0] == (610, "B")  # только посмотреть
assert heapq.heappop(active_bookings) == (610, "B")

heapq.heappush(active_bookings, (615, "D"))
assert heapq.heappop(active_bookings) == (615, "D")
assert heapq.heappop(active_bookings) == (620, "C")
```

После `heapify` нельзя проверять весь внутренний список на равенство
отсортированному. Контракт обещает только минимум в `[0]` и правильный
порядок последовательных `heappop`.

## Разобранный сухой прогон

Добавляем три брони по одной:

```text
push (630, A)
[(630, A)]

push (610, B)
append: [(630, A), (610, B)]
подъём: [(610, B), (630, A)]

push (620, C)
append: [(610, B), (630, A), (620, C)]
родитель 610 меньше — обмен не нужен
```

Теперь извлекаем ближайшее окончание:

```text
pop → (610, B)
последний элемент (620, C) идёт в корень:
[(620, C), (630, A)]
```

Приходит новая активная бронь `(615, D)`:

```text
append: [(620, C), (630, A), (615, D)]
615 меньше родителя 620:
[(615, D), (630, A), (620, C)]
```

Следующий `pop` вернёт `D`, хотя она пришла позже. Это и есть отличие
приоритетной очереди от обычной FIFO-очереди: порядок определяется ключом,
а не временем вставки.

## Несколько полей приоритета

Для очереди ожидания Harbor правило может звучать так:

1. меньший `priority` важнее;
2. при равенстве раньше пришедшая заявка важнее;
3. при полном равенстве нужен устойчивый технический порядок.

Кортеж Python сравнивается слева направо, поэтому правило кодируется прямо:

```python
waiting: list[tuple[int, int, str]] = []

heapq.heappush(waiting, (2, 545, "req-2"))
heapq.heappush(waiting, (1, 550, "req-3"))
heapq.heappush(waiting, (1, 540, "req-1"))

assert heapq.heappop(waiting) == (1, 540, "req-1")
assert heapq.heappop(waiting) == (1, 550, "req-3")
```

Если первые поля совпали, Python сравнит следующее. Поэтому в куче с
объектами, которые нельзя сравнивать между собой, нужен числовой счётчик или
другой уникальный tie-breaker до самого объекта. Иначе редкая ничья дойдёт
до сравнения payload и завершится `TypeError`.

Для максимального приоритета часто хранят отрицательный числовой ключ:
`(-score, arrived_at, request_id)`. Знак меняет порядок чисел, но не смысл
остальных полей. Это надо отразить в имени или комментарии, иначе «меньше»
и «важнее» быстро перепутаются.

## Куча против сортировки и других структур

| Сценарий | Что проще выбрать | Почему |
|----------|-------------------|--------|
| Один раз найти минимум | `min(items)` | Один проход O(n), структуру поддерживать не надо |
| Один раз получить весь порядок | `sorted(items)` | O(n log n), результат действительно полностью отсортирован |
| Много `push` и `pop` вперемешку | куча | Обе изменяющие операции O(log n), вершина O(1) |
| Строго обслуживать по приходу | `deque` | Нужна FIFO-очередь, приоритет отсутствует |
| Часто искать и удалять произвольный id | словарь или составная структура | Куча не даёт быстрого поиска элемента внутри |
| Держать только лучшие `k` из потока | куча размера `k` | O(n log k) без полной сортировки |

Куча не подходит для экрана «покажи все ожидания по порядку»: внутренний
массив не отсортирован. Можно последовательно извлечь все элементы, но это
разрушит очередь; можно сортировать копию, но это отдельная операция
O(n log n).

`heapq` также не умеет быстро удалить произвольную заявку или изменить её
приоритет по `request_id`: сначала элемент пришлось бы искать за O(n).
В проде часто совмещают кучу со словарём актуальных заявок и лениво
пропускают устаревшие записи при извлечении. Это уже отдельный контракт,
а не бесплатное свойство heap.

---

## Когда куча не нужна

- В каталоге двадцать комнат и минимум спрашивают один раз — используйте
  `min`, а не стройте инфраструктуру.
- Все заявки уже собраны и нужен полный отчёт — `sorted` яснее.
- Следующим обязан выйти самый ранний **по приходу**, без других правил —
  нужна `deque`.
- Надо проверять наличие `request_id` — это вопрос к `set`/`dict`, а не к
  корню кучи.
- Нужно выбрать одну комнату по вместимости одним проходом — куча не убирает
  необходимость проверить кандидатов.

Структуру выбирают по повторяющейся операции. Слово «приоритет» в описании
продукта ещё не доказывает, что нужна куча.

## Упражнение в главе

Активные брони приходят в таком порядке:

```text
(660, "A"), (625, "B"), (640, "C"), (620, "D")
```

1. Нарисуйте массив кучи после каждого `push`.
2. Выполните два `pop` рукой и назовите освобождённые комнаты.
3. После этого добавьте `(630, "E")` и назовите следующую вершину, не
   сортируя весь список.
4. Скажите вслух, почему `heap[1]` не обязана быть второй по времени бронью.

Самопроверка последовательности извлечений: сначала `D` (620), затем `B`
(625), после добавления — `E` (630). Конкретное расположение остальных
элементов может отличаться, если свойство кучи сохранено.

## Harbor и интервью

- Активные брони по времени окончания: следующей освобождается вершина
  мин-кучи.
- Ожидающие запросы по бизнес-приоритету и времени прихода: кортежный ключ.
- Топ-k комнат из большого потока: ограниченная куча, если полный порядок не
  нужен.
- На интервью сначала назовите повторяющиеся операции, затем цены
  `peek O(1)`, `push/pop O(log n)`, память O(n).
- Если нужен один минимум или весь отсортированный результат, прямо скажите,
  почему `min` или `sorted` проще.

## Частые ошибки

- Считать массив кучи полностью отсортированным.
- Читать `heap[1]` как второй минимум.
- Забыть дополнительное поле для ничьей и получить сравнение несравнимых
  объектов.
- Изменить ключ элемента прямо внутри списка: свойство кучи само не
  восстановится.
- Использовать кучу там, где требуется FIFO-порядок BFS.
- Говорить «куча O(log n)», не уточнив операцию: просмотр вершины O(1),
  построение через `heapify` O(n).

## Мини-голос

> Приоритетная очередь отвечает, кто должен выйти следующим; куча реализует
> этот контракт.
> В мин-куче гарантирован минимум в корне, но весь массив не отсортирован.
> `peek` стоит O(1), `push` и `pop` — O(log n), `heapify` — O(n).
> В Harbor ключом может быть ближайшее окончание брони или пара
> «приоритет, время прихода».
> Для одного минимума беру `min`, для полного порядка — `sorted`.
