# 01 · Граф площадки

**Мост:** список `MeetingRoom` из M1 — плоский каталог. Пока запрос звучит
как «найти комнату достаточной вместимости», списка хватает. Но вопрос
«через какие зоны пройти от ресепшена до C» зависит уже не от свойств одной
комнаты, а от связей между площадками. Здесь мы выбираем модель этих связей;
в следующей главе начнём по ней ходить.

**Вопрос сюжета:** что хранить, чтобы «кто сосед этой площадки?» было прямым
вопросом к данным, а не новым проходом по всему зданию?

### С собесов

Обычно спрашивают: «Что такое граф?», «Чем дерево отличается от графа?»,
«Список смежности или матрица?» и «Какая цена хранения?». Проверяют не
знание всех названий рёбер, а умение связать представление с запросом. Ответ
«матрица быстрее» неполон: надо назвать, **какой** запрос быстрее и сколько
памяти за это заплачено.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| граф | graph | Набор объектов и явно заданных связей между ними |
| вершина | vertex / node | Объект, который участвует в связях: зона, крыло, комната |
| ребро | edge | Одна связь: «есть проход» или «содержит» |
| ориентированное ребро | directed edge | Связь со стрелкой: из A в B можно, обратно не обещано |
| неориентированное ребро | undirected edge | Двусторонняя связь: проход A—B работает в обе стороны |
| сосед | neighbor | Вершина, соединённая с текущей одним ребром |
| степень вершины | degree | Число рёбер у вершины; для ориентированного графа входящие и исходящие считают отдельно |
| путь | path | Последовательность вершин, где каждая соседняя пара соединена ребром |
| цикл | cycle | Путь, который возвращается в начальную вершину |
| список смежности | adjacency list | Для каждой вершины храним только её соседей |
| матрица смежности | adjacency matrix | Таблица V×V: ячейка отвечает, есть ли ребро между парой вершин |
| дерево | tree | Связный граф без циклов; между двумя вершинами ровно один простой путь |

Буквой `V` дальше обозначаем число вершин, `E` — число рёбер. Это важно
произносить: фраза O(V + E) без определения букв не объясняет цену решения.

---

## Сначала смысл связи, потом контейнер

Граф — не обязательно особый класс или рисунок с кружками. Это способ
ответить на два вопроса:

1. Что в нашей задаче считается вершиной?
2. Что именно означает одно ребро?

Для плана коридоров вершина может быть зоной, а не каждой физической дверью.
Ребро означает «между зонами можно пройти напрямую». Если забыть смысл,
легко смешать в одном графе «комната находится в крыле» и «между комнатами
есть дверь». Тогда путь из комнаты к крылу будет выглядеть как физический
проход, хотя это лишь отношение вложенности.

План одного этажа Harbor:

```text
             [C]
              |
[reception]--[A]--[D]
     |        |
     +-------[B]
```

Здесь вершины — зоны, линия — двусторонний проход. Есть цикл
`reception → A → B → reception`. Поэтому алгоритм обхода обязан помнить
посещённые вершины: иначе он сможет ходить по этому треугольнику бесконечно.

Если же моделируем иерархию, рисунок другой:

```text
[floor-1]
├── [wing-A]
│   ├── [room-A1]
│   └── [room-A2]
└── [wing-B]
    └── [room-B1]
```

Это дерево «родитель содержит ребёнка». У каждой вершины, кроме корня, один
родитель, циклов нет. Дерево является частным случаем графа, но дополнительные
гарантии позволяют рассуждать проще.

---

## Список смежности

Для плана этажа естественно хранить словарь `вершина → соседи`:

```python
floor_graph: dict[str, list[str]] = {
    "reception": ["A", "B"],
    "A": ["reception", "B", "C", "D"],
    "B": ["reception", "A"],
    "C": ["A"],
    "D": ["A"],
}
```

У неориентированного графа каждое ребро записано дважды. Проход
`reception—A` должен добавить `A` к соседям `reception` и `reception` к
соседям `A`. Если записать только одну сторону, данные молча превратятся в
ориентированный граф: от ресепшена пройти можно, обратно — нет.

Построим представление из списка уникальных проходов:

```python
def build_undirected_graph(
    vertices: list[str],
    edges: list[tuple[str, str]],
) -> dict[str, list[str]]:
    graph = {vertex: [] for vertex in vertices}

    for left, right in edges:
        graph[left].append(right)
        graph[right].append(left)

    return graph


vertices = ["reception", "A", "B", "C", "D"]
edges = [
    ("reception", "A"),
    ("reception", "B"),
    ("A", "B"),
    ("A", "C"),
    ("A", "D"),
]

assert build_undirected_graph(vertices, edges)["A"] == [
    "reception",
    "B",
    "C",
    "D",
]
```

Отдельный список `vertices` нужен, чтобы не потерять изолированную площадку:
комнату без проходов не встретить ни в одном ребре, но она всё равно является
вершиной графа.

Память списка смежности — O(V + E). Получить всех соседей вершины стоит
O(степень вершины), потому что именно столько ответов надо вернуть. Проверка
конкретного ребра `B in graph["A"]` по списку в худшем случае тоже проходит
всех соседей A. Если такой вопрос задаётся часто, значения можно хранить в
`set`: средняя проверка станет O(1), но порядок соседей исчезнет и контейнер
потребует больше памяти.

## Матрица смежности

Матрица заводит строку и столбец для каждой вершины. Для рисунка выше:

```text
              R  A  B  C  D
reception R   0  1  1  0  0
A             1  0  1  1  1
B             1  1  0  0  0
C             0  1  0  0  0
D             0  1  0  0  0
```

Ячейка `[i][j]` даёт ответ «есть ребро?» за O(1). Но таблица хранит V²
ячеек, включая почти все нули. Для строковых id дополнительно нужен словарь
`id → индекс`, иначе непонятно, какая строка относится к комнате `A`.

Матрица полезна, когда граф **плотный**: рёбер близко к V², часто проверяются
произвольные пары, а набор вершин компактен и стабилен. Например, учебная
задача может разрешать прямой переход почти между каждой парой сервисов.
План здания обычно **разреженный**: у зоны несколько соседей, а не связь со
всеми зонами. Матрица на 10 000 помещений выделит 100 миллионов ячеек ради
небольшого числа проходов.

| Вопрос | Список смежности | Матрица смежности |
|--------|------------------|-------------------|
| Память | O(V + E) | O(V²) |
| Перечислить соседей `v` | O(deg(v)) | O(V), надо просмотреть строку |
| Проверить ребро `u → v` | O(deg(u)) для `list`, в среднем O(1) для `set` | O(1) |
| Когда выбирать | мало рёбер, важны обходы соседей | много рёбер, часты проверки пар |

Матрица не «быстрее вообще». Она покупает быстрый ответ на один вопрос ценой
памяти и более дорогого перечисления соседей.

## Разобранный сухой прогон: строим план

Вход:

```text
вершины: [R, A, B, C]
проходы: [(R, A), (R, B), (A, B), (A, C)]
```

Начинаем со всех вершин и пустых списков:

```text
R: []   A: []   B: []   C: []
```

Добавляем каждый двусторонний проход:

```text
(R, A) → R:[A]       A:[R]       B:[]       C:[]
(R, B) → R:[A,B]     A:[R]       B:[R]      C:[]
(A, B) → R:[A,B]     A:[R,B]     B:[R,A]    C:[]
(A, C) → R:[A,B]     A:[R,B,C]   B:[R,A]    C:[A]
```

Проверки модели:

- у каждого прохода есть обратная запись;
- вершина `C` присутствует, хотя у неё только один сосед;
- сумма степеней `2 + 3 + 2 + 1 = 8` равна удвоенному числу рёбер `2E`.

Последняя проверка работает для неориентированного графа: каждое ребро
вносит по одному в степень двух концов. Если сумма нечётная или не равна
`2E`, построение потеряло одну сторону или добавило лишнюю.

---

## Когда граф не нужен

Если Harbor один раз ищет комнату с `capacity >= guests`, связи между
комнатами не участвуют в ответе. Обычный проход по списку проще и точнее.
Граф окупается, когда сам запрос сформулирован через отношения: достижимость,
число переходов, соседство, зависимости или иерархию.

Нельзя выбирать граф только потому, что домен «похож на сеть». Сначала
назовите вершину и смысл ребра. Если это не помогает ответить на запрос,
структура добавит код, но не добавит информации.

## Упражнение в главе

Даны зоны `R`, `A`, `B`, `C`, `X` и проходы:

```text
R—A, A—B, B—R, B—C
```

1. Нарисуйте граф. Затем запишите список смежности, не потеряв изолированную
   вершину `X`.
2. Скажите вслух, почему для такого плана список смежности разумнее матрицы.
3. Посчитайте `V`, `E`, степени всех вершин и проверьте сумму степеней.
4. Измените смысл прохода на «турникет разрешает движение только слева
   направо». Какие записи исчезнут и почему проверка `2E` больше не подходит?

Самопроверка для исходного графа: `V = 5`, `E = 4`; степени
`R=2`, `A=2`, `B=3`, `C=1`, `X=0`, их сумма равна 8.

## Harbor и интервью

- Иерархия здания — дерево, если у каждого помещения один родитель.
- План двусторонних коридоров — неориентированный граф, где циклы нормальны.
- Односторонние турникеты — ориентированный граф; обратный проход нельзя
  добавлять автоматически.
- Зависимости задач миграции или сервисов тоже образуют граф, хотя на плане
  здания их не видно.
- На интервью сначала проговорите смысл вершины и ребра, затем плотность
  графа и только после этого выбирайте список или матрицу.

## Частые ошибки

- Добавить одну сторону неориентированного ребра и получить другой граф.
- Создавать ключи только из рёбер и потерять изолированные вершины.
- Смешать «содержит» и «есть проход» в одной связи.
- Выбрать матрицу ради O(1), не назвать память O(V²).
- Считать, что дерево и граф — конкурирующие структуры. Дерево — граф с
  дополнительными ограничениями.

## Мини-голос

> Сначала я определяю вершину и смысл ребра.
> Для редкого плана коридоров беру список смежности: O(V + E) памяти.
> Матрица тратит O(V²), зато проверяет конкретное ребро за O(1).
> В неориентированном графе записываю обе стороны и не теряю изолированные
> вершины.
> Граф нужен только тогда, когда запрос действительно зависит от связей.
