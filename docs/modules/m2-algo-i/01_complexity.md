# 01 · Сложность

**Мост:** в M0.5 вы уже оценивали brute. Здесь оценка становится языком: два
решения одной задачи про комнаты сравнивают не «мне так понятнее», а как
растёт работа, когда комнат сто, тысяча, миллион.

**Вопрос сюжета:** почему линейный проход по комнатам для одной брони нормален,
а вложенный проход по всем парам броней — уже нет?

### С собесов

«Какая сложность?», «можно ли быстрее?», «что будет при n = 10^6?». Ждут не
название функции из библиотеки, а порядок роста и где узкое место.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| размер входа | n | Сколько комнат, чисел, символов в этой задаче |
| по времени | time complexity | Сколько шагов делает алгоритм, когда n растёт |
| по памяти | extra space | Сколько новых данных вы заводите сверх самого входа |
| O(…) | Big O | Верхняя оценка роста: «не быстрее, чем такой порядок» в худшем типичном рассказе на собесе |

Big O здесь — грубая линейка, не доказательство из CLRS. Константы и «ровно
сколько тактов» на собесе middle обычно не спрашивают. Спрашивают, удвоится
ли работа при удвоении n, или вырастет вчетверо, или почти не заметите.

---

## Под капотом (модель)

Считайте не строки кода, а **сколько раз вы трогаете элемент**, когда
элементов становится больше.

Один проход по списку комнат: каждая комната один раз. Комнат в 10 раз
больше — работы примерно в 10 раз больше. Это O(n) по времени. Дополнительная
память O(1), если вы не строите второй список, а только помните ответ.

Два вложенных цикла «каждая с каждой»: для каждой комнаты вы снова смотрите
почти все остальные. Рост ближе к n². Сто комнат — около десяти тысяч
сравнений, тысяча — около миллиона. На одной брони в Harbor это ещё терпимо.
На проверке «каждая бронь с каждой» по году истории — уже нет.

Деление пополам на отсортированном списке: каждый шаг выкидывает половину
остатка. Тысяча элементов — порядка десяти шагов, миллион — порядка двадцати.
Это O(log n). Память по-прежнему O(1), если границы — два индекса.

Множество уже виденных чисел: один проход, на каждый элемент проверка «есть
ли дополнение» в среднем за константу. Время O(n), память O(n), потому что
множество хранит до n чисел. Вы меняете время на память. Это нормальная сделка,
её надо назвать вслух.

## Четыре уже знакомые задачи

| Задача | Тупое верное | Уже лучше | Что платим |
|--------|----------------|-----------|------------|
| Пара с суммой k | два цикла, O(n²), память O(1) | один проход и множество, O(n) время и память | память ради второго цикла |
| Скобки | вычёркивать пары снова и снова, хуже линейного | стек, O(n) время и память | стопка открытых скобок |
| Индекс в отсортированном списке | проход с начала, O(n) | деление пополам, O(log n), память O(1) | список обязан быть отсортирован |
| Первая комната с вместимостью | один проход, O(n) | для одной брони часто и есть ответ | быстрее не нужно, пока комнат мало и нет других условий |

Последняя строка важна для Harbor. `allocate` по вместимости — честный
линейный проход. Усложнять его хешем «вместимость → комната» имеет смысл,
когда запрос другой (найти комнату ровно на k человек среди огромного
каталога). Пока запрос «первая, куда гости влезают», O(n) — нормальный
контракт. Сложность — не спорт «всегда O(1)».

---

## Как говорить на собесе

Назовите n своими словами: «n — число комнат». Потом: сколько раз каждая
комната участвует в работе. Потом память: «кроме входа храню множество / два
индекса / ничего». Если улучшение требует сортировки, добавьте её цену:
сортировка сама по себе обычно O(n log n), и она может быть дороже, чем
один линейный проход.
