# 03 · Два указателя и скользящее окно

**Мост:** хеш из [предыдущей главы](./02_hash.md) убирает повторный поиск,
потому что хранит уже просмотренные значения. Если данные упорядочены или
нас интересует непрерывный отрезок, иногда достаточно двух индексов и
нескольких чисел состояния. Дальше мы перейдём к стеку: там состояние тоже
хранится явно, но удалять нужно будет строго последний незавершённый объект.

**Вопрос сюжета:** какое свойство позволяет двигать границы только вперёд и
никогда не начинать поиск заново?

### С собесов

Фразы «два указателя» и «скользящее окно» сами по себе не объясняют решение.
Обычно ждут инвариант: почему после движения одной границы отброшенные
варианты точно не понадобятся. Типичные провалы — применить указатели к
несортированным данным или окно с суммой к числам, среди которых есть
отрицательные.

---

## Словарь

- **Указатель (pointer)** в этой главе — обычный целочисленный индекс, а не
  указатель на память из C.
- **Два указателя (two pointers)** — два индекса, чьё согласованное движение
  исключает уже проверенные варианты.
- **Скользящее окно (sliding window)** — непрерывный полуинтервал
  `[left, right]`, который расширяют справа и при необходимости сжимают
  слева.
- **Инвариант (invariant)** — утверждение, которое остаётся верным перед
  каждой новой итерацией и объясняет корректность движения границ.

Два указателя — широкая идея. Они могут идти навстречу друг другу, как в
задаче о сумме, или в одну сторону, как границы окна. Окно — частный случай,
где между границами лежит текущий непрерывный кандидат на ответ.

---

## Два указателя на отсортированном списке

Пусть список отсортирован по неубыванию и нужно найти два разных элемента
с суммой `target`.

```text
индексы:   0   1   2   3
числа:    [1,  2,  4,  7]      target = 6
           ▲           ▲
         left        right

сумма велика  → right движется влево, берём число меньше
сумма мала    → left  движется вправо, берём число больше
сумма равна   → ответ найден
```

## Под капотом: почему можно отбрасывать варианты

Если `nums[left] + nums[right] < target`, то текущий левый элемент слишком
мал даже в паре с самым большим доступным элементом `nums[right]`. С любым
элементом левее `right` сумма будет не больше. Значит, `nums[left]` уже не
может участвовать в ответе, и `left` безопасно увеличить.

Если сумма больше цели, текущий правый элемент слишком велик даже в паре с
самым маленьким доступным `nums[left]`. Сдвигаем `right` влево. Именно
сортировка делает эти выводы верными. Без неё соседнее число может быть и
меньше, и больше, поэтому направление движения ничем не обосновано.

Инвариант можно произнести так: **если ответ ещё существует, оба его индекса
лежат внутри отрезка от `left` до `right` включительно**. После каждого
сравнения мы удаляем один индекс только вместе с доказательством, что он не
подходит.

Каждая граница проходит список не более одного раза. Всего движений O(n),
дополнительная память O(1), если список уже отсортирован.

### Мини-пример с сухим прогоном

**Вход:** `nums = [1, 2, 4, 7]`, `target = 6`

**Выход:** `(1, 2)`

1. `left = 0`, `right = 3`: `1 + 7 = 8`, сумма велика. Уменьшаем `right`.
2. `left = 0`, `right = 2`: `1 + 4 = 5`, сумма мала. Увеличиваем `left`.
3. `left = 1`, `right = 2`: `2 + 4 = 6`. Возвращаем `(1, 2)`.

Пустой список и список из одного элемента сразу дают `None`, потому что
условие `left < right` не выполняется.

### Отсортированный и неотсортированный вход

Если список уже отсортирован, два указателя дают O(n) времени и O(1)
дополнительной памяти. Если порядок произвольный, есть три разных решения:

1. Два вложенных цикла: O(n²) времени, O(1) памяти.
2. Хеш из прошлой главы: в среднем O(n) времени, O(n) памяти, исходные
   индексы сохраняются естественно.
3. Сортировка и два указателя: O(n log n) времени. Если нужны исходные
   индексы, придётся сортировать пары «значение, исходный индекс».

Поэтому фраза «два указателя лучше хеша» неверна без условий. Приём выигрывает,
когда порядок уже есть, сортировка разрешена или память важнее времени.

## Окно: непрерывный кандидат на ответ

Теперь задача другая: дан список **неотрицательных** чисел. Нужно найти
самый длинный непрерывный кусок, сумма которого не превышает `limit`.

Правый край добавляет новый элемент. После этого возможны два состояния:

```text
sum <= limit     окно допустимо → обновить лучший ответ
sum > limit      окно недопустимо
                       │
                       ▼
                 двигать left и вычитать
                 элементы, пока sum <= limit
```

Инвариант перед обновлением ответа: **текущее окно допустимо, то есть его
сумма не больше лимита**. Правый край расширяет кандидата. Если инвариант
сломался, левый край сжимает окно столько раз, сколько нужно для
восстановления.

```python
def longest_under_limit(nums: list[int], limit: int) -> int:
    left = 0
    total = 0
    best = 0

    for right, value in enumerate(nums):
        total += value

        while left <= right and total > limit:
            total -= nums[left]
            left += 1

        best = max(best, right - left + 1)

    return best
```

### Мини-пример с сухим прогоном

**Вход:** `nums = [2, 1, 1, 3]`, `limit = 4`

**Выход:** `3`, отрезок `[2, 1, 1]`

1. Добавляем `2`: сумма `2`, окно `[0..0]`, лучшая длина `1`.
2. Добавляем `1`: сумма `3`, окно `[0..1]`, лучшая длина `2`.
3. Добавляем `1`: сумма `4`, окно `[0..2]`, лучшая длина `3`.
4. Добавляем `3`: сумма `7`, окно недопустимо. Убираем слева `2`, сумма
   `5`; всё ещё много. Убираем `1`, сумма `4`. Окно `[2..3]` допустимо,
   его длина `2`, лучший ответ остаётся `3`.

В коде есть цикл `while` внутри `for`, но это не квадрат. Каждый элемент
ровно один раз входит через правую границу и не более одного раза выходит
через левую. Обе границы суммарно делают не больше `2n` движений: время
O(n), дополнительная память O(1).

### Почему важны неотрицательные числа

При неотрицательных элементах расширение окна не уменьшает сумму, а удаление
слева не увеличивает её. Поэтому направление исправления однозначно.

Если разрешить отрицательные числа, это свойство исчезнет. Например, окно
с суммой выше лимита могло бы снова стать допустимым после добавления
отрицательного числа справа. Немедленное сжатие выбросит потенциально лучший
ответ. Значит, классическое окно с суммой здесь неприменимо; нужна другая
идея, а не косметическая правка условия.

## Когда выбирать приём

- **Пара в отсортированном списке:** указатели с двух концов, потому что
  знак ошибки суммы подсказывает направление.
- **Непрерывный отрезок с монотонным ограничением:** окно, потому что после
  расширения нарушение можно исправлять движением только левой границы.
- **Точный поиск среди уже виденных на неупорядоченном входе:** хеш.
- **Поиск одного значения в отсортированном списке:** бинарный поиск, потому
  что середина позволяет выбрасывать половину, а не один край.

### Частые ошибки

1. Сдвинуть левую границу окна один раз через `if`, хотя для восстановления
   инварианта нужно несколько сдвигов через `while`.
2. На каждом шаге заново считать `sum(nums[left:right + 1])`. Тогда повторная
   работа возвращает алгоритм к O(n²).
3. Использовать два конца без сортировки и объяснения направления.
4. Назвать окном набор несоседних элементов. Окно всегда является
   непрерывным отрезком входа.

## Применение в Harbor

- Отсортированный список вместимостей позволяет искать пару или согласованно
  двигать границы без множества.
- Непрерывное окно моделирует подряд идущие интервалы календаря, если
  ограничение меняется монотонно при добавлении и удалении элемента.
- После сортировки броней по началу соседние интервалы можно проверять одним
  проходом, не сравнивая каждую бронь с каждой.
- Для исходного `allocate` порядок каталога важнее сортировки, поэтому
  линейный проход остаётся честным решением.

## Мини-голос

> Указатели работают не из-за двух переменных, а из-за порядка данных.
> Я двигаю границу только после доказательства, что отброшенный индекс не нужен.
> Окно хранит непрерывный кандидат и восстанавливает свой инвариант через `while`.
> При неотрицательной сумме оба края идут только вперёд, поэтому время O(n).
> Без сортировки или монотонности этот приём нельзя применять автоматически.
