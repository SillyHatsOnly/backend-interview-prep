# 02 · Массив и хеш

**Мост:** в [главе о сложности](./01_complexity.md) второй цикл в задаче о
паре чисел оказался повторным поиском. Здесь мы заплатим памятью, чтобы
сохранять уже найденные факты и не искать их заново. В следующей главе
посмотрим, когда ту же линейную скорость можно получить без хеша — за счёт
порядка данных.

**Вопрос сюжета:** как запомнить просмотренные комнаты или числа так, чтобы
вопрос «это уже было?» не запускал новый проход по списку?

### С собесов

Обычно спрашивают: «Почему `dict` и `set` работают в среднем за O(1)?»,
«Что такое коллизия?», «Когда взять множество, а когда словарь?». Не нужно
воспроизводить устройство CPython до байта. Нужно связать структуру с
задачей, назвать среднюю и худшую оценки и не забыть цену O(n) по памяти.

---

## Словарь

- **Массив (array)** хранит элементы последовательно. В Python в роли
  динамического массива обычно выступает `list`: доступ по известному
  индексу дешёвый, но поиск неизвестного значения требует прохода.
- **Хеш-таблица (hash table)** превращает ключ в число и по этому числу
  выбирает место для хранения. На ней основаны `dict` и `set`.
- **Хеш-функция (hash function)** получает ключ и выдаёт целое число,
  устойчивое для этого ключа в течение его жизни.
- **Коллизия (collision)** возникает, когда разные ключи претендуют на одно
  место. Таблица обязана различить их, а не потерять один из ключей.
- **Множество (set)** хранит только факт наличия ключа.
- **Словарь (dict)** хранит пару «ключ → значение».

---

## Список отвечает по позиции, хеш — по ключу

У списка два разных вопроса имеют разную цену:

- «Что лежит на позиции 7?» — индекс уже известен, ответ O(1).
- «На какой позиции лежит комната `A-17`?» — позиция неизвестна, в общем
  случае нужен проход O(n).

Хеш-таблица заранее строит другой путь к данным: не «седьмой элемент», а
«элемент с таким ключом». Поэтому каталог `room_id → MeetingRoom` хорошо
ложится на словарь, а упорядоченный маршрут по комнатам по-прежнему удобнее
держать списком.

---

## Под капотом: почему в среднем O(1)

Упрощённая модель поиска ключа выглядит так:

```text
ключ "A-17"
      │
      ▼
 hash("A-17") = некоторое целое число
      │
      ▼
 номер начальной ячейки
      │
      ├── ячейка пуста ───────────────► ключа нет
      ├── лежит равный ключ ──────────► ключ найден
      └── лежит другой ключ
              │
              ▼
         коллизия: проверить
         следующую ячейку по правилу таблицы
```

Таблица содержит запас свободных ячеек. Когда ключи распределены достаточно
равномерно, до нужного места приходится сделать лишь несколько проверок,
даже если элементов стало намного больше. Поэтому вставка, поиск и удаление
имеют **среднюю** оценку O(1).

Коллизия не является ошибкой: она ожидаема, потому что возможных ключей
больше, чем ячеек. Реализация проверяет сам ключ, а при несовпадении ищет
другое место по своему правилу. Когда таблица становится слишком плотной,
Python выделяет таблицу большего размера и перераскладывает записи. Отдельное
расширение стоит дорого, но происходит не на каждой вставке; его стоимость
распределяется по множеству обычных операций.

В плохом случае длинная цепочка проверок может приблизить операцию к O(n).
Поэтому формулировка на собеседовании точная: «поиск в `dict` или `set` в
среднем O(1), в худшем случае O(n); структура занимает O(n) памяти».

### Контракт ключа

Хеш не может меняться, пока ключ лежит в таблице. Иначе при вставке объект
окажется в одном месте, а при поиске после изменения таблица начнёт искать
его в другом. Именно поэтому список нельзя использовать как ключ: его
содержимое можно поменять.

Числа, строки и кортежи из хешируемых элементов подходят. Замороженный
датакласс подходит, если все поля, участвующие в сравнении и хеше, тоже
неизменяемы. Ещё одно правило: если два ключа равны через `==`, их хеши
должны совпадать. Иначе словарь не сможет надёжно считать их одним ключом.

### Частая ошибка

Фраза «хеш-таблица быстрая» не означает, что ею нужно заменить любой список.
Она ускоряет вопросы по **точному ключу**. Она сама по себе не знает, какой
ключ минимальный, какой следующий, лежит ли значение в диапазоне и какой
объект был первым в исходном порядке.

---

## `set` или `dict`

Выбор определяется тем, какой ответ понадобится позже.

- Нужно только проверить «идентификатор уже встречался?» — достаточно
  множества: `seen_ids: set[str]`.
- Нужно по идентификатору получить комнату — нужен словарь:
  `rooms_by_id: dict[str, MeetingRoom]`.
- Нужно вернуть индекс ранее увиденного числа — словарь хранит
  `число → индекс`. Множество знает, что число было, но не знает где.

Не кладите в словарь фиктивные значения вроде `{"A-17": True}`, если нужен
лишь факт присутствия. Множество выражает такой контракт точнее.

---

## Мини-пример: два числа с заданной суммой

**Условие:** вернуть индексы двух разных элементов, сумма которых равна
`target`, или `None`.

**Вход:** `nums = [10, 15, 3, 7]`, `target = 17`

**Выход:** `(0, 3)`

Словарь `seen` хранит число и его индекс. На каждом шаге вычисляем
`need = target - value` и сначала ищем `need` среди уже просмотренных.

```python
def two_sum_indices(
    nums: list[int],
    target: int,
) -> tuple[int, int] | None:
    seen: dict[int, int] = {}

    for index, value in enumerate(nums):
        need = target - value
        if need in seen:
            return seen[need], index
        seen[value] = index

    return None
```

**Сухой прогон:**

1. Индекс `0`, число `10`, нужно `7`. Словарь пуст. Запоминаем `{10: 0}`.
2. Индекс `1`, число `15`, нужно `2`. Такого ключа нет. Добавляем `15: 1`.
3. Индекс `2`, число `3`, нужно `14`. Такого ключа нет. Добавляем `3: 2`.
4. Индекс `3`, число `7`, нужно `10`. Ключ есть, его индекс `0`.
   Возвращаем `(0, 3)`.

Каждый элемент обрабатывается один раз, а поиск в словаре в среднем O(1).
Итого среднее время O(n), дополнительная память O(n).

Проверка идёт **до** вставки текущего числа. Поэтому один элемент нельзя
использовать дважды: `[3]` при `target = 6` вернёт `None`. При этом
`[3, 3]` вернёт `(0, 1)`: ко второму числу первое уже находится в словаре.

---

## Когда хеш не подходит

1. **Ответ зависит от исходного порядка.** Для `allocate` нужна первая
   подходящая комната, а словарь по вместимости этот смысл теряет.
2. **Нужен диапазон, минимум или ближайший ключ.** Вопрос
   `capacity >= guest_count` не является точным поиском по ключу. Здесь
   полезнее проход, сортировка с бинарным поиском или другая структура.
3. **Память ограничена.** Множество до `n` элементов может быть неприемлемой
   ценой; отсортированный вход иногда позволяет обойтись двумя индексами.
4. **Вход очень мал или запрос выполняется один раз.** Построение индекса
   добавит код и память, но не даст заметной пользы.
5. **Ключ изменяемый.** Даже если удалось обойти запрет языка собственной
   реализацией, изменение ключа разрушит путь, по которому его ищет таблица.

Выбирать хеш стоит, когда вопрос повторяется в форме «есть ли точный ключ?»
или «какое значение связано с этим ключом?», а дополнительная память
приемлема.

## Применение в Harbor

- `rooms_by_id` позволяет получать комнату по точному идентификатору без
  прохода по каталогу.
- `seen_booking_ids` ловит повтор события или повторный импорт.
- Словарь `room_id → список броней` группирует расписание по комнате.
- Подбор первой комнаты по условию вместимости остаётся проходом: это не
  точный поиск по ключу.

## Мини-голос

> Список удобен для порядка и доступа по известному индексу.
> Хеш-таблица строит путь по ключу, поэтому поиск в среднем O(1).
> Коллизии нормальны: таблица проверяет ключ и ищет другую ячейку.
> `set` хранит факт, `dict` — ключ и связанное значение.
> За среднее O(1) я плачу O(n) памяти и не получаю порядок или диапазоны.
