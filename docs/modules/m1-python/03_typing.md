# 03 · Typing · Python 3.10–3.13

**Мост:** модели и декораторы из [01](./01_dataclasses.md)–[02](./02_methods_decorators.md)
уже с аннотациями. Здесь — зачем они, если `python` их не принуждает, и как
Protocol помогает тестам Harbor без жёсткого наследования.

**Вопрос сюжета:** как зафиксировать контракт комнаты так, чтобы IDE и
Pyright ловили враньё до прода?

### С собесов

«Зачем типы, если Python динамический?», «чем Protocol отличается от ABC»,
«что такое TypeAlias». Не просят цитировать PEP наизусть.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| аннотация | type annotation | Подсказка типа у аргумента, поля, возврата |
| объединение | union | `int \| None` — либо int, либо None |
| необязательный тип | Optional | `Optional[T]` — точный синоним `T \| None`, а не default аргумента |
| протокол | Protocol | «Если есть нужные поля/методы — тип подходит» |
| псевдоним | TypeAlias | Короткое имя для сложного типа |
| обобщённый тип | generic | Шаблон типа: `list[T]` или функция, сохраняющая связь входа с выходом |
| проверка | type checker | mypy / pyright; сам `python` типы не гоняет |

---

## Под капотом (модель)

Аннотации — это **метаданные** у функции или класса: «здесь ожидаю int».
Обычный запуск `python file.py` эти подсказки почти не читает и не превращает
в проверки. Поэтому можно вызвать `f("no")` при сигнатуре `f(x: int)` —
интерпретатор выполнит, пока внутри не упадёт что-то своё.

**Type checker** (у нас в курсе — **Pyright**, тот же движок, что у Pylance в
VS Code/Cursor) читает исходник **без запуска** и строит картину типов.
Несовпадение он показывает заранее: в IDE подчёркиванием или в CI. Типы —
дисциплина команды и инструмент раннего отлова, не «новая виртуальная машина».

В Harbor с M1 договариваемся: публичный доменный код должен быть чист по
Pyright. Mypy на рынке тоже встречается; в этом репо канон один — pyright.

У типов и runtime-проверок разные маршруты:

```text
                        ┌─> Pyright читает исходник ─> замечание до запуска
аннотации в исходнике ──┤
                        └─> Python запускает код ────> реальные значения
                                                          │
JSON / строка / БД ───────────────────────────────────────┘
                         здесь всё равно нужна валидация
```

Pyright может доказать, что функция **по коду** возвращает
`MeetingRoom | None`. Он не может обещать, что внешний JSON действительно
содержит положительное число. Проверка типов отвечает за согласованность
нашего кода, а валидация — за недоверенные данные на границе Harbor.
Один инструмент не заменяет другой.

## База 3.10+

```python
def capacity_left(total: int, taken: int) -> int:
    return total - taken


def find_id(row: dict[str, str] | None) -> str | None:
    if row is None:
        return None
    return row.get("id")
```

В Python 3.10+ обычно пишут `str | None`. Запись
`Optional[str]` означает **ровно то же самое**: значение является строкой
или `None`. Слово Optional часто обманывает новичка: оно не разрешает
пропустить аргумент.

```python
from typing import Optional


def by_id(room_id: Optional[str]) -> str:
    return "default" if room_id is None else room_id


by_id()      # TypeError: аргумент всё ещё обязателен
by_id(None)  # допустимо
```

Чтобы аргумент можно было не передавать, нужен default:

```python
def by_id(room_id: str | None = None) -> str:
    return "default" if room_id is None else room_id
```

`list[str]`, `dict[str, int]` — встроенные обобщённые типы (с 3.9 не нужно
тянуть `List`/`Dict` из `typing` для этих случаев).

Смысл для читателя: по сигнатуре видно, может ли прийти «пусто» и что
функция обещает вернуть. Это ускоряет ревью и уменьшает угадывание.

## Дженерики без магии

`list[str]` — уже применение обобщённого типа: сам контейнер один, а тип
элемента подставлен как параметр. `list[MeetingRoom]` сообщает не только
«здесь список», но и что можно безопасно читать у каждого элемента.
Голый `list` стирает эту информацию, и проверяющему приходится доверять
нам или распространять `Any`.

Иногда параметр типа связывает вход и выход функции:

```python
from collections.abc import Sequence
from typing import TypeVar

T = TypeVar("T")


def first_or_none(items: Sequence[T]) -> T | None:
    if not items:
        return None
    return items[0]
```

`T` означает не «какой-нибудь объект вообще», а **один и тот же выбранный
тип в рамках вызова**. Для `first_or_none(["A", "B"])` Pyright выводит
`str | None`; для списка комнат — `MeetingRoom | None`. Если заменить
возврат на `object | None`, связь потеряется, и вызывающий код уже не сможет
без проверки обратиться к полям комнаты. На M1 достаточно уметь читать
такую сигнатуру; сложные ограничения параметров типа появятся по нужде.

### Сухой прогон вывода типа

Пусть `rooms` имеет тип `list[MeetingRoom]`.

1. `list[MeetingRoom]` подходит под `Sequence[T]`.
2. На этом вызове Pyright подставляет вместо `T` тип `MeetingRoom`.
3. Объявленный результат становится `MeetingRoom | None`.
4. После `room = first_or_none(rooms)` выражение `room.capacity` пока
   небезопасно: список мог быть пуст.
5. После `if room is None: return` в оставшейся ветке Pyright сужает тип до
   `MeetingRoom`, и `room.capacity` уже корректен.

Это мысленный прогон, а не работа интерпретатора. Во время запуска Python
просто проверит список и вернёт элемент или `None`.

## TypeAlias

```python
from typing import TypeAlias

ResourceId: TypeAlias = str
Tags: TypeAlias = tuple[str, ...]
```

Когда тип длинный или одно и то же имя встречается в десяти местах, дают
короткое имя. На собесе достаточно сказать: «псевдоним сложного типа».
С 3.12 есть синтаксис `type ResourceId = str`. В Harbor на 3.10–3.11
ориентируйтесь на `TypeAlias`.

## Protocol — утиная типизация

Иногда функции нужна не конкретная иерархия классов, а «объект, у которого
есть вместимость». `Protocol` записывает такой структурный договор: если у
объекта есть перечисленные поля и методы подходящих типов, он годится без
явного наследования. Это удобно на границе Harbor и в тестах, где простой
фейк не должен вступать в искусственную родословную классов.

```python
from typing import Protocol


class HasCapacity(Protocol):
    @property
    def capacity(self) -> int:
        ...


def ok_for_guests(item: HasCapacity, guests: int) -> bool:
    return item.capacity >= guests
```

Подойдёт любой объект, у которого можно прочитать целочисленную
`capacity`, — `MeetingRoom`, тестовый фейк, простая заглушка. Свойство в
протоколе подчёркивает, что функция только читает значение и не требует
права его менять; обычное поле объекта тоже удовлетворяет такому чтению.
Наследовать общий ABC не обязательно. При этом `Protocol` не проверяет
бизнес-правило `capacity > 0`: он описывает форму объекта, а инвариант
по-прежнему поддерживает сама модель.

**Protocol vs ABC.** ABC (`abc.ABC`) — когда хотите запретить создать
«пустой» базовый класс и заставить наследников реализовать методы через
наследование. Protocol — когда важны **поля и методы**, а не родословная.
В тестах Harbor фейк с нужным полем проходит Protocol без лишней иерархии.

## Callable и декораторы

```python
from collections.abc import Callable

Payload = dict[str, object]
Handler = Callable[[Payload], Payload]
```

Так описывают «вызываемый объект: на входе словарь с текстовыми ключами,
на выходе такой же вид данных». Параметры внутри `dict` не дают случайно
превратить его в неявный `Any`. Для строгих декораторов позже появляются
`ParamSpec` и `TypeVar`; на middle достаточно не бояться `Callable` и
помнить про `wraps` из прошлой главы.

## Что проверки типов не делают

```python
def f(x: int) -> int:
    return x


f("no")  # python может выполнить; pyright — ошибка
```

Не путайте «тип checker зелёный» с «в проде все данные честные». Грязный
JSON с границы всё равно валидируют (позже pydantic). Аннотации — контракт
для кода, который вы контролируете, и сигнал для инструментов.

## Подготовка к Pyright в M1b

В M1b вы подключите Pyright руками и разберёте его сообщения. Сейчас
конфигурацию и отдельный каркас создавать не нужно. Полезнее заранее
научиться читать типовую ошибку как вопрос к пути данных.

```python
room = first_or_none(rooms)
print(room.capacity)
```

Проверяющий видит `MeetingRoom | None` и справедливо возражает: при пустом
списке обращение к `capacity` упадёт. Исправление — не «заставить Pyright
замолчать», а обработать обе ветки:

```python
room = first_or_none(rooms)
if room is None:
    print("Подходящих комнат нет")
else:
    print(room.capacity)
```

Такое сужение типа отражает реальное управление потоком. Комментарий
`# type: ignore` уместен только когда вы понимаете, какой факт инструмент
не смог вывести; как первая реакция он прячет дыру в договоре.

## Применение

- Публичные функции домена Harbor — аннотации + `pyright` clean.
- Protocol `HasCapacity` для комнаты и фейков в тестах.
- FastAPI/pydantic опираются на аннотации (M7).

## Упражнение в главе

1. Объясните вслух разницу между
   `room_id: str | None`, `room_id: str | None = None` и возвращаемым
   `MeetingRoom | None`. Для каждого случая скажите, что именно может
   отсутствовать: аргумент в вызове, значение аргумента или результат.
2. Не запуская код, выведите тип результата для
   `numbers: list[int] = [1, 2, 3]` и
   `empty_rooms: list[MeetingRoom] = []`. Затем назовите проверку во время
   выполнения, которую всё равно придётся сделать перед чтением атрибута у
   возможной комнаты.

## Мини-голос

> Аннотации — договор для людей и Pyright, а не runtime-валидация.
> `Optional[T]` и `T | None` равны; пропустить аргумент позволяет только
> default. Дженерик сохраняет связь типов входа и выхода.
> Protocol описывает нужную форму объекта без обязательного наследования.
> Ошибку Pyright читаю как непройденную ветку данных, а не как помеху,
> которую надо сразу скрыть.
