# 01 · dataclass · frozen · slots

**Мост:** цикл из M0.5 учит начинать с примеров. Здесь первый «пример» домена —
объекты комнаты и запроса, без которых не о чем говорить в Harbor.

**Вопрос сюжета:** как представить переговорку и запрос на бронь так, чтобы
не писать руками `__init__`/`__repr__`, не разделить случайно один список
между объектами и не позволить невалидному запросу пройти дальше?

### С собесов

«Что такое dataclass?», «чем frozen отличается», «можно ли dataclass ключом
dict», «slots зачем». Редко просят написать декоратор `@dataclass` с нуля —
ждут, когда брать и какие грабли.

---

## Словарь

| Термин | English | На пальцах |
|--------|---------|------------|
| датакласс | dataclass | Класс под данные: поля в аннотациях, шаблонный код пишет Python |
| поле | field | Атрибут с типом и опциями (`default`, `default_factory`) |
| замороженный | frozen | После создания поля нельзя менять |
| хеш-контракт | hash contract | Хеш ключа не меняется, пока ключ лежит в `dict` или `set` |
| слоты | `__slots__` | Заранее известный набор атрибутов вместо словаря на каждый объект |
| инвариант | invariant | Условие, которое должно быть истинным для корректного объекта |
| DTO | data transfer object | «Перенести данные», без жирной бизнес-логики |

---

## Под капотом (модель)

Обычный класс с полями вы пишете руками: конструктор, красивая печать,
сравнение «равны ли два объекта». Датакласс — договор с Python: вы
перечисляете поля и типы, а декоратор `@dataclass` **генерирует** эти методы
за вас.

Интерпретатор по-прежнему **не проверяет** типы в рантайме. Аннотации здесь —
подсказка генератору и читателю. Получается обычный класс: у экземпляра есть
атрибуты, их можно читать (а без `frozen` — и менять).

Отдельно запомните два флага:

- `frozen=True` подменяет присваивание в поля на ошибку: снаружи объект
  выглядит как снимок, который нельзя «подкрутить».
- `default_factory` вызывается **на каждый** новый экземпляр. Поэтому новый
  список тегов не оказывается общим на все комнаты сразу (см. ниже).

Схема показывает границу ответственности. Декоратор пишет механическую часть,
а правила предметной области всё равно формулируем мы:

```text
аннотации полей
      │
      ▼
@dataclass ── генерирует ──> __init__ / __repr__ / __eq__
      │
      └── наш код ─────────> инварианты / смысл полей / границы мутации
```

Если перепутать эти две части, легко решить, будто `guest_count: int`
автоматически запрещает строку или отрицательное число. Не запрещает:
аннотацию прочитает проверка типов, а значение в рантайме обязан проверить
сам класс или код на границе системы.

## Руками → принято

**Руками** (идея — что пришлось бы писать без декоратора):

```python
class BookingRequestManual:
    def __init__(self, guest_count: int, duration_minutes: int) -> None:
        self.guest_count = guest_count
        self.duration_minutes = duration_minutes

    def __repr__(self) -> str:
        return (
            f"BookingRequestManual({self.guest_count!r}, "
            f"{self.duration_minutes!r})"
        )
```

**Принято:**

```python
from dataclasses import dataclass


@dataclass
class BookingRequest:
    guest_count: int
    duration_minutes: int

    def __post_init__(self) -> None:
        if self.guest_count <= 0:
            raise ValueError("guest_count must be positive")
        if self.duration_minutes <= 0:
            raise ValueError("duration_minutes must be positive")


# вход
req = BookingRequest(2, 60)
# выход
assert req.guest_count == 2 and req.duration_minutes == 60
print(req)  # BookingRequest(guest_count=2, duration_minutes=60)
```

Сгенерированный `__init__` сначала присваивает оба поля, затем вызывает
`__post_init__`. Так проверка стоит в одной точке: нельзя забыть её в одном
обработчике и вспомнить в другом. Если проверка бросила `ValueError`,
запрос с неположительным значением не передаётся вызывающему коду как
готовый объект.

### Читаем свой код: инвариант `BookingRequest`

Инвариант этого запроса можно произнести без Python:

> Число гостей и длительность брони — положительные целые числа.

Сначала читаем поля и называем правило, потом ищем место, которое его
поддерживает. Аннотация `int` помогает Pyright заметить строку, а
`__post_init__` отсекает `0` и отрицательные числа во время выполнения.
Это две разные линии защиты: проверка типов не видит значение
`duration_minutes=-10`, а runtime-проверка не объясняет IDE, какой тип
ожидается.

Если объект строится прямо из недоверенного JSON, одной этой пары всё ещё
мало: положительное значение `1.5` пройдёт сравнение `> 0`, потому что
Python не проверяет аннотацию `int` в рантайме. На границе нужно разобрать
и проверить входные данные, а внутрь домена передавать уже целые числа.
Инвариант — это договор модели; аннотация, фабрика и `__post_init__`
поддерживают разные части этого договора.

Здесь класс не `frozen`, поэтому проверка гарантирует корректность **при
создании**, но не на всю жизнь объекта:

```python
request = BookingRequest(2, 60)
request.guest_count = 0  # dataclass разрешит, инвариант уже нарушен
```

Если запрос в Harbor — снимок входа и его нельзя править по пути, уместно
сделать его `frozen=True`. Если изменения нужны, меняйте состояние через
методы, которые снова проверяют правило, а не прямым присваиванием.
Логику «какую комнату выбрать» сюда всё равно не кладите: она сравнивает
запрос с каталогом комнат и относится к отдельной функции или сервису.

### Сухой прогон конструктора

Прогоним `BookingRequest(3, 45)` без интерпретатора:

1. Сгенерированный `__init__` записывает `guest_count = 3`.
2. Он записывает `duration_minutes = 45`.
3. Python вызывает `__post_init__`; обе проверки ложны.
4. Вызывающий код получает корректный объект.

Для `BookingRequest(0, 45)` третий шаг бросит `ValueError`. Четвёртого шага
не будет. Такой прогон полезнее фразы «валидация есть»: он показывает,
в какой момент перестаёт существовать нормальный путь выполнения.

## default и default_factory

Иногда у поля есть значение «если не передали». Для чисел и строк достаточно
обычного default. Для нового списка или словаря на каждый экземпляр нужна
фабрика — функция, которая создаст значение в момент вызова конструктора.

```python
from dataclasses import dataclass, field


@dataclass
class MeetingRoom:
    id: str
    capacity: int
    tags: list[str] = field(default_factory=list)
```

**Вход:** `MeetingRoom("r1", 2)` → у комнаты свой пустой `tags == []`.

**Почему не `tags: list[str] = []`?** Само выражение `[]` вычисляется
**один раз**, когда выполняется тело класса. Если затем использовать этот
объект как значение по умолчанию, разные экземпляры будут ссылаться на один
список: тег, добавленный комнате A, внезапно появится у комнаты B.

Современный `dataclass` распознаёт очевидный изменяемый default и уже при
объявлении класса бросает `ValueError`. Это не отдельная причуда библиотеки,
а защита от описанного общего состояния. `field(default_factory=list)`
передаёт не готовый список, а функцию `list`; сгенерированный `__init__`
вызывает её заново для каждой комнаты. У пользовательского изменяемого
объекта автоматическая защита может не помочь, поэтому правило шире:
**новое значение на экземпляр создаём фабрикой**.

В Harbor для тегов удобств часто лучше сразу `tuple[str, ...] = ()`: кортеж
нельзя «дописать» на месте, меньше сюрпризов. См. домашку.

## frozen — когда и зачем

```python
@dataclass(frozen=True)
class MeetingRoomId:
    value: str


rid = MeetingRoomId("A101")
# rid.value = "B"  # FrozenInstanceError — поле менять нельзя
```

**Неизменяемость.** После создания объект — снимок. Это удобно для id комнаты,
ключа кэша, «запроса как его приняли»: никто по пути не подменит поле молча.

**Хешируемость (`__hash__`).** При обычных настройках `dataclass`
связка `eq=True, frozen=True` позволяет сгенерировать хеш из полей. Словарь
сначала выбирает корзину по хешу, а затем проверяет равенство кандидатов.
Поэтому у ключа есть договор: равные объекты имеют одинаковый хеш, а хеш
объекта не меняется, пока тот лежит в `dict` или `set`.

Обычный изменяемый датакласс по умолчанию нехешируем. Это безопасное решение:
иначе мы могли бы положить объект в словарь, поменять поле, участвующее в
равенстве, и искать уже по новому хешу не в той корзине.

`frozen=True` замораживает присваивания только верхнего уровня. Он не
превращает вложенный `list` в кортеж:

```python
@dataclass(frozen=True)
class BrokenRoomKey:
    room_id: str
    tags: list[str]


key = BrokenRoomKey("A101", ["quiet"])
hash(key)  # TypeError: unhashable type: 'list'
```

Здесь Python не ломает словарь молча, а отказывается получить хеш, потому
что `list` нехешируем. Ещё опаснее пользовательский изменяемый объект,
который объявил собственный хеш: его внутреннее состояние можно поменять и
действительно нарушить контракт. Практическое правило для ключа простое:
каждое поле, участвующее в сравнении и хеше, должно быть хешируемым и
стабильным по смыслу. Для набора тегов подходит `tuple[str, ...]`, для
идентификатора — строка.

```python
@dataclass(frozen=True, slots=True)
class MeetingRoomKey:
    room_id: str
    tags: tuple[str, ...] = ()


prices = {MeetingRoomKey("A101", ("quiet",)): 1500}
assert prices[MeetingRoomKey("A101", ("quiet",))] == 1500
```

Два разных экземпляра равны по полям, дают одинаковый хеш и находят одну
запись. Именно этот сценарий нужно иметь в виду, а не лозунг
«`frozen` автоматически делает всё неизменяемым».

**Сюжет Harbor:** id комнаты и снимок запроса — frozen DTO; занятость по
времени живёт в хранилище броней, а не в «вечном» объекте комнаты.

## slots (3.10+)

```python
@dataclass(slots=True)
class Point:
    x: float
    y: float
```

Обычный экземпляр хранит атрибуты в словаре `__dict__`: гибко, но на каждый
объект есть накладные расходы. `slots=True` говорит: набор имён полей
известен заранее, отдельный `__dict__` не нужен. На миллионах мелких объектов
это экономит память; заодно нельзя случайно навесить `point.foo = 1` —
опечатка в имени сразу видна.

Цена этой жёсткости — меньше динамики: код, который рассчитывает дописывать
произвольные атрибуты или напрямую читать `obj.__dict__`, перестанет
работать. Наследование со слотами тоже требует внимания. Поэтому `slots`
не ставят как талисман «для скорости»: в маленьком Harbor сначала важнее
понятная модель, а экономию памяти проверяют измерением. Связка
`frozen=True, slots=True` хорошо подходит для множества маленьких DTO,
когда набор полей действительно закрыт.

## До / после

```python
# BAD — общий список на всех, кто не передал features
class Room:
    def __init__(self, name: str, features: list[str] = []):
        self.name = name
        self.features = features


# GOOD — новый список на каждый экземпляр
@dataclass
class Room:
    name: str
    features: list[str] = field(default_factory=list)
```

## Применение

- Тело JSON → dataclass (позже pydantic в M7; идея «поля = контракт» та же).
- Ключ кэша: frozen dataclass из параметров запроса.
- Harbor: `MeetingRoom`, `BookingRequest` в домене.

## Мини-голос

> Dataclass генерирует механические методы, но не придумывает инварианты.
> Новый список для каждого объекта даёт `default_factory`.
> Frozen запрещает присваивание полей, но не замораживает вложенный список.
> Ключ словаря обязан иметь стабильные равенство и хеш.
> Slots убирает `__dict__`, экономит память и запрещает случайные атрибуты,
> но нужен только при понятной цене этой жёсткости.
